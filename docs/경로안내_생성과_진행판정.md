# 경로 안내 생성과 진행 판정

목적지를 말한 순간부터 "왼쪽으로 꺾으세요"가 폰에서 나오기까지, 서버 안에서 무슨 일이
일어나는지 전부 적는다.

두 덩어리다.

    무엇을 말할지   경로 노드가 정한다    app/nav/cues.py
    언제 말할지     비콘이 정한다        app/ws/path_tracker.py

이 둘을 섞으면 안 된다는 것이 이 문서의 전제다. 노드는 지도의 기하이고 비콘은 폰이
감지할 수 있는 유일한 신호인데, 성질이 달라서 한 덩어리로 다루면 어느 쪽 문제인지
구분이 안 된다.

---

# 1부 — 안내 문구 만들기

## 1.1 전체 흐름

```
목적지 확정
   ↓
build_route()                    route_engine.py
   ├ source.graph()              마스크 → 노드·간선          path_nodes.py
   ├ find_node_path()            다익스트라 → node_ids
   └ to_beacon_sequence()        경로 선을 1m 훑어 비콘 순서
   ↓
cues.build()                     cues.py
   ├ walk_owners()               비콘 순서 + 누적거리
   ├ extract()                   노드 → 사건 목록
   ├ nearest_owners()            노드 → 주인 비콘
   ├ assign_by_*()               사건 → 안내할 비콘
   └ finalize()                  합치기 + 거리 표현
```

## 1.2 노드 간격이 넓다 — 그래서 선을 훑는다

관리자웹이 만드는 그래프는 노드가 **코너·맞은편·입구**에만 있다. 긴 복도는 양 끝
두 점뿐이라, 그 사이에 늘어선 비콘이 통째로 빠진다.

그래프에 노드를 더 넣으면 관리자웹이 보여주는 것과 갈라진다. 그래서 노드는 그대로
두고 **훑기만 촘촘하게** 한다.

```python
# route_engine.py
SAMPLE_STEP_M = 1.0

def _walk(graph, node_ids, meters_per_px):
    for (a, a_id), (b, b_id) in zip(pts, pts[1:]):
        n = max(1, int(seg / step_px))
        for i in range(1, n + 1):
            t = i / n
            yield (a.x + (b.x-a.x)*t, a.y + (b.y-a.y)*t), (a_id if t < 0.5 else b_id)
```

**저장되지 않는다.** 경로를 계산하는 그 순간에만 존재하는 가상의 점이다.

### 알려진 구멍

`n = max(1, int(seg / step_px))` 라 **1~2m 구간은 끝점 하나로만 표본화된다.**
그 구간 중간에서만 이길 수 있는 비콘은 빠진다. 실측 4층 407 경로는 13개 구간 중
4개가 2m 미만이었다(그 경로에서 실제로 빠진 비콘은 없었다).

## 1.2.5 건너기에 걸리는 규칙은 둘이다

경로 탐색(`find_node_path`)에서 `cross` 엣지에 걸리는 조건이 둘 있다. **관리자웹
`pathfind.ts` 와 같아야 한다** — 화면에서 검수한 경로와 안내에 쓰는 경로가 갈라지면
검수 자체가 의미를 잃는다.

```python
# ① 목적지 건너기는 그 목적지가 출발지일 때만
if is_cross:
    a = graph.node(e.a)
    if a is not None and a.type == "landmark" and a.id != start_id:
        continue

# ② 건너기는 단방향 — a(입구·벽 끝) → b(맞은편)
if not e.directed:
    adj[e.b].append(...)
```

**①이 왜 필요한가.** 목적지 건너기는 "여기서 출발해 반대편으로 건너세요"라는 뜻이다.
무관한 두 지점 사이의 최단 경로가 지나가는 길에 **남의 방 문 앞을 지름길처럼
가로질러** 버리면, 그 목적지에 있지도 않은 사람에게 벽에서 손을 떼라는 안내가 나간다.
연결자(계단·엘리베이터)는 원래 경로 중간에 거쳐가는 지점이라 이 제한을 두지 않는다.

**②가 왜 필요한가.** 맞은편 지점은 벽에서 떨어진 허공이라 거기서 출발할 수가 없다.

> **한동안 ①이 빠져 있었다.** `path_nodes.py` 를 재포팅할 때 ②만 가져왔다.
> 실측 4층 757쌍 중 **205쌍(27%)이 관리자웹과 다른 경로로 안내되고 있었다.**
> 예: `B1 → 411` 이 `N77 → N12` 로 남의 문 앞을 건너뛰어 14칸으로 끝났는데,
> 관리자웹은 복도를 돌아 18칸이었다. 2026-08-23 에 고쳤다(§1.8 재검사).
>
> 테스트가 못 잡은 이유는 기대값 생성기가 `directed` 와 노드 `type` 을 안 실어서다.
> `gen_pathnodes_reference.mjs` 가 둘을 싣게 고치고 규칙 ①②를 밟는 케이스 4개를
> 추가했다(`directed_forward` `directed_backward` `landmark_cross_not_shortcut`
> `landmark_cross_from_itself`).

## 1.3 비콘 순서 정하기

각 표본에서 **반경 안 가장 가까운 비콘 하나**를 고르고, 직전과 같으면 접는다.

```python
BEACON_MATCH_RADIUS_M = 3.0     # db_map_source.py
```

**연속이 아닌 중복은 접지 않는다.** ㄷ자로 들어갔다 나오는 경로에서 같은 비콘 옆을
두 번 지나는 것은 실제로 일어나는 일이고, 그때는 두 번 세는 것이 맞다. 다만 이것이
2부의 판정에서 문제를 만든다(§2.7).

반경을 줄이면 경로 밖 비콘이 빠지지만 경로 위 비콘도 같이 빠진다. 실측 4층 B1→407:

| 반경 | 칸 수 | 결과 |
| --- | --- | --- |
| 3.0m | 9 | B4·B8 처럼 경로 밖 비콘까지 포함 |
| 2.0m | 7 | 경로 밖은 빠지고 경로 위는 유지 |
| 1.5m | 5 | B18·B19 까지 잃어 구간이 벌어짐 |

## 1.4 사건 뽑기 — `extract()`

**비콘을 보지 않는다.** 나오는 것은 "경로의 몇 m 지점에서 무슨 일이 일어나는가"뿐이다.

| 조건 | 사건 | 문구 | 표 번호 |
| --- | --- | --- | --- |
| `edge.type == "cross"` 시작 노드 | `crossEnter` | 벽이 끊깁니다. 손을 떼고 직진하세요. | 6 |
| 그 엣지의 끝 노드 | `crossExit` | 벽이 끊깁니다. 벽에 도달하면 {방향}으로 꺾으세요. | 7 |
| 중간 노드에서 회전각 ≥ 30° | `turn` | 벽을 따라 {방향}으로 꺾으세요. | 4 |
| 직전 사건에서 12m 이상 무사건 | `straight` | 계속 직진하세요. | 3 |
| 마지막 노드 | `arrive` | {목적지}입니다. | 12 |

### 회전 방향

```python
cross = (v1x*v2y - v1y*v2x) / (n1*n2)
return "right" if cross > 0 else "left"
```

**화면 좌표라 y 가 아래로 증가한다.** 그래서 `cross > 0` 이 오른쪽이다. 이걸 뒤집으면
"왼쪽으로 꺾으세요"가 오른쪽으로 나가고, 화면을 볼 수 없는 사용자는 확인할 방법이 없다.

### crossExit 가 회전을 삼킨다

횡단 도달 안내가 이미 방향을 말하므로, 그 노드에서는 `turn` 을 따로 만들지 않는다.
안 그러면 같은 코너를 두 번 말한다(실측 407 경로에서 4.9·17.4·37.8m 세 군데가 그랬다).

### crossExit 도 "벽이 끊깁니다"를 담는다

진입과 도달이 **다른 비콘에 배정될 수 있다.** 그때 도달 안내만 들으면 "벽에 도달하면"이
무슨 말인지 알 수 없다. 같은 비콘에 모이면 §1.7 에서 한 문장으로 합친다.

## 1.5 주인 정하기 — `nearest_owners()`

노드에서 **가장 가까운 경로 비콘**이 주인이다. 후보는 경로에 오른 비콘뿐이다 —
경로 밖 비콘이 아무리 가까워도 그것이 잡히는 순간을 추적기가 안 보므로 안내를 걸 수 없다.

### 반경으로 자르지 않는다

한때 3m 안에서만 주인을 찾았다. 그랬더니 **2.9m 는 살고 3.2m 는 안내가 통째로
사라졌다.** 0.3m 차이로 회전 안내가 없어지는 셈이다. 반경은 "경로에 어느 비콘을
세울지" 고를 때 쓰는 값이지 이미 세워진 비콘에 노드를 나눠 줄 때 쓰는 값이 아니다.

### 순서를 건너뛰지 않는다

경로에 같은 비콘이 두 번 이상 나오면, 좌표만으로는 **어느 쪽 칸인지 가릴 수가 없다.**
같은 비콘이니 거리가 똑같이 나온다.

```python
repeated = len({b.id for _, b in route}) < len(route)

floor_index = 0
for nid in node_ids:              # 노드 순서대로
    후보 = [i for i in route if not (repeated and i < floor_index)]
    owner[nid] = 가장 가까운 후보
    floor_index = owner[nid]
```

주인 index 가 **앞으로만 간다.** 중복이 없으면 이 제약을 걸지 않는다 — 순서가 꼬일
일이 없는데 걸면 정상 배정까지 틀어진다.

> **실측 사례** — B25 → 412 경로는 `B25 B12 B11 B10 B11 B24 B23 B22` 로 B11 이 두 번
> 나온다. 22.0m 회전의 주인이 B11 인데 좌표만 보면 둘 다 1.8m 라 앞쪽(9.2m 지점)을
> 집었고, 그 한 칸 앞이 B12(6.1m) 여서 **15.9m 앞서 안내**했다. 순서 제약을 넣으니
> 뒤쪽 B11 이 주인이 되고 안내는 B10(13.1m)으로 옮겨갔다.

## 1.6 배정 — 세 가지 방식

셋 다 "사건보다 앞선 비콘에서 미리 말한다"는 같은 일을 한다. 다른 것은 **얼마나
앞설지를 무엇으로 재느냐**다.

| 방식 | 규칙 | 함수 |
| --- | --- | --- |
| 거리 | 사건보다 여유(회전 2m·횡단 4m) 이상 앞선 마지막 비콘 | `assign_by_distance` |
| **소유** | 주인 비콘의 **한 칸 앞** | `assign_by_owner` |
| 절충 | 한 칸 앞을 쓰되 10m 초과면 거리 방식 | `assign_by_hybrid` |

```
비콘 간격이 좁으면(2m)  2m 앞 = 한 칸 앞      → 같은 답
비콘 간격이 넓으면(6m)  2m 앞 = 직전 칸       → 거리는 여유를 못 채움
                      한 칸 앞 = 6m 앞       → 소유는 너무 일찍 말함
```

### 왜 미리 말하나

코너에 있는 비콘에서 "꺾으세요"라고 하면 **이미 코너를 지난 뒤**다. 게다가 그 비콘의
판정이 늦어지면 아예 말할 기회를 놓친다.

횡단은 더 앞당긴다(4m). 코너는 늦어도 벽을 짚고 있어 손으로 느끼지만, 횡단은 벽에서
손을 떼는 일이라 안내를 놓치면 사용자가 벽 끝에서 멈춰 선다.

### 도착만은 예외

셋 다 **마지막 비콘에 고정**한다. 다른 안내는 "곧 무엇을 하라"는 예고지만 도착은
"지금 여기가 그곳이다"라는 사실이라 앞당기면 거짓말이 된다.

> 한 칸 앞을 그대로 적용했을 때 실측 4층에서 평균 6m, 최악 15m 전에 "계단1입니다"가
> 나갔다. 사용자는 엉뚱한 문 앞에 선다.

## 1.7 다듬기 — `finalize()`

배정이 끝난 뒤에 한다. 어느 비콘에 몇 개가 모였는지는 배정해봐야 안다.

### 순서

```
merge_crossing()  →  collapse()  →  lead_phrase()
```

### 횡단 합치기 — `merge_crossing()`

한 비콘에 `crossEnter` + `crossExit` 가 나란히 있으면:

```
벽이 끊깁니다. 손을 떼고 직진하세요.
벽이 끊깁니다. 벽에 도달하면 왼쪽으로 꺾으세요.
        ↓
벽이 끊깁니다. 손을 떼고 직진하다가, 벽에 도달하면 왼쪽으로 꺾으세요.
```

한 번 끊기는 벽을 두 번 끊긴다고 말하는 셈이라 잇는다.

### 다중 회전 — `collapse()`

한 비콘에 `turn` 이 둘 이상이면 `turnMulti` 하나로:

```
벽을 따라 계속 가세요.        (표 5번)
```

방향을 하나씩 세면 어느 것이 지금 할 일인지 알 수 없고, 0.7m/s 로 걷는 사람에게 세
문장은 다 듣기 전에 첫 코너를 지난다. 이런 자리는 대개 복도가 계단식으로 꺾이는
곳이라 벽을 짚고 있으면 손이 알아서 따라간다.

**회전만 접는다.** 횡단은 손을 떼는 일이라 하나하나가 다른 동작이다.

### 거리 표현 — `lead_phrase()`

안내하는 비콘에서 그 일이 벌어지는 지점까지의 거리를 말에 담는다.

| 거리 | 접두 | 0.7m/s 기준 |
| --- | --- | --- |
| 6m 미만 | 없음 | 9초 안 — 몇 걸음이라 "지금 할 일" |
| 6~15m | `조금 뒤` | 9~21초 |
| 15m 이상 | `약 {5m 단위}미터 뒤` | 어림짐작이 안 되니 숫자로 |

`straight` 에는 안 붙인다. 지점을 가리키는 말이 아니라 지금 상태를 확인해 주는
말이라 "조금 뒤 계속 직진하세요"는 뜻이 안 통한다.

> 처음에 3m 부터 붙였더니 거의 모든 안내에 수식이 달려서 정작 정말 먼 것과 구분이
> 안 됐다. "잠시 후"도 뺐다 — "조금 뒤"와 어느 쪽이 더 먼지 사용자가 알 수 없다.

# 2부 — 진행 판정

`app/ws/path_tracker.py`. 폰이 올린 RSSI 로 "지금 몇 번째 칸인가"를 정한다.

## 2.1 판정기가 둘이다

```
handler._tracker        /ws 용 — 전역 하나 (bleapp · /monitor 수동 경로)
NavSession.tracker      /ws/navigation 용 — 연결마다 하나 (사용자앱)
```

`/monitor` 판정 설정은 `handler._track_tuning` 에 저장되고, **경로를 걸 때** 양쪽 모두
읽어간다.

```python
session.tracker.set_path(plan.keys, **_track_tuning)     # navigation_ws.py
```

이미 진행 중인 안내에는 반영되지 않는다 — `set_path` 는 경로를 걸 때만 부른다.

## 2.2 세 가지 모드

| 모드 | 추세 계산 | 확정 |
| --- | --- | --- |
| `trend` | 최근 40개 중 양끝 4개씩 평균차 | ① 통과 즉시 |
| `segment` | 시간 창을 5구간으로 쪼갠 기울기 | ① 통과 즉시 |
| **`confirm`** (기본) | segment 와 동일 | ① → ② 대기 → ③ 재확인 |

`confirm` = `segment` + 확인 단계다.

## 2.3 전진 판정

### ① 추세 + 교차 (같은 순간)

```python
trend_cur  < -threshold          현재가 떨어지는 중
trend_next > +threshold          다음이 오르는 중
next_latest > cur_latest         실제로 값이 역전됨
next_latest > min_next           다음이 너무 약하지 않음
```

넷이 **한 번의 판정에서 동시에** 성립해야 하고, `forward_streak_need` 회 연속이어야 한다.

### ② 무장

`confirm` 모드는 여기서 확정하지 않고 `armed` 상태로 들어간다. 안내는 안 나간다.

### ③ 확인 (`confirm_delay_ms` 뒤부터)

```python
other_g - cur_g >= confirm_gap        기본 5.0dB
```

그 사이 다시 역전되면(`other_g <= cur_g`) **취소**하고 처음으로 돌아간다.
못 미치면 취소가 아니라 계속 지켜본다 — 대기 시간은 "이때부터 본다"는 뜻이지 마감이 아니다.

## 2.4 후퇴 판정

전진과 대칭이지만 **연속 요구가 더 많다**(`back_streak_need` 기본 3, 전진은 2).
틀렸을 때 대가가 다르기 때문이다 — 전진 오판은 번호를 하나 건너뛰는 정도지만,
후퇴 오판은 `"경로를 벗어났습니다. 뒤로 돌아가세요"` 가 나가서 잘 가고 있는 사람을
되돌려 세운다.

```python
trend_prev > threshold
trend_prev > trend_next
prev_latest > cur_latest
not next_rising                  ← 아래 참고
```

### 다음이 오르는 중이면 후퇴가 아니다

코너를 돌아 다음 비콘 쪽으로 향하면 **현재 비콘은 이미 등졌는데 다음 비콘은 아직
안 올라온** 골짜기가 생긴다. 그 몇 초 동안은 이전 비콘이 셋 중 제일 세다.
이것만 보면 "뒤로 갔다"로 읽힌다.

> **실측 사례** — 412 경로에서 4번(B24) 도달 3.4초 뒤에 3번(B11)으로 되돌려
> "경로를 벗어났습니다"가 나갔다. 사용자는 정상적으로 걷고 있었다.
> 그래프에서 13.5초에 B24 가 정점 후 급락하고, 다음 비콘 B5 는 16초가 넘어서야
> 올라오기 시작한다. 그 사이가 골짜기다.

```python
next_rising = trend_next is not None and trend_next > self.threshold
```

정말 되돌아가는 중이라면 다음 비콘은 멀어지므로 이 조건이 후퇴를 막지 않는다.

확인 단계(`_confirm_stage`)에서도 같은 검사를 한 번 더 한다 — 무장은 골짜기 초입에
이미 걸렸을 수 있다.

### 검증

```
골짜기 — 다음 오름            forward   6.8초    (이탈 아님)
정상 전진 — 다음만 오름        forward   5.8초
진짜 되돌아감 — 다음 떨어짐     backward  3.2초    (이탈 유지)
진짜 되돌아감 — 다음 정지       backward  3.2초
```

실측 13개 데이터셋 재평가에서 성능 변화 없음 — 정지 오탐 0 · 매칭 26 · 평균 지연
+1.51초 · 최대 +4.67초. 왕복 데이터셋(`walk_roundtrip`)도 8/8 그대로.

## 2.5 연속 횟수는 시간 필터가 아니다

`evaluate()` 는 **비콘 패킷이 올 때마다** 불린다. 실측에서 초당 32~118회였다.

```
2회 연속 = 17~62ms
```

같은 잡음 봉우리 안이다. 시간 필터 역할은 **추세 창(2초)** 과 **confirm 대기(0.5초)**
가 한다. `min_hold_ms` 기본값이 0인 이유가 이것이다 — 켜면 검출만 깎인다(27 → 25건).

추세를 끄면(`require_trend=false`) 시간 필터가 통째로 사라지므로 `min_hold_ms` 를
반드시 켜야 한다.

## 2.6 안 들리는 칸은 건너뛴다

경로에는 아직 한 번도 안 잡힌 비콘도 들어 있다(목적지가 정해지면 DB 로 경로 전체를
미리 세우기 때문). 바로 옆 칸만 보면 그런 자리에서 판정이 멈춰 안내가 영영 안 나간다.

```python
def _audible_idx(self, direction):
    i = self.index + direction
    while 0 <= i < len(self.path):
        if self._latest(self.path[i]) is not None:
            return i
        i += direction
    return None
```

## 2.7 미해결 — 같은 비콘이 두 번 나오는 경로

추적기는 **비콘 키로 신호를 찾는다.** 경로에 같은 비콘이 두 번 나오면 `history[key]`
가 하나뿐이라 두 칸을 구분할 수단이 없다.

```
경로:  B12 → B11 → B10 → B11 → B24
index:  0     1     2     3     4

index 2 에서:  prev = path[1] = B11
               next = path[3] = B11     ← 같은 키
```

앞뒤가 완전히 같은 값을 보게 되므로:

- 후퇴 조건의 `trend_prev > trend_next` 가 **항상 거짓** → 그 자리에서 이탈 판정 불가
- 사용자가 실제로 되돌아가도 **전진으로 판정**하고 index 3 으로 넘어감

768개 중 117개 경로가 해당한다. 정방향으로 걸으면 결과가 우연히 맞아서 실제 영향은
제한적이지만, 되돌아갈 때는 틀린다.

풀 방법 후보:

1. `to_beacon_sequence` 가 떨어진 중복도 접는다 → 그 구간 안내가 붙을 자리가 사라짐
2. 앞뒤가 같은 키인 자리에서는 이탈 판정을 끄고 시간 기반으로 넘긴다
3. 그대로 두고, 이탈은 시간 기반(표 15·16번)으로 잡는다

## 2.8 튜닝 값

| 값 | 기본 | 뜻 |
| --- | --- | --- |
| `mode` | `confirm` | 판정 방식 |
| `threshold` | 2.5 | 추세 임계(dB, 창 전체 변화량) |
| `min_next` | -85.0 | 다음 비콘 최소 세기 |
| `min_gap` | 0.0 | ①의 신호차 요구(0 = 넘어서기만) |
| `require_trend` | True | 추세를 AND 로 요구 |
| `window_ms` / `segments` | 2000 / 5 | 구간 방식 추세 창 |
| `confirm_delay_ms` | 500 | 무장 후 대기 |
| `confirm_gap` | 5.0 | 확인 시점 요구 신호차(dB) |
| `forward_streak_need` | 2 | 전진 연속 |
| `back_streak_need` | 3 | 후퇴 연속 |

`/monitor` 의 지도 카드와 경로 추적 카드 양쪽에서 바꿀 수 있고, 두 곳이 값을 공유한다.
