## 1. 층이 매 패킷마다 뒤집혔다

### 무엇이 잘못됐나

`_locate()` 는 들어오는 비콘의 major 를 **언제나 즉시** 따라갔다. 그런데 이 함수는
비콘 하나하나마다 불렸고 앱은 스캔될 때마다 한 개씩 보낸다. 그래서 두 층 신호가
번갈아 잡히는 자리 — 계단 앞, 엘리베이터 앞 — 에서는 이렇게 됐다.

```
major 104 →  4층
major 103 →  3층
major 104 →  4층
major 103 →  3층   …
```

뒤집힐 때마다 `located` 가 True 라서, 목적지가 정해지기 전이면 "목적지를 말씀해
주세요" + 목록이 계속 다시 나갔다. 폰은 그때마다 마이크를 새로 열었고,
**사용자가 말을 시작할 수가 없었다.**

반대로 한 번 정하고 잠가버리면 경로 없이 층을 옮겼을 때 서버가 모른다.
3층에 서 있는데 4층 목록을 주고 4층 경로를 만든다.

### 어떻게 고쳤나

함수를 둘로 쪼갰다.

```
_locate_building()   MAC 으로 한 번만. major 는 건물을 안 담는다
_locate_floor()      패킷 하나가 다 처리된 뒤 한 번만 부른다
```

`_locate_floor` 는 두 갈래다.

```
최초    건물이 정해지고 FLOOR_SETTLE_MS 뒤, 가장 센 비콘의 major
이후    후보 major 가 FLOOR_SWITCH_DWELL_MS 동안 혼자 유지되면 전환
```

**"혼자"가 핵심이다.** 지금 층 신호가 한 번이라도 섞여 들어오면 후보를 깬다.

```
엘리베이터 앞에 서 있다   지금 층이 계속 들린다  →  후보가 매번 깨진다  →  안 바뀐다
정말 타고 올라갔다        지금 층이 끊긴다      →  후보가 유지된다     →  바뀐다
```

같은 장치가 두 경우를 다 가른다. 서 있는 것만으로 다음 구간이 시작되던 문제가
여기서 풀린다.

### 최초 확정만 다른 이유

이후 판정에서 "가장 센 것"을 쓰면 안 된다. **칼만 필터는 신호가 끊겨도 값을 잃지
않아서**, 3층에 막 내린 순간에도 20초 전 4층 비콘이 여전히 제일 세다. 그러면 층이
바뀐 것을 영영 못 알아채고 안내가 멈춘다.

반대로 최초 확정에 "유지되는지"를 쓸 수는 없다. 비교할 지금 층이 아직 없다.

### "혼자 유지" 로는 안 됐다 — 세기로 겨룬다

위 규칙을 실측에 걸었더니 **엘리베이터에서 내려도 층이 안 바뀌었다.** 2026-08-26
로그가 그대로 남아 있다(5초 간격).

```
t=0    103-1:-60   104-1:-85          엘리베이터 앞
t=15   103-1:-75                      문 닫힘
t=20   103-1:-77                      차 안. 5초에 비콘 4개
t=25   103-1:-77   104-1:-62          문 열림. 4층
t=30   103-1:-76   104-1:-61
t=35   103-1:-79   104-1:-53
t=40   103-1:-79   104-1:-46          33dB 차이
t=45+  → 그제서야 전환
```

**t=25 에 이미 4층인데 전환은 20초 뒤였다.** 그전 실측에서는 아예 안 바뀌어서,
5층 비콘을 회수하러 옆 계단으로 올라간 순간에야 뒤늦게 발화했다 — 계단이 잘 된
것이 아니라 **계단실에 들어가서야 유령 신호가 끊긴 것**이다.

원인은 하나다. `session.major in seen_majors` 는 **세기를 안 본다.** 그리고 앱은
스캔된 것을 거르지 않고 전부 올린다 — `NavClient` 어디에도 RSSI 하한이 없다.
그래서 슬래브를 뚫고 들어온 -90dB 유령 신호가 -46dB 와 똑같은 한 표를 가졌고,
그 한 표가 매번 3초 시계를 0으로 돌렸다. 깨끗한 3초 창이 우연히 열리기를
기다리는 셈이라, **안 열리면 영영 안 바뀐다.**

그래서 층끼리 세기로 겨룬다.

```
층별 점수 = 그 층의 살아있는 비콘 중 가장 센 값
후보      = 지금 층을 FLOOR_WIN_DB 이상 이기는 층 중 가장 센 것
전환      = 그 상태가 FLOOR_SWITCH_DWELL_MS 동안 이어질 때
```

```
엘리베이터 앞에 서 있다   지금 층이 같은 방에서 세다   →  못 이긴다
내려서 나왔다             새 층이 같은 방, 옛 층은 슬래브 너머  →  이긴다
지금 층이 통째로 끊겼다   겨룰 상대가 없다             →  곧바로 후보가 선다
```

같은 장치가 세 경우를 다 가른다. 위 로그를 그대로 재생하면 **3.5초**에 바뀐다
(`test_multi_floor` 의 "실측 로그 재생").

### 살아있는 비콘 — 이것 없이는 세기 비교가 무의미하다

칼만 필터는 표본이 와야만 갱신된다. **시간이 지난다고 값을 깎지 않는다.**
5분 전에 마지막으로 들은 비콘도 그때 그 -45dB 를 그대로 들고 있다.

```
5층 로비 비콘, 그 앞에 섰을 때 -45 로 굳음
4층에 내려서 -50 을 새로 들음
      → 얼어붙은 -45 가 이김 → 영영 5층
```

그래서 `session.last_seen` 에 비콘별 마지막 수신 시각을 들고, `BEACON_STALE_MS`
지난 것은 **없는 것으로 친다.** 신호는 초당 수십 개씩 오므로 5초 동안 하나도
없으면 정말 안 들리는 것이다.

세기 비교와 늙히기는 **한 세트다.** 하나만 넣으면 둘 다 무의미하다.

### 값

```
FLOOR_SETTLE_MS        1500   층을 정하기 전에 모으는 시간
FLOOR_SWITCH_DWELL_MS  3000   새 층이 계속 이기고 있어야 하는 시간
FLOOR_WIN_DB           6.0    후보가 지금 층을 이겨야 하는 여유
BEACON_STALE_MS        5000   이만큼 안 들리면 없는 것으로 친다
```

**전부 실측으로 정한 값이 아니다.** 다만 `FLOOR_WIN_DB` 는 근거가 있다 —
콘크리트 슬래브 하나면 보통 10~20dB 떨어지므로, 6dB 는 층이 실제로 바뀌면
넉넉히 넘고 잡음(±2dB)으로는 안 넘는다.

### 엉뚱한 층 재계획은 껐다

`REPLAN_ON_WRONG_FLOOR = False`.

기다리던 층이 아닌 곳에 내리면 거기서 다시 계획할 수 있다. 그런데 엘리베이터가
층을 지나칠 때 그 층으로 판정되면, `WRONG_FLOOR_DWELL_MS` 뒤에 **아직 타고 있는
사람에게** 경로가 새로 짜인다. 그 층 비콘은 제대로 안 잡히므로 대개 실패한다.

꺼도 갇히지 않는다. 목표 층 신호가 올 때까지 조용히 기다릴 뿐이고, 잘못 내렸으면
그 층으로 다시 가면 이어진다. 층 판정이 충분히 믿을 만해지면 그때 켠다.

## 2. `_maybe_resume` 이 한 번밖에 안 불렸다 — 갈래 둘이 죽어 있었다

이건 맥에서 온 것이 아니라 **여기서 찾은 것**이다. `2eae9d5` 부터 있었다.

호출부가 이랬다.

```python
if located and session.awaiting_floor is not None:
    out_msgs.extend(_maybe_resume(session))
```

`located` 는 "층이 **방금** 바뀌었다"는 뜻이다. 층을 옮기는 동안 딱 한 번만 True 다.
그런데 `_maybe_resume` 안에는 여러 패킷에 걸쳐 봐야 하는 것이 둘 있다.

```
엉뚱한 층에 내렸나    floor_since 로부터 WRONG_FLOOR_DWELL_MS 를 재야 한다
구간을 못 걸었나      신호가 더 잡히면 다시 시도해야 한다
```

층이 바뀐 그 순간에는 머문 시간이 0 이라 첫째는 **언제나** "아직 지나가는 중"으로
빠져나갔다. 둘째는 되돌린 뒤 다시 불릴 일이 없었다. 둘 다 **한 번도 안 도는
코드**였다.

```python
if session.awaiting_floor is not None:
    out_msgs.extend(_maybe_resume(session))
```

조건이 안 맞으면 `_maybe_resume` 이 곧장 빈 목록을 돌려주므로 비용도 없다.

이걸 고치기 전까지 `WRONG_FLOOR_DWELL_MS = 5000` 은 **아무 데도 안 쓰이는 상수**였다.

## 3. 다음 구간을 못 만들면 되돌린다

층은 바뀌었는데 그 층 비콘이 아직 제대로 안 잡히면 `_start_leg` 이 실패한다.
그때 `_start_leg` 은 `destination` 을 지우고 `routeFailed`(`listenAfter=true`)를
내보낸다.

**첫 구간이라면 맞다.** 사용자가 방금 목적지를 말했고 그게 안 됐으니 다시 물어야 한다.
**여기서는 틀리다.** 사용자는 그냥 엘리베이터에서 내리는 중이고 목적지를 다시 말할
일이 없다. 실제로 이것 때문에 안내가 통째로 처음으로 돌아갔다.

그래서 실패를 삼키고 되돌린다.

```python
msgs = _start_leg(session)
if any(m.get("event") in ("routeFailed", "error") for m in msgs):
    session.leg_index -= 1
    session.awaiting_floor = want
    session.destination = dest      # _start_leg 이 지웠을 수 있다
    return []
```

앱에는 아무것도 안 나간다 — 층을 옮기는 동안 조용한 것이 정상이다. `_start_leg` 의
실패 갈래 셋(`leg is None` · `MapDataError` · 그 밖)은 전부 `session.plan` 을 건드리기
**전에** 빠져나가므로, 이 세 줄이면 상태가 온전히 돌아온다.

§2 를 같이 고쳐야 실제로 다시 시도된다. 하나만 고치면 세션이 `awaiting_floor` 에
갇힌다.

## 4. 목적지 목록은 건물 전체로

```
음성   지금 층을 먼저 보고, 없을 때만 다른 층 (on_destination — 그대로)
목록   건물 전체 (_building_items — 새로)
```

음성을 건물 전체로 열면 "화장실"이 층마다 있어서 매번 되묻게 된다. 반대로 목록을
이 층으로 좁히면 **화면으로 고르는 사용자는 다른 층에 아예 갈 수가 없다** — 음성이
안 되는 자리(시끄러운 곳, STT 실패)에서 갇힌다.

되묻기가 생기지 않는 쪽만 넓히는 것이라 둘이 부딪히지 않는다.

다른 층 것에는 `(4층)` 을 붙인다. 안 붙이면 "화장실"이 다섯 개 나열돼서 화면으로도
소리로도 무엇이 무엇인지 가릴 수가 없다. 지금 층 것은 그대로 둔다 — 대부분이
그것이라 전부 층이 붙으면 읽는 데 방해만 된다.

DB 조회가 실패하면 이 층 목록으로 떨어진다. 목록이 좁아질 뿐 안내는 그대로 돈다.

## 6. 목적지 건너기 제한 — 맥 사본에는 없었다

맥이 받아간 `2eae9d5` 에는 **없다.** `49f615c` 에서 들어갔고 그건
`feature/no-connector` 브랜치에만 있었다. 그래서 맥에서 본 "랜드마크에서 그냥
건널 수 있다"는 정확한 관찰이다.

규칙은 WEB-FE `bdffedb`(`isCrossEdgeUsable`)를 옮긴 것이다.

```
목적지에서 뻗는 건너기 엣지는 그 목적지가 출발지일 때만 쓴다
```

맞은편으로 무조건 넘어갈 수 있는 것이 아니다. 407호 앞에서 복도를 건너는 엣지는
**407호에서 출발할 때만** 쓸 수 있고, 지나가는 길에 지름길로 쓸 수는 없다.

없을 때 실측 4층 757쌍 중 **205쌍**이 관리자웹과 다른 경로로 안내되고 있었다.

### 시간을 어떻게 재나

새 판정은 전부 벽시계를 본다. 테스트에서 1.5초·3초를 실제로 기다릴 이유가 없으므로
**시계를 되감는다.**

```python
session.building_at -= FLOOR_SETTLE_MS        # 층 확정 대기를 건너뛴다
session.floor_cand_at -= FLOOR_SWITCH_DWELL_MS # 유지시간을 채운다
session.floor_since -= WRONG_FLOOR_DWELL_MS    # 그 층에 머물렀다고 친다
```

`feed()` 헬퍼가 첫째만 자동으로 한다. 나머지 둘은 손으로 부른다 — 자동으로 하면
"지나가는 층에서는 안 움직인다"를 잴 수가 없다.
