# 경로 그래프는 누가 만들고 누가 고르는가

건너기(cross)를 두고 값이 두 벌씩 돌아다녀서 정리한 기록.

---

## 두 단계는 주체가 다르다

```
노드·간선 생성    관리자웹    pathNodes.ts       마스크에서 코너를 뽑고 건너기를 만든다
검수·저장         관리자웹    PathNodePage.tsx   점을 옮기고 잘못된 건너기를 지운 뒤 저장
경로 선택         안내 서버   route_engine.py    저장된 그래프에 다익스트라
```

건너기 **최대 폭**은 생성 단계, 건너기 **페널티**는 선택 단계에 걸린다. 둘을 나란히
적어두면 같은 종류의 설정처럼 보이지만 서로 다른 시점에 서로 다른 곳에서 쓰인다.

---

## 무엇이 어긋나 있었나

### 서버가 그래프를 따로 만들고 있었다

저장된 경로노드가 없는 층은 서버가 `path_nodes.py`(= `pathNodes.ts` 를 옮긴 것)를
직접 돌려 그래프를 만들었다. 두 벌의 생성 코드를 똑같이 유지해야 한다는 뜻이고,
실제로 갈라져 있었다.

    건너기 최대 폭     관리자웹 3m (고정)      서버 12m

관리자가 화면에서 검수한 것보다 훨씬 촘촘한 건너기로 안내가 나갈 수 있었다.
`tests/test_path_nodes.py` 의 실측 대조도 `연결 수` 에서 이미 어긋나 있다.

**고침** — `graph()` 는 저장된 경로노드만 읽는다. 없으면 만들어내지 않고 거절한다.

    이 층은 경로노드가 저장되어 있지 않아 안내할 수 없습니다.
    관리자웹의 경로노드 화면에서 그래프를 확인하고 저장해주세요.

사람이 검수하지 않은 그래프로 시각장애인을 안내하는 것보다 안내를 거절하는 편이
낫다. `path_nodes.py` 는 이제 테스트가 저장 상태를 만들 때만 쓴다
(`tests/pathnode_seed.py`).

캐시(`_GRAPH_CACHE`)도 같이 없앴다. 마스크에서 노드를 만들 때는 한 번에 0.8초가
걸려 들고 있어야 했지만, 지금은 저장된 행을 읽어 좌표만 환산한다(1ms 미만).
캐시가 없으니 관리자가 저장한 즉시 반영된다.

### 건너기 페널티를 저장할 자리가 없었다

관리자웹은 이 값을 화면 입력으로 받는다.

```tsx
const [crossPenaltyM, setCrossPenaltyM] = useState(String(DEFAULT_CROSS_PENALTY_M))
```

그런데 저장 요청(`PathNodesData`)에 이 필드가 없어서 서버로 가지 않았다. 서버는
같은 기본값 5.0 을 따로 박아두고 있었고, 관리자가 화면에서 3 으로 바꿔 경로를
검수해도 안내는 5 로 나갔다. 화면을 새로 열면 입력값도 기본값으로 돌아간다.

**고침** — `floor_path_nodes` 에 컬럼을 추가하고 경로노드와 함께 저장한다.

```sql
ALTER TABLE floor_path_nodes ADD COLUMN IF NOT EXISTS cross_penalty_m DOUBLE PRECISION;
ALTER TABLE floor_path_nodes ADD COLUMN IF NOT EXISTS crossing_max_m  DOUBLE PRECISION;
```

`create_all` 은 없는 테이블만 만들고 컬럼은 안 건드리므로 위 SQL 을 직접 돌려야 한다.
기존 행은 NULL 이고, 읽는 쪽에서 기본값 5.0 으로 대체한다.

`crossing_max_m` 은 서버가 계산에 쓰지 않는다. 간선은 이미 만들어져 저장된
상태이기 때문이다. 이 그래프가 어떤 폭으로 만들어졌는지 남겨두려고 같이 보관한다.

### 목적지 건너기 제한이 방향을 안 봤다

건너기는 "여기서 출발해 반대편으로 건너세요"라는 안내다. 그래서 출발하는 쪽이 남의
목적지·연결자 앞이면 쓰지 않는다. 그런데 판정을 간선의 `a` 한쪽만 보고 했다.

```python
if is_cross:
    a_node = graph.node(e.a)
    if a_node is not None and not cross_edge_usable(...):
        continue          # 두 방향이 통째로 사라진다
```

두 가지가 어긋났다.

- `directed` 가 안 붙은 건너기는 역방향(`b→a`)이 무검사로 열렸다. `b` 가 남의
  목적지 앞이어도 거기서 출발하는 안내가 나갔다.
- 반대로 `a` 가 목적지라는 이유만으로 목적지 쪽으로 건너 **들어가는** 방향까지
  같이 사라졌다. 도착지로 들어가는 건너기는 막을 이유가 없다.

**고침** — 방향마다 발을 떼는 쪽 노드로 판정한다.

```python
a_ok = b_ok = True
if is_cross:
    a_ok = cross_edge_usable(getattr(graph.node(e.a), "type", None), e.a, start_id)
    b_ok = cross_edge_usable(getattr(graph.node(e.b), "type", None), e.b, start_id)
if a_ok:
    adj[e.a].append(...)
if not e.directed and b_ok:
    adj[e.b].append(...)
```

같이 `_log_crossings` 를 넣었다. 채택된 건너기를 출발 쪽 노드 종류와 함께 한 줄로
찍는다.

    [경로] 건너기 1회 — N14(corner) → N31 2.4m

"엉뚱한 데서 건넌다" 를 확인할 때 볼 것이 세 가지다 — 어느 간선을 탔는지, 출발 쪽
노드가 무슨 종류인지, 제한에 걸리는 종류인데 통과했다면 그 노드가 출발 노드였는지.

---

## 남은 것

`pathfind.ts` 에도 같은 방향 구멍이 있다. 관리자 화면은 `directed` 가 붙은
건너기만 다루므로 지금 당장 드러나지는 않지만, 서버와 화면이 같은 답을 내야 하므로
같이 고쳐야 한다. WEB-FE 는 손대지 않았다.
