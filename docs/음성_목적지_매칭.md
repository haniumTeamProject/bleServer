## 1. 문제 — 이름이 사람이 말하는 것과 다르다

실제 데이터에 들어 있는 랜드마크 24개는 이렇게 생겼다.

```
401 402 403 404 405(1) 405(2) 406 407 408 409(1) 409(2) 410 411 412 413 414 415
계단1 계단2 계단3      엘베1 엘베2      화1 화2
```

여기서 네 가지 문제가 동시에 생긴다.

**① 접미사가 반대다.** 데이터는 `407` 인데 사용자는 "407호"라고 말한다.

**② 줄임말이라 문자 유사도가 통하지 않는다.**
"화장실"과 `화1` 은 겹치는 글자가 "화" 하나뿐이라 편집거리로는 절대 못 잇는다.
"엘리베이터"와 `엘베` 도 마찬가지다.

**③ 음성인식이 숫자를 한글로 뱉을 수 있다.**
"407"을 "사백칠"로도, "사공칠"로도 읽는다.

**④ 같은 번호가 두 개 있다.** `405(1)/405(2)`, `409(1)/409(2)`, 계단 3개, 화장실 2개.

그래서 **단순 유사도 매칭으로는 안 되고** 정규화 → 별칭 → 유사도 3단이 필요하다.

## 2. 핵심 설계 — 이름을 (접두사, 숫자, 변형)으로 쪼갠다

이 한 가지가 나머지를 전부 풀어준다.

```python
_NAME_RE = re.compile(r"^(?P<prefix>\D*?)(?P<number>\d+)?(?:\((?P<variant>\d+)\))?$")
```

```
"407"     → 접두사 ""     숫자 407  변형 None
"409(1)"  → 접두사 ""     숫자 409  변형 1
"화1"     → 접두사 "화"    숫자 1    변형 None
"계단2"   → 접두사 "계단"   숫자 2    변형 None
```

**접두사가 비어 있으면 그 숫자는 '방 번호'이고, 접두사가 있으면 그 숫자는 '몇 번째'다.**

```python
@property
def is_room(self) -> bool:
    """접두사가 없고 숫자가 있으면 방 번호로 본다."""
    return not self.prefix and self.number is not None
```

이 구분이 왜 결정적이냐면, 두 경우에 **정반대의 규칙**이 필요하기 때문이다.

| | 방 번호 (`407`) | 종류+순번 (`화1`) |
|---|---|---|
| 숫자가 다르면 | **완전히 다른 곳.** 407과 406은 남남 | 같은 종류의 다른 것. 후보로 올려야 함 |
| 숫자를 안 말하면 | 특정할 수 없음 | 종류 전체가 후보 → 되묻기 |
| 매칭 규칙 | 숫자가 **정확히** 같아야 함 | 접두사만 같으면 됨 |

**방 번호를 유사도로 이어주면 위험하다.** 407이라고 했는데 406으로 안내하면
시각장애인 입장에서는 잘못된 문 앞에 서게 된다. 그래서 코드에서 명시적으로 막는다.

```python
if lm.is_room:
    if query.numbers:
        if lm.number in query.numbers:
            ...
            return 1.0
        # 숫자를 말했는데 다르면 다른 방이다. 407과 406은 남남이므로
        # 유사도로 이어주지 않고 확실히 배제한다.
        return 0.1
```

테스트에도 이 규칙을 따로 박아뒀다.

```python
MUST_NOT_MATCH = [
    ("407", "406"), ("407", "408"), ("401", "410"),
    ("403", "413"), ("405", "415"),
]
```

## 3. 1단 — 정규화

```python
_NUM_SUFFIX = re.compile(r"(?<=\d)\s*(호실|호|번방|번|실|방|층)")

def normalize(text: str) -> str:
    s = text.strip().lower()
    s = s.replace("－", "-").replace("（", "(").replace("）", ")")
    s = _NUM_SUFFIX.sub("", s)                        # "407호" → "407"
    s = re.sub(r"[\s.,!?~・·\-_/]+", "", s)            # 공백·문장부호 제거
    changed = True
    while changed and s:                              # 조사·서술어 반복 제거
        changed = False
        for suffix in _TRAILING:
            if s.endswith(suffix) and len(s) > len(suffix):
                s = s[: -len(suffix)]
                changed = True
                break
    return s
```

**`_NUM_SUFFIX` 에 `(?<=\d)` 가 붙은 게 중요하다.** 숫자 바로 뒤에서만 지운다.

```
"407호"   → "407"     ✓
"화장실"   → "화장실"    ✓   ← 그냥 "실"을 지우면 "화장"이 되어 별칭이 깨진다
```

이걸 놓치면 화장실 매칭이 통째로 무너진다. 그래서 테스트에 못 박아뒀다.

```python
NORMALIZE_CASES = [
    ("407호로 가줘", "407"),
    ("화장실", "화장실"),   # "실"을 지우면 별칭이 깨진다 — 숫자 뒤에서만 지워야 함
]
```

조사·서술어는 **반복해서** 벗긴다. "411로 가고 싶어" 는 "가고싶어" 를 떼고
남은 "411로" 에서 "로" 를 또 떼야 "411" 이 된다.

괄호는 일부러 남긴다. `409(1)` 이 랜드마크 이름이기 때문이다.

## 4. 1단 — 한글 수사

```python
def korean_numbers(text: str) -> set[int]:
    results: set[int] = set()
    has_unit = any(u in text for u in _UNIT_WORDS)     # 십 백 천 만

    if has_unit:
        # 자릿수 읽기: "사백칠십오" → 475
        total = current = 0
        for ch in text:
            if ch in _DIGIT_WORDS:
                current = _DIGIT_WORDS[ch]
            elif ch in _UNIT_WORDS:
                total += (current if current else 1) * _UNIT_WORDS[ch]
                current = 0
        total += current
        if total > 0:
            results.add(total)
    else:
        # 한 자씩 읽기: "사공칠" → "407"
        digits, matched = "", 0
        for ch in text:
            if ch in _DIGIT_WORDS:
                digits += str(_DIGIT_WORDS[ch]); matched += 1
            elif ch.isdigit():
                digits += ch; matched += 1
        if len(digits) >= 2:
            results.add(int(digits))
        elif len(digits) == 1 and matched == len(text):
            results.add(int(digits))
    return results
```

**"십·백·천"이 있으면 자릿수 읽기, 없으면 한 자씩 읽기**로 갈린다.
같은 방을 두 가지로 읽을 수 있어서 둘 다 지원해야 한다.

```
"사백칠"  →  4×100 + 7        = 407
"사공칠"  →  4, 0, 7 을 이어서 = 407
```

마지막 조건 `matched == len(text)` 이 방어 장치다.

```python
elif len(digits) == 1 and matched == len(text):
    # 한 글자짜리는 전체가 숫자일 때만 인정한다.
    # "출구"의 "구"를 9로 읽어버리는 것을 막기 위함.
```

"구"가 9라서, 이 조건이 없으면 **"출구"가 9번 방을 찾는 발화로 해석된다.**

## 5. 2단 — 종류 판단 (별칭 표를 없앤 이유)

처음에는 여기에 손으로 적은 별칭 표가 있었다.

```python
ALIAS_GROUPS = [
    ("화",   ("화장실", "변소", "해우소", …)),
    ("엘베", ("엘리베이터", "승강기", …)),
]
```

랜드마크 이름이 `화1`, `엘베1` 처럼 줄임말이라 문자 유사도로는 못 이었기 때문이다.
**그런데 이름을 `화장실 1`, `엘리베이터 1` 로 제대로 붙이자 이 표가 오히려 방해가 됐다.**

```
                별칭 표 ON        별칭 표 OFF
"화장실"        notFound  ✗       화장실 1, 화장실 2  ✓
"엘리베이터"     notFound  ✗       엘리베이터 1, 2     ✓
"화장실 급해요"   notFound  ✗       화장실 1, 화장실 2  ✓
```

표가 "화장실"을 접두사 `화` 로 바꿔버리는데 실제 랜드마크 접두사는 `화장실` 이라
서로 안 맞아서, 멀쩡히 있는 화장실을 밀어냈다.

**그래서 표를 지우고, 종류 판단을 실제 랜드마크 이름과 직접 비교하도록 바꿨다.**

```python
CATEGORY_MATCH = 0.8

if lm.prefix:
    said = query.body or query.norm      # 순서 표현을 뗀 나머지
    ratio = jamo_ratio(said, lm.prefix)
    if ratio >= CATEGORY_MATCH:
        if query.ordinal is not None:
            return 1.0 if lm.number == query.ordinal else 0.15
        return 0.95
    return ratio * 0.5
```

건물이 바뀌어도 코드를 고칠 일이 없다. 대신 "변소", "승강기" 같은 **동의어 지식은
포기한다** — 그건 LLM이 맡는다(9장).

이 결정을 테스트에 못 박아뒀다. 나중에 누가 별칭 표를 다시 넣으려 하면 걸린다.

```python
# 규칙 엔진이 못 잡는 게 **정상**인 것들. 동의어 지식은 LLM이 맡는다.
# 여기에 별칭 표를 다시 넣으면 이름이 바뀐 건물에서 매칭이 깨진다.
NOT_RULES_JOB = ["변소", "승강기", "층계", "화장실 급해요", "밥 먹는 데"]
```

## 6. 3단 — 자모 유사도

위에서 못 잡은 것만 여기로 온다.

```python
_CHO  = "ㄱㄲㄴㄷㄸㄹㅁㅂㅃㅅㅆㅇㅈㅉㅊㅋㅌㅍㅎ"
_JUNG = "ㅏㅐㅑㅒㅓㅔㅕㅖㅗㅘㅙㅚㅛㅜㅝㅞㅟㅠㅡㅢㅣ"
_JONG = " ㄱㄲㄳㄴㄵㄶㄷㄹㄺㄻㄼㄽㄾㄿㅀㅁㅂㅄㅅㅆㅇㅈㅊㅋㅌㅍㅎ"

def to_jamo(text: str) -> str:
    """한글을 자모 단위로 편다. "화장실" → "ㅎㅘㅈㅏㅇㅅㅣㄹ" """
    out = []
    for ch in text:
        code = ord(ch)
        if 0xAC00 <= code <= 0xD7A3:
            i = code - 0xAC00
            out.append(_CHO[i // 588])
            out.append(_JUNG[(i % 588) // 28])
            jong = _JONG[i % 28]
            if jong != " ":
                out.append(jong)
        else:
            out.append(ch)
    return "".join(out)
```

**음절이 아니라 자모로 비교하는 이유**: 음성인식은 받침이나 모음 하나를 자주 틀린다.
음절 단위로 보면 한 글자가 통째로 다른 것이 되지만, 자모로 펴면 자모 하나 차이가 된다.

```
"화장실" vs "화장싴"
  음절 단위 → 3글자 중 1글자 다름 = 67% 유사
  자모 단위 → 8자모 중 1자모 다름 = 88% 유사   ← 이쪽이 실제 오류에 맞다
```

## 7. 점수 계산

```python
def score(query: Query, lm: Landmark) -> float:
    if query.norm == normalize(lm.name):
        return 1.0                                  # 이름을 그대로 말함

    # ---- 종류가 있는 랜드마크 (화1, 계단2, 엘베1) ----
    if query.prefix and lm.prefix:
        if query.prefix == lm.prefix:
            if query.ordinal is not None:
                return 1.0 if lm.number == query.ordinal else 0.15
            return 0.95        # 종류만 말함 → 여럿이면 되묻게 된다
        return jamo_ratio(query.body, normalize(lm.name)) * 0.5

    # ---- 방 번호 (407, 409(1)) ----
    if lm.is_room:
        if query.numbers:
            if lm.number in query.numbers:
                if query.variant is not None:
                    return 1.0 if lm.variant == query.variant else 0.15
                return 1.0
            return 0.1                              # 다른 방 — 확실히 배제
        return jamo_ratio(query.body, normalize(lm.name)) * 0.4

    return jamo_ratio(query.norm, normalize(lm.name)) * 0.9
```

**"종류만 말했을 때 0.95를 주는 것"이 되묻기의 방아쇠다.**
화1과 화2가 똑같이 0.95를 받으므로 동점이 되고, 동점이면 되묻는다.

## 8. 결정 — 확정 / 되묻기 / 실패

```python
MIN_ACCEPT = 0.55   # 이 아래면 "못 알아들었다"
TIE_DELTA  = 0.08   # 1위와 이만큼 이내면 "구분이 안 된다"
```

```python
ranked = sorted(((score(query, lm), lm) for lm in landmarks),
                key=lambda p: (-p[0], p[1].name))
top_score, top_lm = ranked[0]

if top_score < MIN_ACCEPT:
    return MatchResult(status="notFound", ...)

tied = [(s, lm) for s, lm in ranked if top_score - s <= TIE_DELTA]
if len(tied) > 1:
    return MatchResult(status="ambiguous", candidates=[lm for _, lm in tied], ...)

return MatchResult(status="resolved", landmark=top_lm, ...)
```

**`MIN_ACCEPT` 를 낮게 잡지 않은 이유**: 시각장애인이 쓰는 도구라
엉뚱한 곳으로 안내하는 것보다 "다시 말씀해 주세요"가 훨씬 낫다.
확실하지 않으면 거절하는 쪽으로 기울여 뒀다.

## 9. 되묻기

후보가 여럿이면 **이름을 순서대로 읽어준다.**

```
사용자: "화장실"
서버:   "화장실 1번, 화장실 2번 중에서 말씀해 주세요."
사용자: "두 번째"          (또는 "화장실 2번")
서버:   "화장실로 안내합니다."   → 화장실 2 확정
```

### 왜 "몇 번째"로 뭉뚱그리지 않는가

처음에는 이렇게 읽었다.

```
"화장실이 2곳 있습니다. 첫 번째, 두 번째 중에 말씀해 주세요."
```

후보가 **한 종류일 때만** 맞는 방식이다. 종류가 섞이면 이렇게 깨진다.

```
후보    ['계단 1', '엘리베이터 1', '계단 2', '계단 3']
안내    "계단이 4곳 있습니다. 첫 번째, 두 번째, 세 번째, 네 번째 중에…"
```

첫 후보의 종류만 보고 전체를 묶어버려서 **엘리베이터가 계단이 됐다.**
사용자가 "두 번째"라고 답하면 계단인 줄 알고 엘리베이터로 간다.
화면을 볼 수 없는 사용자에게는 이 오류를 알아챌 방법이 없다.

지금은 후보를 하나씩 읽는다.

```python
def _spoken_item(lm: Landmark) -> str:
    """후보 하나를 읽는 말. 방 번호와 종류+순번의 읽는 법이 다르다."""
    if lm.is_room:
        return f"{lm.number}호 {lm.variant}번" if lm.variant is not None else f"{lm.number}호"
    if lm.prefix and lm.number is not None:
        return f"{lm.prefix} {lm.number}번"
    return lm.name


def ambiguous_speech(candidates: list[Landmark]) -> str:
    items = [_spoken_item(c) for c in candidates]
    if len(items) == 1:
        return f"{items[0]}(으)로 안내할까요?"
    return ", ".join(items) + " 중에서 말씀해 주세요."
```

```
계단 1번, 엘리베이터 1번, 계단 2번, 계단 3번 중에서 말씀해 주세요.
409호 1번, 409호 2번 중에서 말씀해 주세요.
```

읽는 시간은 길어진다. 하지만 사용자가 **무엇 중에서 고르는지 알 수 있다.**
"두 번째"는 여전히 받으므로, 목록이 길면 순서로 답하면 된다.

### 대답 해석도 모델이 한다

```python
def choose(text: str, candidates: list[Landmark]) -> MatchResult:   # llm_matcher.py
```

후보 목록과 대답을 그대로 주고 어느 것인지 고르게 한다.

```

```

프롬프트에 순서 표현 사전이 없다. `둘째`·`두번째`·`3번째` 어느 것도 들어
있지 않다. 모델이 원래 아는 것으로 푼다.

출력은 후보 id 안으로 묶여 있고 후보가 몇 개뿐이라, 엉뚱한 곳으로 갈 수 없다.
답이 안 오거나 형식이 깨지면 규칙 엔진이 받는다(`source=llm→rule(사유)`).

### 이름으로 답하면 순서보다 먼저 본다

이름을 읽어주게 되면서 **따라 말하는 게 가장 흔한 대답**이 됐다.
그런데 이름 안의 숫자가 순서로 읽히는 문제가 있었다.

```
후보    ['계단 1', '엘리베이터 1', '계단 2', '계단 3']

"엘리베이터 1번"  → 계단 1     ← 이름 속 1을 순서로 읽음
"계단 2번"       → 엘리베이터 1
"계단 3"        → 계단 2
```

읽어준 대로 답했는데 전부 틀렸다. 규칙 엔진(폴백)의 순서를 뒤집어 고쳤다.

```python
CHOOSE_NAME_MATCH = 0.85

def choose(text: str, candidates: list[Landmark]) -> MatchResult:   # landmark_matcher.py
    norm = normalize(text)

    # 1) 이름으로 고른 경우 — 순서 해석보다 먼저
    best, best_score = None, 0.0
    for c in candidates:
        r = max(partial_ratio(norm, normalize(c.name)),
                partial_ratio(norm, normalize(_spoken_item(c))))   # 읽어준 말 그대로도 본다
        if r > best_score:
            best, best_score = c, r
    if best is not None and best_score >= CHOOSE_NAME_MATCH:
        return MatchResult(status="resolved", landmark=best, ...)

    # 2) 순서 표현으로 고른 경우 ("두 번째")
    ordinal, _rest = extract_ordinal(norm, require_rest=False)

    # 3) 숫자로만 말한 경우 ("2", "3번", "3번째")
    #    다른 말이 섞여 있으면 이름의 일부일 수 있으므로,
    #    발화가 숫자와 순서 접미사뿐일 때만 순서로 본다.
    if ordinal is None:
        m = re.fullmatch(r"(\d{1,2})(째|번|번째)?", norm)
        if m:
            ordinal = int(m.group(1))

    if ordinal is not None and 1 <= ordinal <= len(candidates):
        return MatchResult(status="resolved", landmark=candidates[ordinal - 1], ...)

    return MatchResult(status="ambiguous", candidates=candidates, ...)   # 다시 묻기
```

`_spoken_item` 과도 비교하는 게 핵심이다. 이름은 `계단 1` 인데 읽어준 말은
`계단 1번` 이라, 사용자가 들은 대로 따라 말하면 이름과 정확히 같지 않다.

3)의 `re.fullmatch` 는 발화 전체가 숫자여야 한다는 조건이다. 정규화가 숫자 뒤
`번`을 지우므로 `"3번째"` 는 `"3째"` 로 들어온다 — 그래서 접미사에 `째` 가 있다.

받는 대답 정리:

| 대답 | 처리 |
|---|---|
| "엘리베이터 1번", "계단 2번" | 이름 대조 (읽어준 말 그대로) |
| "첫 번째", "둘째", "가운데 거" | 모델이 해석 (폴백은 사전 5개) |
| "3번째", "2" | 숫자만일 때 순서로 |
| "409(2)" | 후보 안에서 이름 대조 |
| "몰라" | 다시 묻는다 |

### `require_rest` — 실제로 났던 버그

```python
def extract_ordinal(text: str, require_rest: bool = True) -> tuple[int | None, str]:
    """require_rest=True 면 순서 표현을 뗀 뒤에 뭔가 남아야만 인정한다."""
```

처음 발화와 되묻기 답변은 요구 조건이 정반대다.

```
처음 발화 "두 번째 화장실"  → 순서를 뗀 뒤 "화장실"이 남아야 순서로 인정
되묻기 답 "두 번째"        → 뗀 뒤 아무것도 안 남는 게 정상
```

같은 함수를 두 곳에서 쓰면서 이 차이를 안 두었더니, **되묻기의 가장 흔한 답인
"두 번째"가 전부 실패했다.** 테스트로 잡았다.

## 9-2. LLM 매칭 (`llm_matcher.py`) ★

규칙 엔진으로는 동의어와 문장형 발화를 감당할 수 없어서, **실제 서비스 경로는 LLM**이다.

```bash
ollama pull exaone3.5:7.8b     # LG EXAONE — 한국어 특화
ollama serve
```

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| `LLM_PROVIDER` | `ollama` | `ollama` / `openai` / `off` |
| `LLM_MODEL` | `exaone3.5:7.8b` | `qwen3:8b`, `gemma3` 등으로 교체 가능 |
| `LLM_BASE_URL` | `http://localhost:11434` | |
| `LLM_TIMEOUT` | `6` | 초 |
| `LLM_VERIFY_NUMBER` | `1` | 번호 검증 끄려면 `0` |

의존성은 추가하지 않았다. `urllib` 만 쓴다.

### 출력을 목록 안으로 제약한다

LLM이 자유 텍스트를 내면 없는 장소를 지어낸다. 그래서 **id 목록을 주고 그중에서만
고르게** 하고, 돌아온 id가 목록에 없으면 버린다. 프롬프트로 부탁하는 게 아니라
구조로 막는다.

```python
known = {lm.id for lm in landmarks}
for i in ids:
    if i in known: clean.append(i)
    else: dropped.append(i)

if not clean and dropped:
    # 낸 게 전부 지어낸 것이었다. 이건 "그런 곳이 없다"는 답이 아니라
    # 응답을 통째로 못 믿는다는 뜻이므로 규칙 엔진으로 넘긴다.
    # (빈 배열 [] 을 낸 것과 반드시 구분해야 한다)
    return None
```

마지막 구분이 실제로 났던 버그다. 처음엔 둘 다 빈 목록으로 처리해서, 환각만 낸
응답이 "그런 곳 없습니다"로 사용자에게 나갔다.

### 번호를 검증한다

```python
def _number_conflict(text, picked) -> bool:
    """발화에 방 번호가 뚜렷한데 결과가 그 번호와 다르면 True.

    사용자가 "407"이라고 분명히 말했는데 406이 나오는 상황을 막는다.
    LLM 판정을 못 믿어서가 아니라, 틀렸을 때의 대가가 커서 두는 안전장치다.
    """
```

방 번호는 규칙으로 100% 보장할 수 있고, 틀리면 시각장애인이 **잘못된 문 앞에 선다.**
LLM이 407 대신 406을 내면 그 답을 버리고 규칙 결과를 쓴다.

### 없어도 돌아간다

```
모델 서버 죽음      → 규칙 엔진
JSON 파싱 실패      → 규칙 엔진
전부 환각           → 규칙 엔진
번호 불일치         → 규칙 엔진
```

연속 실패하면 30초간 호출을 건너뛴다(`_FAIL_COOLDOWN_S`). 매 발화마다 타임아웃을
기다리면 안내가 통째로 느려지기 때문이다.

### 캐시

목적지 종류가 몇십 개뿐이라 금방 대부분이 캐시에 들어가고, 그때부터 지연이 사라진다.

```
같은 말 3번 → 모델 호출 1번
```

### 되묻기도 LLM이 해석한다

```python
def choose(text: str, candidates: list[Landmark]) -> MatchResult:
    """되물은 뒤의 대답도 모델이 해석한다.

    순서 표현("두 번째", "3번째")을 코드의 사전으로 처리하면 사전에 없는 말투에서
    깨진다. 후보 목록과 대답을 그대로 주고 모델이 고르게 한다.

    후보가 이미 좁혀져 있어 선택지가 몇 개뿐이므로, 출력 검증만 하면
    엉뚱한 곳으로 갈 위험이 없다.
    """
```

처음에는 "순서 표현은 규칙으로 100% 처리되니 부를 필요 없다"고 두었다.
100%인 건 **사전에 적어둔 다섯 개**뿐이고, 사전에 없는 말투는 전부 실패한다.

호출이 한 번 더 늘지만 후보가 몇 개뿐이라 프롬프트가 짧고, 같은 대답은 캐시된다.

### 테스트

`tests/test_llm_matcher.py` 는 **모델 없이** 돈다. 모델 호출부를 가짜로 바꿔서

## 10. 조사 처리

TTS가 읽을 문장이라 조사가 어색하면 바로 티가 난다.

```python
def _josa_iga(word: str) -> str:
    """"화장실이", "엘리베이터가" — 받침에 맞는 조사를 고른다."""
    return "이" if _has_jongseong(word) else "가"

def _josa_ro(word: str) -> str:
    """"407호로", "계단으로" — 받침이 있으면 '으로', 단 ㄹ 받침은 '로'."""
    jong = (ord(word[-1]) - 0xAC00) % 28
    return "로" if jong in (0, 8) else "으로"     # 8 = ㄹ
```

`ㄹ` 받침만 예외인 게 포인트다. "화장실**로**"(O) / "화장실**으로**"(X).

숫자로 끝나는 경우는 읽는 소리로 판단한다.

```python
if ch.isdigit():
    # 0 영, 1 일, 3 삼, 6 육, 7 칠, 8 팔 은 받침 있음
    return ch in "0136780"
```

결과:

```
화장실 1번, 화장실 2번…      엘리베이터 1번, 2번…        계단 1번, 2번, 3번…
407호로 안내합니다           계단으로 안내합니다            화장실로 안내합니다
```

## 10-2. 안드로이드 쪽 (앱) ★

| 파일 | 역할 |
|---|---|
| `speech/VoiceInput.java` | **신규** — 음성 인식(STT) 래퍼 |
| `speech/SpeechGuide.java` | 수정 — 다 읽은 뒤 콜백(`speak(text, done)`) 추가 |
| `ble/BleScanner.java` | 수정 — `requestDestination()` / `chooseDestination()` / `DestinationListener` |
| `MainActivity.java` | 수정 — 마이크 버튼과 전체 흐름 |
| `AndroidManifest.xml` | 수정 — `RECORD_AUDIO`, `<queries>` |
| `activity_main.xml`, `strings.xml` | 수정 — 버튼·상태줄 |

**폰은 판단하지 않는다.** 받아적은 문자열을 그대로 올려보내고, 돌아온 `speech` 를 읽어줄
뿐이다. 그래서 별칭이나 판정 기준을 고쳐도 앱을 다시 빌드하지 않아도 된다.

### 전체 흐름

```
[마이크 버튼] → VoiceInput.listen()
      ↓ onHeard("화장실")
BleScanner.requestDestination("화장실")
      ↓ {"type":"destination","event":"resolve","text":"화장실"}
   [서버 — LLM 해석]
      ↓ {"event":"ambiguous","speech":"화장실 1번, 화장실 2번 중에서…","candidates":[…]}
MainActivity.onDestinationMessage()
      ↓ SpeechGuide.speak(speech, ▶ 다 읽은 뒤 voiceInput::listen)
[마이크 자동 재개] → onHeard("두 번째")
BleScanner.chooseDestination("두 번째")
      ↓ {"event":"choose","text":"두 번째"}
   [서버]
      ↓ {"event":"resolved","landmark":{"name":"화장실 2",…}}
      ↓ SpeechGuide.speak("화장실로 안내합니다.")
```

### 함정 세 개

**① TTS와 STT가 겹치면 안 된다.**

되묻기 안내를 읽는 도중에 마이크를 켜면 **그 소리를 그대로 받아적는다.**
그래서 `SpeechGuide` 에 "다 읽은 뒤 실행"을 붙였다.

```java
// 콜백은 바인더 스레드에서 오므로 메인으로 넘긴다.
tts.setOnUtteranceProgressListener(new UtteranceProgressListener() {
    @Override public void onDone(String utteranceId) { fireDone(); }
    @Override public void onError(String utteranceId) {
        // 읽기에 실패해도 다음 단계는 진행시켜야 흐름이 멈추지 않는다
        fireDone();
    }
});
```

읽기가 **실패했을 때도** `fireDone()` 을 부르는 게 중요하다. 안 그러면 마이크가 영영
안 켜져서 되묻기에서 흐름이 멈춘다. 음성 안내를 꺼둔 사용자도 마찬가지라,
`speak()` 는 읽을 게 없어도 `done` 을 바로 실행한다.

```java
if (text == null || text.trim().isEmpty() || !enabled) {
    if (done != null) mainHandler.post(done);
    return;
}
```

**② Android 11부터 `<queries>` 가 없으면 음성 인식이 안 보인다.**

```xml
<!--
  Android 11(API 30)부터는 다른 앱이 보이지 않는 것이 기본이라,
  이 선언이 없으면 음성 인식기가 깔려 있어도
  SpeechRecognizer.isRecognitionAvailable()이 false를 돌려준다.
  원인을 찾기 어려운 실패라 반드시 있어야 한다.
-->
<queries>
    <intent><action android:name="android.speech.RecognitionService"/></intent>
</queries>
```

깔려 있는데도 "이 기기에서 음성 인식을 쓸 수 없습니다"가 뜨면 십중팔구 이것이다.

**③ `SpeechRecognizer` 는 메인 스레드 전용이다.**

서버 응답은 웹소켓 백그라운드 스레드로 오는데, 거기서 바로 `listen()` 을 부르면 죽는다.
`VoiceInput.listen()` 이 알아서 메인으로 넘기고, `MainActivity` 도
`runOnUiThread` 로 받는다.

```java
bleScanner.setDestinationListener(msg -> runOnUiThread(() -> onDestinationMessage(msg)));
```

### 무한 반복 막기

못 알아들으면 자동으로 한 번 더 듣는데, 여기에 상한이 없으면 시끄러운 곳에서
마이크가 영원히 켜져 있게 된다.

```java
// 못 알아들었을 때 자동으로 다시 듣는 횟수. 무한 반복을 막는다 —
// 주변이 시끄러우면 계속 실패하는데, 그때 마이크가 영원히 켜져 있으면 안 된다.
private static final int MAX_AUTO_RETRY = 1;
```

되묻기(`ambiguous`)는 사용자가 답할 차례가 분명하므로 상한을 걸지 않고,
`notFound` 와 인식 실패에만 건다. 권한·기기 문제는 다시 해도 결과가 같으므로
아예 재시도하지 않는다.

```java
boolean retry = VoiceInput.isRetryable(message) && autoRetryCount < MAX_AUTO_RETRY;
```

### 오류를 사람 말로 바꾼다

시각장애인이 쓰는 도구라 "오류 7" 같은 건 아무 도움이 안 된다.

```java
case ERROR_NO_MATCH, ERROR_SPEECH_TIMEOUT → "잘 못 들었습니다. 다시 말씀해 주세요."
case ERROR_INSUFFICIENT_PERMISSIONS       → "마이크 권한이 필요합니다."
case ERROR_NETWORK, ERROR_NETWORK_TIMEOUT → "네트워크에 연결되지 않아 음성 인식을 할 수 없습니다."
case ERROR_RECOGNIZER_BUSY                → "음성 인식이 아직 준비되지 않았습니다…"
```

이 문장들은 화면에 표시할 뿐 아니라 **TTS로도 읽어준다.**

### 그 밖

- **마이크 권한을 허용하면 바로 이어서 듣는다.** 버튼을 한 번 더 눌러야 한다면
  화면을 못 보는 사람에게 불친절하다.
- **화면을 벗어나면(`onStop`) 마이크를 끈다.** 켜둔 채로 두면 배터리도 먹고,
  다른 화면에서 한 말이 목적지로 들어간다.
- **버튼을 크게 잡았다(64dp).** 손가락으로 더듬어 찾을 수 있어야 한다.
- 듣는 중에 버튼을 다시 누르면 취소된다.

## 10-3. 파이프라인 — 해석이 위치 판정을 막지 않게 ★

폰이 말한 한마디는 이 경로를 지난다.

```
폰 STT ──► WebSocket ──► 서버 ──► Ollama ──► 응답 ──► 폰 TTS ──► 마이크 재개
```

여기서 **Ollama 가 답하는 데 1~3초 걸린다**는 사실이 서버 구조를 결정한다.
목적지는 출발할 때 한 번만 정하므로 사용자가 몇 초 기다리는 건 괜찮다.
문제는 기다리는 동안 서버가 무엇을 못 하느냐다.

### 왜 스레드로 빼는 것만으론 부족했나

처음엔 이렇게 고쳤다. LLM 호출이 동기 함수니까 스레드로 넘긴 것이다.

```python
if _is_slow_message(raw):
    payload, guides = await asyncio.to_thread(_process_message, raw, session)
```

`await` 이 붙었으니 이벤트 루프는 다른 연결을 처리하러 간다. 맞다.
**그런데 이 연결의 읽기 루프는 그 자리에 서 있다.** 2.5초 동안
`receive_text()` 를 안 부른다.

RSSI 를 보내는 것도 같은 연결이다. 그동안 폰이 올려보낸 25개가 소켓 버퍼에
쌓였다가, 해석이 끝나는 순간 한꺼번에 들어온다. 판정기는 그걸 "거의 같은
시각에 도착한 25개"로 보게 되어 2.5초 구간 창이 한 점으로 뭉갠다.

측정하니 그대로 나왔다.

```
── RSSI 를 흘리면서 목적지 해석 ──
  ✓ 목적지 응답              확정 계단1  (2.51초)
  ✗ 중계가 끊긴 최대 구간       2.60초        ← 해석 시간만큼 그대로 멈췄다
```

### 고친 방법 — 읽기 루프에서 떼어낸다

```python
if _is_slow_message(raw):
    task = asyncio.create_task(_handle_destination(websocket, raw, session, lock))
    tasks.add(task)
    task.add_done_callback(tasks.discard)
    continue                      # ← 곧장 다음 메시지를 읽으러 간다

# RSSI·측정 메시지는 빠르고 순서가 중요하므로 루프에서 그대로 처리한다
payload, guides = _process_message(raw, session)
```

```python
async def _handle_destination(websocket, raw, session, lock):
    """목적지 해석을 읽기 루프 밖에서 처리한다."""
    async with lock:                                   # 연결당 한 번에 하나
        _payload, guides = await asyncio.to_thread(_process_message, raw, session)
    for guide in guides:
        await _send(websocket, json.dumps(guide, ensure_ascii=False))
```

`lock` 이 필요한 이유: 해석이 백그라운드로 도는 사이에 다음 요청이 들어오면
되묻기 상태가 엉킨다. 연결 안에서는 순서를 지키되, 읽기는 막지 않는다.

같은 측정을 다시 하면:

```
  ✓ 목적지 응답              확정 계단1  (2.51초)
  ✓ 중계가 끊긴 최대 구간       0.10초        ← RSSI 송신 간격 그 자체
```

해석에 2.5초가 걸려도 중계는 한 박자도 안 빠진다.

### `_is_slow_message` — 판별을 싸게

```python
def _is_slow_message(raw: str) -> bool:
    """LLM 호출로 오래 걸릴 수 있는 메시지인지 싸게 판별한다."""
    if _DESTINATION_TYPE not in raw:
        return False                      # RSSI 는 여기서 끝 — 파싱 안 함
    try:
        data = json.loads(raw)
    except json.JSONDecodeError:
        return False
    return isinstance(data, dict) and data.get("type") == _DESTINATION_TYPE
```

RSSI 는 초당 열 번씩 들어온다. 여기서 매번 json 을 두 번 파싱하면 그게 더
손해라, 문자열 검사로 먼저 걸러낸다.

### 되묻기 상태는 연결마다

```python
_PENDING_KEY = "pending"
_PENDING_AT_KEY = "pending_at"
_PENDING_TTL_MS = 120_000
```

전에는 모듈 전역 하나였다. `_filters`·`_tracker` 는 실측 도구 수준의 한계로
전역이지만 되묻기는 성격이 다르다. 폰 A 에게 "계단 1번, 2번, 3번 중에서"
물어놓은 상태에서 폰 B 가 "두 번째"라고 하면, 전역이면 **B 가 A 의 후보를
집어간다.**

이제 연결별 `session` dict 에 담고, `_process_message(raw, session)` 이 받는다.
`_take_pending()` 이 꺼낼 때 나이를 본다 — 2분 넘게 답이 없으면 버리고 새
요청으로 취급한다. 되묻고 그냥 둔 채 한참 뒤에 다른 말을 하면 그건
되묻기 답변이 아니기 때문이다.

### 목적지 응답은 물어본 폰에게만

```python
for guide in guides:
    await _send(websocket, json.dumps(guide, ensure_ascii=False))   # 브로드캐스트 아님
```

다른 안내(`guide`)는 전체에 뿌리는 게 맞다. 목적지 응답은 다르다.

폰 두 대로 재보고 알았다. 세션은 분리했는데도 이렇게 나왔다.

```
폰A '계단' → ['계단1', '계단2', '계단3']
폰B '엘베' → ['계단1', '계단2', '계단3']     ← A 의 응답을 B 가 받았다
```

전체로 뿌리니까 B 가 A 의 후보 목록을 자기 질문의 답인 줄 알고 받았다.
안내 음성도 마찬가지다 — 옆 사람 목적지가 내 이어폰에서 들린다.
모니터 페이지는 `destination` 을 안 쓰므로 잃는 것도 없다.

고친 뒤:

```
폰A '계단' → ['계단1', '계단2', '계단3']
폰B '엘베' → ['엘베1', '엘베2']
폰B '엘베2' 선택 → 엘베2
폰A '계단2' 선택 → 계단2      ✓ 두 폰의 되묻기가 안 섞인다
```

### 판정 시간축은 손대지 않았다

`_tracker.feed(key, filtered_rssi)` 는 여전히 **서버 도착 시각**을 쓴다.
메시지 안에 폰이 찍은 `timestamp` 가 들어 있어서 그걸 넘기면 네트워크
지터까지 같이 해결되지만, 판정 로직의 시간축을 바꾸는 일이라 이번에는
그대로 뒀다. 위의 백그라운드 처리로 몰려 들어오는 원인 자체가 없어졌으므로
지금 당장 문제가 되지는 않는다.

남은 위험은 순수한 네트워크 지연이다. Wi-Fi 가 끊겼다 붙으면 같은 현상이
생길 수 있다.

## 11. 메시지 프로토콜

`app/ws/handler.py` 의 `_process_destination()`.

### 폰 → 서버

```json
{ "type":"destination", "event":"resolve", "text":"화장실", "requestId":"r1" }
{ "type":"destination", "event":"choose",  "text":"두 번째", "requestId":"r1" }
{ "type":"destination", "event":"cancel" }
{ "type":"destination", "event":"list" }
```

**폰은 STT 결과 문자열만 보낸다.** 매칭은 전부 서버가 한다.
별칭 사전이나 임계값을 고쳐도 앱을 다시 빌드할 필요가 없다.

### 서버 → 전체(폰 포함)

```json
{ "type":"destination", "event":"resolved", "requestId":"r1", "heard":"화장실",
  "landmark":{"id":"L13","name":"화2","x":1286,"y":1327},
  "speech":"화장실로 안내합니다.", "timestamp":1754… }

{ "type":"destination", "event":"ambiguous", "requestId":"r1", "heard":"화장실",
  "candidates":[{"id":"L12","name":"화1",…},{"id":"L13","name":"화2",…}],
  "speech":"화장실 1번, 화장실 2번 중에서 말씀해 주세요." }

{ "type":"destination", "event":"notFound", "requestId":"r1", "heard":"옥상",
  "suggestions":[…], "speech":"목적지를 알아듣지 못했습니다. 다시 말씀해 주세요." }
```

**응답은 중계용이 아니라 안내용(`guides`)으로 돌려준다.** 요청을 보낸 폰이 바로
그 응답을 들어야 할 대상이라, "보낸 쪽 제외" 브로드캐스트를 타면 정작 폰이 못 받는다.
경로 안내(`guide`) 메시지와 같은 이유다.

```python
    path = _map_tool_dir() / "static" / "mappin_project.json"

    if _landmarks and _landmarks_mtime == mtime:

```

파일이 13MB라 매번 파싱하면 느리다. **수정 시각으로 캐시**해서, 지도 도구에서
랜드마크를 고치고 저장하면 서버 재시작 없이 반영된다.

## 13. 아직 안 한 것

- **목적지가 정해진 뒤 경로를 짜는 부분.** 지금은 랜드마크를 특정하는 데까지만 한다.
  경로 계산은 `map-tool/이동규칙_로직정리.md` 쪽 로직과 이어야 한다.
- **실제 모델로 지연 재기.** `--live` 로 재보고, 너무 느리면 더 작은 모델
  (`gemma3:4b`, `qwen3:4b`)로 바꾸거나 캐시를 미리 채워두는 방법이 있다.
- **랜드마크 이름 정리.** 프로젝트 파일에 아직 `화1`, `엘베1` 이 남아 있다.
  `화장실 1`, `엘리베이터 1` 로 바꾸면 규칙 엔진 폴백의 품질이 올라간다.
- **실기기 확인.** 샌드박스에 Gradle이 없어서 컴파일 검증을 못 했다. 리소스 참조·
  메서드 존재·괄호 균형은 정적으로 대조했고, 앱이 만드는 JSON을 서버에 그대로 먹여
  왕복은 확인했다. 실제 빌드와 마이크 동작은 기기에서 봐야 한다.
- **동시 사용자.** `_pending_candidates` 가 전역 하나라 두 사람을 동시에 상대하지
  못한다. `_tracker`·`_filters` 와 같은 한계다.
- **현재 위치 기반 정렬.** 되묻기 순서를 "가까운 것부터"로 바꾸면 첫 번째 선택률이
  올라갈 것이다. 지금은 프로젝트 파일에 적힌 순서 그대로다.
