## 경로 진행 추적 (위치 추정) — `/monitor` 페이지

위치: `app/ws/handler.py`의 `_MONITOR_HTML` 안 `<script>`, "경로 진행 추적" 섹션.

### 전제

경로탐색 알고리즘(Dijkstra 등)이 이미 비콘 순서 `[b0, b1, ..., bn]`을 확정해줌. `currentIndex`는 지금 사용자가 있다고 판단하는 경로상 위치고, prev/current/next는 이 순서에서 -1/0/+1 — 즉 next는 방향을 추측하는 게 아니라 경로 목록에서 그냥 다음 칸.

### 추세(trend) 계산

```js
// 추세 = 최근 2개 평균 - 가장 오래된 2개 평균. 양수=신호가 강해짐(접근중), 음수=약해짐(멀어짐)
function trendOf(key) {
  const hist = historyByKey[key];
  if (!hist || hist.length < 4) return null;
  const n = hist.length;
  const recentAvg = (hist[n - 1].filtered + hist[n - 2].filtered) / 2;
  const oldAvg = (hist[0].filtered + hist[1].filtered) / 2;
  return recentAvg - oldAvg;
}
```

각 비콘의 필터링된(칼만 필터 통과한) RSSI 값을 최근 40개까지 `historyByKey`에 버퍼로 쌓아두고, 그 안에서 최근 2개 평균과 가장 오래된 2개 평균의 차이로 방향을 봄. 단순 부등호(지금 값이 이전 값보다 큰가)로는 노이즈에 바로 흔들려서, 구간 평균 차이로 완만하게 봄.

### 시작 노드 판정

```js
// 경로상 비콘들 중 지금 신호가 가장 센(필터값이 0에 가장 가까운) 걸 시작 노드로
let bestIdx = 0, bestVal = -Infinity;
pathTerms.forEach((term, idx) => {
  const key = findKeyForTerm(term);
  const hist = key ? historyByKey[key] : null;
  if (hist && hist.length > 0) {
    const latest = hist[hist.length - 1].filtered;
    if (latest > bestVal) { bestVal = latest; bestIdx = idx; }
  }
});
currentIndex = bestIdx;
```

앱 실행 시 신호가 가장 강한 노드를 시작 노드로 삼는다는 규칙 그대로 구현. "시작" 버튼 누른 시점의 스냅샷으로 한 번만 판정함.

### 전진 / 후퇴 / 유지 판정

```js
// 전진: next 추세가 +임계값 이상 && current 추세가 -임계값 이하 && next 신호가 최소 기준을 넘었을 때만 인정
if (trendNext !== null && trendCur !== null && trendNext > thresh && trendCur < -thresh
    && nextLatest !== null && nextLatest > minNext) {
  currentIndex += 1;
  backCounter = 0;
  verdict = '전진 → 다음 노드로 이동';
}
// 후퇴 의심: prev 추세가 next 추세보다 크면서 +임계값 넘으면 카운트. 3번 연속돼야 실제로 되돌림
else if (trendPrev !== null && trendPrev > thresh && (trendNext === null || trendPrev > trendNext)) {
  backCounter += 1;
  if (backCounter >= 3) {
    currentIndex = Math.max(0, currentIndex - 1);
    backCounter = 0;
    verdict = '후퇴 → 이전 노드로 되돌림';
  } else {
    verdict = `이탈 의심 (${backCounter}/3, 연속되면 되돌림)`;
  }
} else {
  backCounter = 0;
}
```

**전진 조건을 3개 다 걸어둔 이유**: next 추세만 보면 "잠깐 노이즈로 next가 튄 것"과 실제 접근을 구분 못 함. current가 실제로 약해지고 있다는 것까지 같이 확인해야 함. `nextLatest > minNext`(기본 -85dBm)는 아직 거의 안 잡히는 next를 성급하게 현재 위치로 인정하지 않기 위한 최소 감지 기준.

**후퇴는 바로 안 되돌리고 3번 연속 조건**: 이전 노드 방향으로 신호가 세지는 건 사용자가 실제로 되돌아가는 경우 말고도 순간적인 반사/간섭으로도 생길 수 있어서, 1회성 노이즈로 `currentIndex`가 흔들리지 않게 완충 역할.

**prev/next 추세를 서로 비교하는 이유**: 비콘 하나의 신호는 거리(반경)만 알려주고 방향은 안 알려줌. prev·next 양쪽 신호가 동시에 세지는 애매한 구간(비콘 사이 좁은 공간 등)이 생길 수 있는데, 이때 "어느 쪽으로 더 강하게 끌리는지" 상대 비교로 결정함.

### 파라미터 (실측 후 조정 필요)

| 이름 | 기본값 | 의미 |
|---|---|---|
| 추세 임계값 | 3dB | 이 이상 변해야 "확실히 접근/이탈 중"으로 인정 |
| 다음 비콘 최소 신호 | -85dBm | 이보다 약하면 next로 전진 인정 안 함 |
| 후퇴 연속 횟수 | 3회 (코드에 고정) | 노이즈 한 번으로 안 되돌리기 위한 완충 |
| 추세 계산 윈도우 | 40개 샘플 (코드에 고정) | 너무 짧으면 노이즈에 흔들리고, 너무 길면 반응이 느려짐 |

`/monitor` 페이지에서 추세 임계값·다음 비콘 최소 신호는 입력창으로 바로 조정 가능. 나머지 둘은 코드 상수라 값 바꾸려면 `handler.py` 수정 필요.

### 원본 값도 같이 표시

```js
function drawLine(hist, field, color, dashed) {
  ctx.setLineDash(dashed ? [4, 3] : []);
  ctx.strokeStyle = color;
  ctx.lineWidth = dashed ? 1.5 : 2;
  ctx.beginPath();
  hist.forEach((p, idx) => {
    const x = pad + ((p.t - minT) / (maxT - minT)) * w;
    const y = pad + h - ((p[field] - minRssi) / (maxRssi - minRssi)) * h;
    if (idx === 0) ctx.moveTo(x, y); else ctx.lineTo(x, y);
  });
  ctx.stroke();
  ctx.setLineDash([]);
}

series.forEach(s => {
  const hist = historyByKey[s.key];
  drawLine(hist, 'raw', s.color, true);       // 원본 값 (점선)
  drawLine(hist, 'filtered', s.color, false); // 필터 값 (실선)
});
```

원래 차트는 필터(칼만) 값만 그렸는데, 원본이랑 비교가 안 되면 필터가 실제로 얼마나 노이즈를 줄이고 있는지 확인이 안 됨. `historyByKey`에 `raw`도 같이 저장하도록 바꾸고, 같은 색으로 실선(필터)·점선(원본) 두 줄을 겹쳐 그림. 추세 계산(`trendOf`)은 그대로 필터 값 기준 — 판정 로직 자체를 원본으로 바꾸면 다시 노이즈에 흔들리니까 여기는 안 건드림.

### 측정 구간 저장 (실측용)

```js
// 측정 중이면 (히스토리 버퍼와 별개로) 구간 전체를 따로 계속 쌓아둠 — 40개 제한 없이
if (measuring) {
  measurementLog.push({ t: Date.now(), key, raw: rawVal, filtered: filteredVal });
}
```

`historyByKey`는 추세 계산용으로 최근 40개까지만 남기는 롤링 버퍼라, 실측하면서 오래 재는 동안 앞부분 데이터가 계속 밀려서 없어짐. 그래서 "측정 시작" 누른 시점부터 "측정 종료"까지는 `measurementLog`라는 별도 배열에 개수 제한 없이 전부 쌓아둠. 특정 3개(prev/current/next)만이 아니라 그 순간 들어오는 모든 비콘 데이터를 기록함 — 나중에 분석할 때 어떤 비콘이 유용할지 미리 알 수 없어서.

종료하면 비콘별 샘플 수·원본/필터 min-max-평균을 표로 보여주고, `timestamp_iso, elapsed_ms, beacon, raw_rssi, filtered_rssi` 컬럼으로 CSV 다운로드 가능. 서버로 안 보내고 브라우저 안에서 Blob 만들어서 바로 다운로드하는 방식이라 백엔드 변경 없음.

### 추세 노이즈 완화 (실측 피드백 반영)

실측해보니 가만히 서 있는데도 추세 값이 순간적으로 6dB 이상 튀는 경우가 있었음 (임계값 기본 3dB의 두 배). 원인은 추세 계산이 최근 2개·가장 오래된 2개 평균만 비교하다 보니 RSSI 노이즈 한두 개에 바로 흔들렸기 때문. 두 가지로 완화함.

```js
// 1) 평균 구간을 2개 -> 4개로 늘림 (노이즈 한두 개가 평균에 미치는 영향 축소)
const TREND_WINDOW = 4;
function trendOf(key) {
  const hist = historyByKey[key];
  if (!hist || hist.length < TREND_WINDOW * 2) return null;
  const n = hist.length;
  let recentSum = 0, oldSum = 0;
  for (let i = 0; i < TREND_WINDOW; i++) {
    recentSum += hist[n - 1 - i].filtered;
    oldSum += hist[i].filtered;
  }
  return (recentSum / TREND_WINDOW) - (oldSum / TREND_WINDOW);
}
```

```js
// 2) 전진도 후퇴처럼 연속 판정 게이트를 둠 (기존엔 후퇴만 3연속 조건, 전진은 1회성으로 바로 넘어갔음)
if (/* 전진 조건 */) {
  forwardCounter += 1;
  backCounter = 0;
  if (forwardCounter >= 2) {
    currentIndex += 1;
    forwardCounter = 0;
    // ... 전진 확정
  } else {
    // "전진 감지 (N/2, 연속되면 이동)" — 아직 확정 아님
  }
}
```

후퇴는 기존처럼 3연속, 전진은 2연속으로 게이트를 걸어서, 노이즈로 한 번 튄 값만으로는 currentIndex가 안 바뀌게 함.

### 그래프 스냅샷 기능 제거

측정 시작/종료 및 비콘 전환 시점에 `trackChart`를 PNG로 캡처해 쌓아두는 스냅샷 기능을 한동안 넣어봤는데, 아래 "측정 구간 그래프" 기능으로 필요한 시각화가 대체되면서 쓸모가 없어져 관련 코드(`captureChartSnapshot`, `renderSnapshots`, `snapshots` 배열, `AUTO_SNAPSHOT_ON_CROSSOVER` 플래그, "📸 그래프 스냅샷" 카드/CSS 전부)를 삭제함. `/monitor`에는 더 이상 이 기능이 없음.

### 측정 구간 그래프 (CSV 대체용 시각화)

CSV 표는 숫자가 그대로 나열돼서 한눈에 추세가 안 들어온다는 피드백을 받아서, 측정 종료 시 x축 = 측정 시작 기준 경과 시간(delta t), y축 = RSSI로 하는 그래프를 새로 그려서 CSV 표 아래에 추가함. 측정 중 잡힌 비콘 전부를 색깔별로 겹쳐 그림 (원래 경로 추적 그래프처럼 실선=필터값, 점선=원본값).

```js
function drawMeasureChart(byKey) {
  const maxT = Math.max(...measurementLog.map(r => r.t - measureStartTime), 1000);
  function xFor(elapsed) { return leftPad + (elapsed / maxT) * w; }  // delta t 기준
  function yFor(v) { return topPad + h - ((v - minRssi) / (maxRssi - minRssi)) * h; }
  // 비콘별로 순회하며 raw(점선)/filtered(실선) 두 줄씩 그림, 색상은 팔레트에서 순서대로 배정
}
```

`historyByKey`(추적용, 40개 롤링)와 달리 `measurementLog`는 측정 구간 전체를 다 갖고 있어서, 그래프도 그 전체 구간을 다 그림 (표시 개수 제한 없음). x축 델타 t는 `row.t - measureStartTime`으로 계산.

그래프 옆에 "그래프 이미지 저장" 버튼을 둬서 `canvas.toDataURL('image/png')`로 그 순간 그래프를 PNG로 내려받을 수 있게 함 — 자동 캡처는 아니고 사용자가 원할 때만 저장하는 방식.

### 측정 그래프에 주변 비콘까지 다 잡히는 문제

측정 그래프를 실제로 뽑아보니 관심 없는 주변 ESP 비콘까지 전부 한 그래프에 겹쳐 그려져서 범례(4개)보다 훨씬 많은 선이 보이고 알아보기 힘든 문제가 있었음. 원인은 `measurementLog`가 상단 RSSI 표의 필터(`filterInput`)와 무관하게 서버에서 오는 모든 비콘 데이터를 그대로 다 기록하고 있었기 때문.

```js
// 상단 필터 입력창(filterInput)에 걸리는 비콘만 측정 기록에 남김 (필터를 비워두면 기존처럼 전부 기록)
if (measuring && matchesFilter(key)) {
  measurementLog.push({ t: Date.now(), key, raw: rawVal, filtered: filteredVal });
}
```

이미 있던 `matchesFilter()`(RSSI 표 필터링용)를 측정 기록 단계에도 그대로 재사용함. 측정 시작 전에 원하는 비콘 이름/MAC을 필터에 입력해두면 그래프·CSV 모두 그 비콘들만 남고, 필터를 비워두면 예전처럼 전부 기록됨.

### 절대 신호값 검증 추가 (추세만으로는 안 되는 이유)

실측해보니, current가 절대 신호값(RSSI) 기준으로는 여전히 확실히 더 센(가까운) 상태인데도, 노이즈로 순간 추세가 튀면서 currentIndex가 next/prev로 넘어가는 경우가 있었음. 추세(변화 방향)만 보고 절대값(지금 누가 실제로 더 가까운가)은 안 보고 있었던 게 원인.

```js
// current/prev의 "지금 이 순간" 절대 신호값
const curLatest = curHist && curHist.length > 0 ? curHist[curHist.length - 1].filtered : null;
const prevLatest = prevHist && prevHist.length > 0 ? prevHist[prevHist.length - 1].filtered : null;

// 전진: 기존 추세 조건에 추가로, next의 절대값이 실제로 current를 앞질렀을 때만 인정
if (trendNext !== null && trendCur !== null && trendNext > thresh && trendCur < -thresh
    && nextLatest !== null && nextLatest > minNext
    && curLatest !== null && nextLatest > curLatest) {
  ...
}
// 후퇴도 동일하게: prev의 절대값이 실제로 current를 앞질렀을 때만 인정
else if (trendPrev !== null && trendPrev > thresh && (trendNext === null || trendPrev > trendNext)
    && prevLatest !== null && curLatest !== null && prevLatest > curLatest) {
  ...
}
```

트렌드 비교 방식 자체는 그대로 유지(단순 부등호 판정으로 되돌아간 게 아님) — 다만 "추세가 방향을 가리켜도, 절대값 상 아직 current가 더 가까우면 넘어가지 않는다"는 조건을 AND로 하나 더 건 것. 즉 추세는 "누가 강해지는 방향인가"를 보고, 절대값 비교는 "실제로 그 비콘이 현재보다 가까워졌는가"를 보는 이중 확인 구조가 됨.

### 측정 그래프에 비콘 전환 지점 표시

측정 구간(시작~종료) 동안 `updateTracking()`에서 실제로 `currentIndex`가 바뀐(전진/후퇴 확정) 시점들을 따로 기록해뒀다가, 측정 그래프 위에 그 지점을 세로 점선 + 라벨로 표시함.

```js
let measurementCrossovers = []; // { t, label }

// updateTracking()의 전진 확정 블록 안에서
if (measuring) {
  measurementCrossovers.push({ t: Date.now(), label: `${pathTerms[currentIndex]} 도착` });
}
// 후퇴 확정 블록에도 동일하게 (label만 "복귀"로)
```

```js
// drawMeasureChart 안에서, RSSI 라인들을 다 그린 다음
measurementCrossovers.forEach(ev => {
  const elapsed = ev.t - measureStartTime;
  if (elapsed < 0 || elapsed > maxT) return;
  const x = xFor(elapsed);
  // x 위치에 세로 주황 점선 + 세로로 회전된 라벨 텍스트
});
```

측정 시작 버튼을 누를 때 `measurementLog`와 함께 초기화됨. "경로 진행 추적"이 켜져 있는 상태에서 측정해야 전환 지점이 기록됨 (추적을 안 켜두면 currentIndex 자체가 안 바뀌므로 표시할 것도 없음).

### 전환 라벨의 "도착/복귀" 구분 제거

실측해보니 어떤 구간에서 "beacon2 도착"이 나와야 할 것 같은 지점에 "beacon1 복귀"가 찍히는 등 라벨이 기대와 안 맞는 경우가 있었음. 원인은 버그가 아니라 **"도착"/"복귀"가 currentIndex 증가·감소(pathInput에 입력한 순서) 기준으로 결정되기 때문** — 실제로 어느 비콘이 지금 더 가까운지와는 무관함. pathInput에 `beacon1,beacon2`로 넣었는지 `beacon2,beacon1`로 넣었는지에 따라 똑같은 물리적 이동도 "전진"이 될 수도 "후퇴"가 될 수도 있어서, 사용자 입장에서는 방향성 라벨이 헷갈릴 수밖에 없음.

```js
// 방향(전진/후퇴) 구분 없이, 그냥 지금 currentIndex로 잡힌 비콘 이름만 남김
measurementCrossovers.push({ t: Date.now(), label: `${pathTerms[currentIndex]}로 전환` });
```

전진/후퇴 확정 블록 두 곳 모두 동일한 형식으로 통일함. 판정 로직(전진/후퇴 자체)은 그대로 두고, 측정 그래프에 남기는 라벨에서만 이 방향성 표현을 없앰 — 이전에 "현재 비콘이 뭔지만 보이면 되고 미래/과거 구분은 안 해도 된다"고 한 방향과도 일치.

### /monitor 차트를 Chart.js로 교체 + 비콘 체크박스 선택

기존엔 canvas 2D API로 직접 선을 그렸는데 두 가지 문제가 있었음.

1. **선명도**: canvas의 `width`/`height` 속성(픽셀 버퍼)과 CSS 표시 크기가 달라서, 고해상도(devicePixelRatio > 1) 화면에서 그림이 늘어나며 뭉개져 보였음.
2. **비콘 지정 방식**: 그래프에 띄울 비콘을 이름 일부로 타이핑하면 `findKeyForTerm()`이 substring 매칭으로 찾는 구조라, 오타나 부분 일치 때문에 엉뚱한 비콘이 잡히는 오류가 잦았음.

**차트 라이브러리로 교체.** 처음엔 Chart.js(v4)로 바꿨다가, 그래프 앞뒤가 잘려 보이는 문제가 남아서 최종적으로 **uPlot(v1.6.32, CDN)** 으로 다시 교체함. 둘 다 devicePixelRatio를 알아서 처리해서 선명도 문제는 해결되지만, uPlot 쪽이 실시간으로 계속 갱신되는 시계열에 더 가볍고 빠름. 시간축은 별도 날짜 어댑터 의존성을 피하려고 "경과 초"를 쓰는 일반 숫자축(`time: false`)으로 씀.

**축 범위 고정.** 축이 데이터에 맞춰 자동으로 늘었다 줄었다 하면 값이 들어올 때마다 눈금이 계속 바뀌어 그래프가 출렁이는 것처럼 보임. 그래서 축 범위를 고정값으로 바꾸고, 값은 입력창으로 조정할 수 있게 함.

- **Y축**: `Y축 최소/최대(dBm)` 입력값으로 고정 (기본 -100 ~ -30). 실시간·측정 그래프 공통.
- **실시간 그래프 X축**: `X축 표시 폭(초)` 만큼 폭을 고정한 채 최신 데이터를 따라 옆으로 흐름 (기본 30초 스크롤 창).
- **측정 그래프 X축**: 구간 전체를 한눈에 봐야 하므로 `0 ~ 측정 길이`로 고정 (스크롤 창 아님).

**X축 좌우 여백 없애기.** 처음엔 `end = Math.max(마지막값, 표시폭)`으로 잡았는데, 데이터가 아직 표시 폭만큼 안 쌓인 초반에는 **오른쪽이 비고 왼쪽에도 데이터 없는 구간이 남아** 양끝에 여백처럼 보였음. 축 범위를 항상 실제 데이터의 양 끝에 정확히 맞추도록 바꿈.

```js
function liveXRange(u) {
  const win = windowSec();
  const xs = u.data[0];
  if (!xs || xs.length === 0) return [0, win];
  const first = xs[0], last = xs[xs.length - 1];
  if (last <= first) return [first, first + 1];    // 점이 하나뿐일 때 0폭 방지
  if (last - first <= win) return [first, last];   // 표시 폭을 못 채웠으면 데이터에 딱 맞춤
  return [last - win, last];                       // 다 채운 뒤에는 고정 폭으로 스크롤
}
```

같이 필요했던 것 두 가지:

1. **표시용 버퍼 분리.** `historyByKey`는 추세 계산 규칙이 40개 기준으로 맞춰져 있어서 늘리면 판정 의미가 달라짐. 그래서 그래프 표시용 `displayByKey`(3분치 / 최대 1500개)를 따로 두고, 추세는 계속 40개 버퍼로 계산함. 이게 없으면 40개가 표시 폭보다 짧은 시간만 덮어서 X축 표시 폭 설정이 무의미해짐.
2. **윈도우 밖 데이터는 아예 안 넘김.** `buildAligned(..., sinceT)`로 표시 폭 밖의 오래된 점을 걸러서 넘김. 배열이 작아져 갱신이 가벼워지고, `xs[0]`이 곧 윈도우 시작점이 되어 축을 데이터에 딱 맞출 수 있음.

입력값을 바꾸면 `setData(chart.data)`로 다시 넣어야 `scales`의 `range` 함수가 재평가됨 — `redraw()`만 하면 이미 계산된 스케일을 그대로 다시 그려서 값이 안 바뀜.

**앞뒤 잘림 문제의 원인과 해결.** uPlot은 모든 시리즈가 **하나의 x축 배열을 공유**하는 구조라, 비콘마다 수신 시각이 제각각인 데이터를 그대로 넣을 수 없음. 그래서 전체 타임스탬프의 합집합을 x축으로 만들고 각 비콘은 자기 값이 없는 시각에 `null`을 채우는 정렬 단계를 넣었는데(`spanGaps`가 null 구간을 이어 그림), 이 정렬 덕분에 **시리즈별 x 범위가 달라서 그래프 앞뒤가 잘려 보이던 문제도 같이 해결됨**. 추가로 축 양끝에 6% 여백을 주는 `paddedRange()`를 x·y 모두에 적용해서 선이 축에 딱 붙어 잘려 보이지 않게 함.

```js
function buildAligned(sourceByKey, keys, t0) {
  const tsSet = new Set();
  keys.forEach(k => (sourceByKey[k] || []).forEach(p => tsSet.add(p.t)));
  const ts = Array.from(tsSet).sort((a, b) => a - b);

  const cols = [ts.map(t => (t - t0) / 1000)];   // 공유 x축 (경과 초)
  keys.forEach(k => {
    const byT = new Map();
    (sourceByKey[k] || []).forEach(p => byT.set(p.t, p));
    cols.push(ts.map(t => { const p = byT.get(t); return p ? p.filtered : null; }));
    cols.push(ts.map(t => { const p = byT.get(t); return p ? p.raw : null; }));
  });
  return cols;
}

function paddedRange(u, min, max) {
  if (min === max) return [min - 1, max + 1];
  const pad = (max - min) * 0.06;
  return [min - pad, max + pad];
}
```

실시간 차트는 매 메시지마다 차트를 다시 만들면 느려서, **보이는 비콘 구성(체크 상태)이 바뀔 때만 재생성**하고 평소엔 `setData()`로 값만 갱신함.

**비콘 선택은 체크박스로.** 들어오는 비콘을 `registerKey()`로 자동 등록하고(기본 체크됨, 색상도 이때 한 번만 배정해서 이후 순서가 바뀌어도 색이 안 흔들림), 체크를 풀면 표·실시간 그래프·측정 기록에서 모두 빠짐.

```js
function registerKey(key) {
  if (knownKeys.indexOf(key) !== -1) return false;
  knownKeys.push(key);
  colorByKey[key] = PALETTE[(knownKeys.length - 1) % PALETTE.length];
  checkedByKey[key] = true;   // 새 비콘은 기본으로 보이게
  return true;
}
function isChecked(key) { return checkedByKey[key] !== false; }
```

`isChecked()`가 예전 `matchesFilter()`가 하던 역할(표 필터 + 측정 기록 게이트)을 그대로 대체함.

**경로 노드도 타이핑 대신 드롭다운.** `pathSlots` 배열에 슬롯을 두고 각 슬롯마다 `<select>`를 띄우는데, 선택지는 실제로 잡힌 비콘 키 목록에서만 나옴. 그래서 `findKeyForTerm()` 같은 매칭 단계 자체가 사라졌고 `pathKeys`에는 항상 정확한 키가 들어감.

**전환 시점 표시는 uPlot 인라인 플러그인으로.** 별도 annotation 플러그인을 받지 않고 `draw` 훅에서 직접 세로 점선을 그림. uPlot 캔버스는 devicePixelRatio가 곱해진 좌표계라 `valToPos(..., true)`로 캔버스 픽셀을 직접 받고, 선 두께·폰트 크기도 `devicePixelRatio`를 곱해줘야 스케일이 맞음.

```js
function crossoverPlugin(getEvents) {
  return { hooks: { draw: u => {
    const dpr = devicePixelRatio || 1;
    getEvents().forEach(ev => {
      const x = u.valToPos(ev.sec, 'x', true);   // 캔버스 픽셀 좌표
      if (x < u.bbox.left || x > u.bbox.left + u.bbox.width) return;
      // 세로 주황 점선 + 가로 라벨 그리기 (선 두께/폰트에 dpr 곱)
    });
  } } };
}
```

라벨은 처음에 90도 회전시켜 세로로 그렸는데 읽기 불편해서 x축과 평행한 가로 방향으로 바꿈. 가로로 바꾸니 두 가지 문제가 새로 생겨서 같이 처리함.

**① 오른쪽 끝에서 잘림** — 남은 폭을 재서 안 들어가면 선 왼쪽에 그림.
**② 전환 시점이 가까우면 글자끼리 겹침** — 라벨을 모두 같은 높이에 그려서 생긴 문제. 줄마다 "이미 글자가 차지한 오른쪽 끝"을 기록해두고, 겹치지 않는 첫 줄을 찾아 한 칸씩 아래로 내려 그림.

```js
const rowEnds = [];   // 각 줄에서 글자가 차지한 오른쪽 끝 x
const sorted = events.slice().sort((a, b) => a.sec - b.sec);  // 왼쪽부터 배치해야 줄 배정이 자연스러움

sorted.forEach(ev => {
  const textWidth = ctx.measureText(ev.label).width;
  const fitsRight = x + gap + textWidth <= left + width;
  const startX = fitsRight ? x + gap : x - gap - textWidth;   // 안 들어가면 선 왼쪽으로
  const endX = startX + textWidth;

  let row = 0;
  while (row < rowEnds.length && startX < rowEnds[row]) row += 1;  // 빈 줄 찾기
  rowEnds[row] = endX + gap;

  ctx.fillText(ev.label, startX, top + 4 * dpr + row * lineHeight);
});
```

**③ 라벨 자체가 너무 김** — 비콘 키가 `"MAC|이름"` 형태라 `44:B1:76:19:46:32|ESP32-Beacon2로 전환`처럼 길어짐. `shortName()`으로 `|` 뒤의 이름만 뽑아 씀.

이미지 저장은 캔버스 배경이 투명이라, 흰 배경을 깐 임시 캔버스에 옮겨 그린 뒤 `toDataURL`로 내보냄.

### 기록 지우기 (버튼 2종)

표시용 버퍼가 3분치까지 쌓이다 보니, 자리를 옮겨가며 여러 번 재는 동안 옛 기록이 그래프에 계속 남아 방해가 됨. 지우는 범위를 두 단계로 나눔 — 매번 설정을 다시 하고 싶지는 않기 때문.

**① 그래프 기록 지우기** — 쌓인 값만 비우고 비콘 목록·체크 상태·색상·경로 설정은 그대로 둠. 자리만 옮겨서 다시 잴 때 사용.

```js
Object.keys(historyByKey).forEach(k => { historyByKey[k].length = 0; });
Object.keys(displayByKey).forEach(k => { displayByKey[k].length = 0; });
Object.keys(rows).forEach(k => { delete rows[k]; });
backCounter = 0;   // 비운 직후엔 비교할 이력이 없으므로 추세 판정 상태도 초기화
forwardCounter = 0;
```

배열을 `[]`로 새로 할당하지 않고 `length = 0`으로 비우는 이유는, `displayByKey[key]`를 참조로 들고 있는 코드(수신 루프의 `buf`)와 어긋나지 않게 하기 위함.

**② 비콘 목록까지 초기화** — 이제 안 잡히는 옛 비콘이 목록에 계속 남아있을 때 사용. 키·체크 상태·색상까지 전부 지움. 경로 설정이 사라진 비콘을 가리킬 수 있으므로 추적도 같이 중지하고 경로 슬롯을 비움. 되돌릴 수 없어서 `confirm()`으로 한 번 확인함.

### 폰에서 측정 구간 지정 (측정 제어 JSON)

`/monitor`에서 시작/종료를 누르면, 실제로 걸어다니는 사람과 버튼을 누르는 사람이 달라서 구간 경계가 부정확해짐. 그래서 **폰에서 구간을 지정하고 서버로 돌아와서 확인**하는 방식을 추가함. RSSI를 보내는 것과 **같은 웹소켓 연결**로 제어 메시지를 보낸다.

#### JSON 스펙

RSSI 메시지와 구분하기 위해 `type` 필드를 둠. RSSI 메시지에는 `type`이 없으므로 이 한 필드로 완전히 갈린다.

**측정 시작**

```json
{
  "type": "measure",
  "event": "start",
  "sessionId": "20260805-143012-a1b2",
  "label": "3층 복도 A→B",
  "timestamp": 1754400000000,
  "device": "SM-S911N"
}
```

**지점 표시** (측정 중 원하는 순간 — 비콘 통과 지점 등)

```json
{
  "type": "measure",
  "event": "mark",
  "sessionId": "20260805-143012-a1b2",
  "label": "beacon2 통과",
  "timestamp": 1754400012000
}
```

**측정 종료**

```json
{
  "type": "measure",
  "event": "end",
  "sessionId": "20260805-143012-a1b2",
  "label": "3층 복도 A→B",
  "timestamp": 1754400030000,
  "markCount": 2
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `type` | string | 항상 `"measure"`. 이 값이 있으면 RSSI가 아니라 제어 메시지 |
| `event` | string | `start` / `mark` / `end` 셋 중 하나 |
| `sessionId` | string | 폰이 발급 (`날짜-시각-난수`). 여러 폰이 붙어도 구간이 섞이지 않게 구분하는 용도 |
| `label` | string | 측정 이름. 앱의 입력창에 적은 값. 비어 있어도 됨 |
| `timestamp` | int | 폰 기준 epoch ms. 없으면 서버가 수신 시각으로 채움 |
| `device` | string | 폰 모델명(`Build.MODEL`). 어느 폰이 보낸 건지 로그에서 구분 |
| `markCount` | int | `end`에만 포함. 그 구간에서 표시한 지점 개수 |

#### 서버 처리

```python
# RSSI 데이터가 아닌 제어 메시지는 필터 경로를 타지 않고 따로 처리
if isinstance(data, dict) and data.get("type") == _MEASURE_TYPE:
    return _process_control(data)
```

`_process_control()`은 필드를 정규화해서(빈 값 채우기, 타입 강제) 중계용 JSON을 만들고 콘솔에 사람이 읽을 로그를 남김. **`_filters`(RSSI 칼만 필터 상태)는 전혀 건드리지 않음** — 제어 메시지가 필터 상태를 오염시키면 안 되므로 경로를 완전히 분리한 것.

스펙에 없는 `event`가 오면 그대로 통과시키지 않고 `{"event":"error","reason":...}`로 바꿔서 보냄. 그래야 `/monitor`가 모르는 이벤트를 측정 시작/종료로 착각하지 않음.

#### 앱 쪽 (bleapp)

- `WebSocketManager.sendControl(JSONObject)` — RSSI 전송(`send`)과 달리 맵 병합·timestamp 자동 추가를 하지 않고 만들어진 JSON을 그대로 보냄.
- `BleScanner.startMeasurement(label)` / `markMeasurement(label)` / `stopMeasurement()` — 세션 ID 발급과 상태 관리를 담당. `isMeasuring()`으로 현재 상태 조회.
- `MainActivity` — 측정 이름 입력창 + `측정 시작` / `지점 표시` / `측정 종료` 버튼. `BleScanner`가 싱글턴이라 화면을 나갔다 와도 측정이 유지되므로, `onStart()`에서 `updateMeasureUi()`로 버튼 상태를 실제 상태에 맞춤.

#### /monitor 쪽

버튼으로 시작하든 폰에서 시작하든 같은 경로를 타도록 `beginMeasurement(label, origin)` / `finishMeasurement(origin)`으로 공통화함. 화면에는 누가 시작했는지 아이콘으로 구분해서 표시(📱 폰 / 🖥️ 모니터)하고 측정 이름도 같이 보여줌.

```js
if (msg.event === 'end') {
  // 다른 세션(다른 폰)의 종료 신호로 내 측정이 끊기지 않게 세션 ID를 대조.
  // 단, monitor에서 직접 시작한 경우엔 세션 ID가 없으므로 그때는 그냥 종료시킨다.
  if (measureSessionId && msg.sessionId && msg.sessionId !== measureSessionId) return;
  finishMeasurement('phone');
}
```

`mark`는 기존 `measurementCrossovers`(비콘 전환 지점 표시용)에 그대로 넣어서, 측정 그래프에 세로 점선 + 라벨로 나타남 — 자동 전환 감지와 수동 표시가 같은 시각화를 공유한다.

### 한계 / 남은 문제

- 비콘 하나짜리 반경 정보만 쓰기 때문에, 갈림길·넓은 공간에서는 prev/current/next 세 개만으로 안 풀리는 경우가 있을 수 있음. 이 경우엔 근처에서 잡히는 다른 비콘까지 같이 봐야 할 수도 있음.
- 실제 비콘 간격·설치 밀도에 따라 임계값들이 달라질 수 있어서, 실측 데이터로 캘리브레이션 필요 (사용자가 이미 인지하고 있던 지점).
- 측정 구간 그래프도 비콘 수가 많아지면 팔레트(8색) 순환이라 색이 겹칠 수 있음 — 비콘이 8개를 넘는 세션에서는 범례로 구분 필요.
- uPlot을 CDN에서 받으므로 `/monitor`를 여는 브라우저에 인터넷이 없으면 그래프가 안 뜸. 오프라인 실측이 필요해지면 `uPlot.iife.min.js`와 `uPlot.min.css`를 받아서 정적 파일로 같이 서빙하도록 바꿔야 함.
- 측정 제어 메시지는 서버가 상태를 저장하지 않고 중계만 함. 그래서 `/monitor`를 측정 도중에 새로고침하면 그 구간 기록은 사라짐 (폰에서 종료를 눌러도 받을 페이지가 이미 초기화된 상태). 필요해지면 서버가 세션별로 들고 있도록 바꿔야 함.
- 폰이 `mark`를 보냈는데 `/monitor`가 측정 중이 아니면 그 표시는 버려짐 (담아둘 구간이 없음).
- `buildAligned()`는 비콘마다 타임스탬프가 거의 겹치지 않아서 x축 길이가 (비콘 수 × 샘플 수)만큼 커지고, 각 시리즈는 대부분 null이 됨. 실시간 차트는 비콘당 40개라 문제없지만, 아주 긴 구간을 측정하면 배열이 커질 수 있음 — 그때는 일정 간격으로 묶는(버킷팅) 처리가 필요할 수 있음.
