## 경로 진행 추적 (위치 추정) — `/monitor` 페이지

위치: `app/ws/handler.py`의 `_MONITOR_HTML` 안 `<script>`, "경로 진행 추적" 섹션.

### 전제

경로탐색 알고리즘(Dijkstra 등)이 이미 비콘 순서 `[b0, b1, ..., bn]`을 확정해줌. `currentIndex`는 지금 사용자가 있다고 판단하는 경로상 위치고, prev/current/next는 이 순서에서 -1/0/+1 — 즉 next는 방향을 추측하는 게 아니라 경로 목록에서 그냥 다음 칸.

### 추세(trend) 계산

```js
// 추세 = 최근 2개 평균 - 가장 오래된 2개 평균. 양수=신호가 강해짐(접근중), 음수=약해짐(멀어짐)
function trendOf(key) {
  const hist = historyByKey[key];
  if (!hist || hist.length < 4) return null;
  const n = hist.length;
  const recentAvg = (hist[n - 1].filtered + hist[n - 2].filtered) / 2;
  const oldAvg = (hist[0].filtered + hist[1].filtered) / 2;
  return recentAvg - oldAvg;
}
```

각 비콘의 필터링된(칼만 필터 통과한) RSSI 값을 최근 40개까지 `historyByKey`에 버퍼로 쌓아두고, 그 안에서 최근 2개 평균과 가장 오래된 2개 평균의 차이로 방향을 봄. 단순 부등호(지금 값이 이전 값보다 큰가)로는 노이즈에 바로 흔들려서, 구간 평균 차이로 완만하게 봄.

### 시작 노드 판정

```js
// 경로상 비콘들 중 지금 신호가 가장 센(필터값이 0에 가장 가까운) 걸 시작 노드로
let bestIdx = 0, bestVal = -Infinity;
pathTerms.forEach((term, idx) => {
  const key = findKeyForTerm(term);
  const hist = key ? historyByKey[key] : null;
  if (hist && hist.length > 0) {
    const latest = hist[hist.length - 1].filtered;
    if (latest > bestVal) { bestVal = latest; bestIdx = idx; }
  }
});
currentIndex = bestIdx;
```

앱 실행 시 신호가 가장 강한 노드를 시작 노드로 삼는다는 규칙 그대로 구현. "시작" 버튼 누른 시점의 스냅샷으로 한 번만 판정함.

### 전진 / 후퇴 / 유지 판정

```js
// 전진: next 추세가 +임계값 이상 && current 추세가 -임계값 이하 && next 신호가 최소 기준을 넘었을 때만 인정
if (trendNext !== null && trendCur !== null && trendNext > thresh && trendCur < -thresh
    && nextLatest !== null && nextLatest > minNext) {
  currentIndex += 1;
  backCounter = 0;
  verdict = '전진 → 다음 노드로 이동';
}
// 후퇴 의심: prev 추세가 next 추세보다 크면서 +임계값 넘으면 카운트. 3번 연속돼야 실제로 되돌림
else if (trendPrev !== null && trendPrev > thresh && (trendNext === null || trendPrev > trendNext)) {
  backCounter += 1;
  if (backCounter >= 3) {
    currentIndex = Math.max(0, currentIndex - 1);
    backCounter = 0;
    verdict = '후퇴 → 이전 노드로 되돌림';
  } else {
    verdict = `이탈 의심 (${backCounter}/3, 연속되면 되돌림)`;
  }
} else {
  backCounter = 0;
}
```

**전진 조건을 3개 다 걸어둔 이유**: next 추세만 보면 "잠깐 노이즈로 next가 튄 것"과 실제 접근을 구분 못 함. current가 실제로 약해지고 있다는 것까지 같이 확인해야 함. `nextLatest > minNext`(기본 -85dBm)는 아직 거의 안 잡히는 next를 성급하게 현재 위치로 인정하지 않기 위한 최소 감지 기준.

**후퇴는 바로 안 되돌리고 3번 연속 조건**: 이전 노드 방향으로 신호가 세지는 건 사용자가 실제로 되돌아가는 경우 말고도 순간적인 반사/간섭으로도 생길 수 있어서, 1회성 노이즈로 `currentIndex`가 흔들리지 않게 완충 역할.

**prev/next 추세를 서로 비교하는 이유**: 비콘 하나의 신호는 거리(반경)만 알려주고 방향은 안 알려줌. prev·next 양쪽 신호가 동시에 세지는 애매한 구간(비콘 사이 좁은 공간 등)이 생길 수 있는데, 이때 "어느 쪽으로 더 강하게 끌리는지" 상대 비교로 결정함.

### 파라미터 (실측 후 조정 필요)

| 이름 | 기본값 | 의미 |
|---|---|---|
| 추세 임계값 | 3dB | 이 이상 변해야 "확실히 접근/이탈 중"으로 인정 |
| 다음 비콘 최소 신호 | -85dBm | 이보다 약하면 next로 전진 인정 안 함 |
| 후퇴 연속 횟수 | 3회 (코드에 고정) | 노이즈 한 번으로 안 되돌리기 위한 완충 |
| 추세 계산 윈도우 | 40개 샘플 (코드에 고정) | 너무 짧으면 노이즈에 흔들리고, 너무 길면 반응이 느려짐 |

`/monitor` 페이지에서 추세 임계값·다음 비콘 최소 신호는 입력창으로 바로 조정 가능. 나머지 둘은 코드 상수라 값 바꾸려면 `handler.py` 수정 필요.

### 원본 값도 같이 표시

```js
function drawLine(hist, field, color, dashed) {
  ctx.setLineDash(dashed ? [4, 3] : []);
  ctx.strokeStyle = color;
  ctx.lineWidth = dashed ? 1.5 : 2;
  ctx.beginPath();
  hist.forEach((p, idx) => {
    const x = pad + ((p.t - minT) / (maxT - minT)) * w;
    const y = pad + h - ((p[field] - minRssi) / (maxRssi - minRssi)) * h;
    if (idx === 0) ctx.moveTo(x, y); else ctx.lineTo(x, y);
  });
  ctx.stroke();
  ctx.setLineDash([]);
}

series.forEach(s => {
  const hist = historyByKey[s.key];
  drawLine(hist, 'raw', s.color, true);       // 원본 값 (점선)
  drawLine(hist, 'filtered', s.color, false); // 필터 값 (실선)
});
```

원래 차트는 필터(칼만) 값만 그렸는데, 원본이랑 비교가 안 되면 필터가 실제로 얼마나 노이즈를 줄이고 있는지 확인이 안 됨. `historyByKey`에 `raw`도 같이 저장하도록 바꾸고, 같은 색으로 실선(필터)·점선(원본) 두 줄을 겹쳐 그림. 추세 계산(`trendOf`)은 그대로 필터 값 기준 — 판정 로직 자체를 원본으로 바꾸면 다시 노이즈에 흔들리니까 여기는 안 건드림.

### 측정 구간 저장 (실측용)

```js
// 측정 중이면 (히스토리 버퍼와 별개로) 구간 전체를 따로 계속 쌓아둠 — 40개 제한 없이
if (measuring) {
  measurementLog.push({ t: Date.now(), key, raw: rawVal, filtered: filteredVal });
}
```

`historyByKey`는 추세 계산용으로 최근 40개까지만 남기는 롤링 버퍼라, 실측하면서 오래 재는 동안 앞부분 데이터가 계속 밀려서 없어짐. 그래서 "측정 시작" 누른 시점부터 "측정 종료"까지는 `measurementLog`라는 별도 배열에 개수 제한 없이 전부 쌓아둠. 특정 3개(prev/current/next)만이 아니라 그 순간 들어오는 모든 비콘 데이터를 기록함 — 나중에 분석할 때 어떤 비콘이 유용할지 미리 알 수 없어서.

종료하면 비콘별 샘플 수·원본/필터 min-max-평균을 표로 보여주고, `timestamp_iso, elapsed_ms, beacon, raw_rssi, filtered_rssi` 컬럼으로 CSV 다운로드 가능. 서버로 안 보내고 브라우저 안에서 Blob 만들어서 바로 다운로드하는 방식이라 백엔드 변경 없음.

### 추세 노이즈 완화 (실측 피드백 반영)

실측해보니 가만히 서 있는데도 추세 값이 순간적으로 6dB 이상 튀는 경우가 있었음 (임계값 기본 3dB의 두 배). 원인은 추세 계산이 최근 2개·가장 오래된 2개 평균만 비교하다 보니 RSSI 노이즈 한두 개에 바로 흔들렸기 때문. 두 가지로 완화함.

```js
// 1) 평균 구간을 2개 -> 4개로 늘림 (노이즈 한두 개가 평균에 미치는 영향 축소)
const TREND_WINDOW = 4;
function trendOf(key) {
  const hist = historyByKey[key];
  if (!hist || hist.length < TREND_WINDOW * 2) return null;
  const n = hist.length;
  let recentSum = 0, oldSum = 0;
  for (let i = 0; i < TREND_WINDOW; i++) {
    recentSum += hist[n - 1 - i].filtered;
    oldSum += hist[i].filtered;
  }
  return (recentSum / TREND_WINDOW) - (oldSum / TREND_WINDOW);
}
```

```js
// 2) 전진도 후퇴처럼 연속 판정 게이트를 둠 (기존엔 후퇴만 3연속 조건, 전진은 1회성으로 바로 넘어갔음)
if (/* 전진 조건 */) {
  forwardCounter += 1;
  backCounter = 0;
  if (forwardCounter >= 2) {
    currentIndex += 1;
    forwardCounter = 0;
    // ... 전진 확정
  } else {
    // "전진 감지 (N/2, 연속되면 이동)" — 아직 확정 아님
  }
}
```

후퇴는 기존처럼 3연속, 전진은 2연속으로 게이트를 걸어서, 노이즈로 한 번 튄 값만으로는 currentIndex가 안 바뀌게 함.

### 그래프 스냅샷 기능 제거

측정 시작/종료 및 비콘 전환 시점에 `trackChart`를 PNG로 캡처해 쌓아두는 스냅샷 기능을 한동안 넣어봤는데, 아래 "측정 구간 그래프" 기능으로 필요한 시각화가 대체되면서 쓸모가 없어져 관련 코드(`captureChartSnapshot`, `renderSnapshots`, `snapshots` 배열, `AUTO_SNAPSHOT_ON_CROSSOVER` 플래그, "📸 그래프 스냅샷" 카드/CSS 전부)를 삭제함. `/monitor`에는 더 이상 이 기능이 없음.

### 측정 구간 그래프 (CSV 대체용 시각화)

CSV 표는 숫자가 그대로 나열돼서 한눈에 추세가 안 들어온다는 피드백을 받아서, 측정 종료 시 x축 = 측정 시작 기준 경과 시간(delta t), y축 = RSSI로 하는 그래프를 새로 그려서 CSV 표 아래에 추가함. 측정 중 잡힌 비콘 전부를 색깔별로 겹쳐 그림 (원래 경로 추적 그래프처럼 실선=필터값, 점선=원본값).

```js
function drawMeasureChart(byKey) {
  const maxT = Math.max(...measurementLog.map(r => r.t - measureStartTime), 1000);
  function xFor(elapsed) { return leftPad + (elapsed / maxT) * w; }  // delta t 기준
  function yFor(v) { return topPad + h - ((v - minRssi) / (maxRssi - minRssi)) * h; }
  // 비콘별로 순회하며 raw(점선)/filtered(실선) 두 줄씩 그림, 색상은 팔레트에서 순서대로 배정
}
```

`historyByKey`(추적용, 40개 롤링)와 달리 `measurementLog`는 측정 구간 전체를 다 갖고 있어서, 그래프도 그 전체 구간을 다 그림 (표시 개수 제한 없음). x축 델타 t는 `row.t - measureStartTime`으로 계산.

그래프 옆에 "그래프 이미지 저장" 버튼을 둬서 `canvas.toDataURL('image/png')`로 그 순간 그래프를 PNG로 내려받을 수 있게 함 — 자동 캡처는 아니고 사용자가 원할 때만 저장하는 방식.

### 측정 그래프에 주변 비콘까지 다 잡히는 문제

측정 그래프를 실제로 뽑아보니 관심 없는 주변 ESP 비콘까지 전부 한 그래프에 겹쳐 그려져서 범례(4개)보다 훨씬 많은 선이 보이고 알아보기 힘든 문제가 있었음. 원인은 `measurementLog`가 상단 RSSI 표의 필터(`filterInput`)와 무관하게 서버에서 오는 모든 비콘 데이터를 그대로 다 기록하고 있었기 때문.

```js
// 상단 필터 입력창(filterInput)에 걸리는 비콘만 측정 기록에 남김 (필터를 비워두면 기존처럼 전부 기록)
if (measuring && matchesFilter(key)) {
  measurementLog.push({ t: Date.now(), key, raw: rawVal, filtered: filteredVal });
}
```

이미 있던 `matchesFilter()`(RSSI 표 필터링용)를 측정 기록 단계에도 그대로 재사용함. 측정 시작 전에 원하는 비콘 이름/MAC을 필터에 입력해두면 그래프·CSV 모두 그 비콘들만 남고, 필터를 비워두면 예전처럼 전부 기록됨.

### 절대 신호값 검증 추가 (추세만으로는 안 되는 이유)

실측해보니, current가 절대 신호값(RSSI) 기준으로는 여전히 확실히 더 센(가까운) 상태인데도, 노이즈로 순간 추세가 튀면서 currentIndex가 next/prev로 넘어가는 경우가 있었음. 추세(변화 방향)만 보고 절대값(지금 누가 실제로 더 가까운가)은 안 보고 있었던 게 원인.

```js
// current/prev의 "지금 이 순간" 절대 신호값
const curLatest = curHist && curHist.length > 0 ? curHist[curHist.length - 1].filtered : null;
const prevLatest = prevHist && prevHist.length > 0 ? prevHist[prevHist.length - 1].filtered : null;

// 전진: 기존 추세 조건에 추가로, next의 절대값이 실제로 current를 앞질렀을 때만 인정
if (trendNext !== null && trendCur !== null && trendNext > thresh && trendCur < -thresh
    && nextLatest !== null && nextLatest > minNext
    && curLatest !== null && nextLatest > curLatest) {
  ...
}
// 후퇴도 동일하게: prev의 절대값이 실제로 current를 앞질렀을 때만 인정
else if (trendPrev !== null && trendPrev > thresh && (trendNext === null || trendPrev > trendNext)
    && prevLatest !== null && curLatest !== null && prevLatest > curLatest) {
  ...
}
```

트렌드 비교 방식 자체는 그대로 유지(단순 부등호 판정으로 되돌아간 게 아님) — 다만 "추세가 방향을 가리켜도, 절대값 상 아직 current가 더 가까우면 넘어가지 않는다"는 조건을 AND로 하나 더 건 것. 즉 추세는 "누가 강해지는 방향인가"를 보고, 절대값 비교는 "실제로 그 비콘이 현재보다 가까워졌는가"를 보는 이중 확인 구조가 됨.

### 측정 그래프에 비콘 전환 지점 표시

측정 구간(시작~종료) 동안 `updateTracking()`에서 실제로 `currentIndex`가 바뀐(전진/후퇴 확정) 시점들을 따로 기록해뒀다가, 측정 그래프 위에 그 지점을 세로 점선 + 라벨로 표시함.

```js
let measurementCrossovers = []; // { t, label }

// updateTracking()의 전진 확정 블록 안에서
if (measuring) {
  measurementCrossovers.push({ t: Date.now(), label: `${pathTerms[currentIndex]} 도착` });
}
// 후퇴 확정 블록에도 동일하게 (label만 "복귀"로)
```

```js
// drawMeasureChart 안에서, RSSI 라인들을 다 그린 다음
measurementCrossovers.forEach(ev => {
  const elapsed = ev.t - measureStartTime;
  if (elapsed < 0 || elapsed > maxT) return;
  const x = xFor(elapsed);
  // x 위치에 세로 주황 점선 + 세로로 회전된 라벨 텍스트
});
```

측정 시작 버튼을 누를 때 `measurementLog`와 함께 초기화됨. "경로 진행 추적"이 켜져 있는 상태에서 측정해야 전환 지점이 기록됨 (추적을 안 켜두면 currentIndex 자체가 안 바뀌므로 표시할 것도 없음).

### 전환 라벨의 "도착/복귀" 구분 제거

실측해보니 어떤 구간에서 "beacon2 도착"이 나와야 할 것 같은 지점에 "beacon1 복귀"가 찍히는 등 라벨이 기대와 안 맞는 경우가 있었음. 원인은 버그가 아니라 **"도착"/"복귀"가 currentIndex 증가·감소(pathInput에 입력한 순서) 기준으로 결정되기 때문** — 실제로 어느 비콘이 지금 더 가까운지와는 무관함. pathInput에 `beacon1,beacon2`로 넣었는지 `beacon2,beacon1`로 넣었는지에 따라 똑같은 물리적 이동도 "전진"이 될 수도 "후퇴"가 될 수도 있어서, 사용자 입장에서는 방향성 라벨이 헷갈릴 수밖에 없음.

```js
// 방향(전진/후퇴) 구분 없이, 그냥 지금 currentIndex로 잡힌 비콘 이름만 남김
measurementCrossovers.push({ t: Date.now(), label: `${pathTerms[currentIndex]}로 전환` });
```

전진/후퇴 확정 블록 두 곳 모두 동일한 형식으로 통일함. 판정 로직(전진/후퇴 자체)은 그대로 두고, 측정 그래프에 남기는 라벨에서만 이 방향성 표현을 없앰 — 이전에 "현재 비콘이 뭔지만 보이면 되고 미래/과거 구분은 안 해도 된다"고 한 방향과도 일치.

### 한계 / 남은 문제

- 비콘 하나짜리 반경 정보만 쓰기 때문에, 갈림길·넓은 공간에서는 prev/current/next 세 개만으로 안 풀리는 경우가 있을 수 있음. 이 경우엔 근처에서 잡히는 다른 비콘까지 같이 봐야 할 수도 있음.
- 실제 비콘 간격·설치 밀도에 따라 임계값들이 달라질 수 있어서, 실측 데이터로 캘리브레이션 필요 (사용자가 이미 인지하고 있던 지점).
- 측정 구간 그래프도 비콘 수가 많아지면 팔레트(8색) 순환이라 색이 겹칠 수 있음 — 비콘이 8개를 넘는 세션에서는 범례로 구분 필요.
