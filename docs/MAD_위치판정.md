# 위치 판정 방식 개선 — MAD 검토와 구간 분할 채택

폰을 가만히 뒀는데도 "1번, 2번, 1번" 하고 안내가 튀는 문제를 해결하는 과정에서
여러 방식을 실측 데이터로 비교했다. 결론부터: **MAD는 이 문제에 맞지 않았고,
구간 분할 방식을 채택했다.** 이 문서는 그 판단 근거를 남긴다.

---

## 1. 문제의 원인 — BLE 광고 채널 로테이션

실측 결과, **폰이 정지 상태여도 RSSI가 약 5.6초 주기로 10~12dB씩 오르내린다.**

BLE는 채널 3개(37/38/39 = 2402/2426/2480MHz)로 번갈아 광고하는데, 안드로이드 스캐너가
**한 채널에 약 1.8초씩 머물다가** 옮겨간다. 주파수가 78MHz나 떨어져 있어 채널마다 반사·간섭
양상이 다르고(frequency-selective fading), 실내에서 10dB 이상 차이는 흔하다.

**근거**: 서로 다른 위치의 비콘 2개가 소수점까지 같은 5.6초 주기(자기상관 0.66 / 0.69)를 보이면서
정확히 반대 위상(교차상관 **-0.71**)으로 움직였다. 환경이나 비콘 개체의 문제라면 이럴 수 없다.

정지 상태의 RSSI는 이런 모양이 된다.

```
-77 -77 -77 -78 -77 -77 -77 -78 -78 -78 | -67 -67 -67 -67 -67 -67 -67 -67 -67
←──────── 채널 A (약 1.8초) ──────────→  ←────── 채널 B로 전환 ──────→
```

한 채널에 머무는 동안은 같은 주파수·같은 경로라 값이 거의 안 변하고(같은 정수값이 20~25개
연속으로 나온다), 채널이 바뀌는 순간 **뚝 끊어지듯 10dB가 점프**한다.

> 참고: 처음에는 "같은 값이 25개 연속으로 나오는 건 물리적으로 불가능하다"고 판단했는데
> **틀렸다.** 채널 체류를 고려하면 자연스러운 현상이다. 또 안드로이드가 같은 패킷을 재전달하는
> 것도 아니다 — 패킷 수신 시각(`getTimestampNanos`)을 재보니 6만 개 중 중복이 0건이었다.

## 2. MAD란 무엇인가

**MAD**는 값들이 얼마나 흩어져 있는지를 재는 지표다. 표준편차와 목적은 같지만 평균 대신
**중앙값**을 쓴다. 여기서 주의할 점은 **이름이 같은 두 가지 정의가 있다**는 것이다.

| 이름 | 계산 | 성질 |
|---|---|---|
| 중앙값절대편차 (Median AD) | 중앙값에서의 거리들의 **중앙값** | 극단값에 매우 강함 |
| 평균절대편차 (Mean AD) | 중앙값에서의 거리들의 **평균** | 극단값에 끌려감 |

### 손으로 따라 해보기 (중앙값절대편차)

값이 `[-80, -78, -77, -77, -76]` 일 때:

1. **중앙값** — 정렬하면 `-80, -78, -77, -77, -76`, 가운데(3번째)는 **-77**
2. **각 값과의 거리** — `3, 1, 0, 0, 1`
3. **거리들의 중앙값** — 정렬하면 `0, 0, 1, 1, 3`, 가운데는 **1**

→ **MAD = 1**

여기서 **중앙값은 계산해서 만든 값이 아니라 정렬했을 때 실제로 한가운데 있는 값**이다.
(개수가 짝수면 가운데 두 값의 평균을 쓴다 — 이때만 계산이 들어간다)

### 극단값에 강한 이유

같은 값에 `-55` 하나를 추가해보자.

| | 원래 | -55 추가 후 | 변화 |
|---|---|---|---|
| 평균 | -77.6 | -73.8 | **3.8 끌려감** |
| 표준편차 | 1.4 | 8.5 | **6.3배 폭증** |
| 중앙값 | -77.0 | -77.0 | **변화 없음** |
| 중앙값절대편차 | 1.0 | 1.0 | **변화 없음** |

거리들은 `3, 1, 0, 0, 1, 22`가 되는데 정렬하면 `0, 0, 1, 1, 3, 22`이고, 가운데 두 값(1과 1)의
평균이라 MAD는 그대로 1.0이다. **-55가 만든 거리 22는 맨 끝으로 밀려나 가운데 선택에
아무 영향을 주지 못한다.**

### 두 정의의 결정적 차이

30개 샘플 중 `-67`(채널 전환값)이 늘어날 때:

| -67 개수 | 중앙값 | 거리의 **중앙값** | 거리의 **평균** |
|---|---|---|---|
| 0 | -77.0 | 0.0 | 0.00 |
| 9 | -77.0 | 0.0 | 3.00 |
| 14 | -77.0 | 0.0 | **4.67** |
| **15 (절반)** | **-72.0** | **5.0** | 5.00 |
| 16 | -67.0 | 0.0 | 4.67 |
| 30 | -67.0 | 0.0 | 0.00 |

- **거리의 평균**을 쓰면 극단값이 섞이는 만큼 값이 계속 커진다
- **거리의 중앙값**은 극단값이 **정확히 50%를 넘는 순간에만** 계단식으로 튄다

즉 중앙값 계열은 극단값에 강하지만, 50% 경계에서는 **한 샘플 차이로 10dB가 점프**하는
절벽이 있다. (실측에서는 `-67` 구간이 1.3~1.6초로 3초 창의 절반을 못 넘어서 이 절벽에
도달하지 않았고, 샘플 간 최대 점프는 평균 방식과 같은 1.45dB였다.)

## 3. MAD를 쓰지 않기로 한 이유

### 이유 1 — 방향 정보가 없다

MAD는 "얼마나 변했나"만 알려주고 "어느 쪽으로 변했나"는 알려주지 못한다. 부호가 없기 때문이다.

- 비콘에 **다가가서** -80 → -67로 올라도 → MAD 큼
- 비콘에서 **멀어져서** -67 → -80로 내려도 → MAD 큼
- 가만히 있는데 **채널만 바뀌어** -77 ↔ -67을 오가도 → MAD 큼

셋을 구분할 수 없으므로 **MAD 자체를 추세로 쓸 수 없다.** 추세에는 방향이 필요하다.

### 이유 2 — 정지/이동 구분도 안 된다

그렇다면 "지금 움직이는 중인가"를 판단하는 문지기로는 쓸 수 있을까? 실측 3파일(3초 창) 결과:

| | 정지 최대 | 이동 중앙값 | 판정 |
|---|---|---|---|
| 거리의 중앙값 | 2.75 | 0.75 | **겹침 (구분 불가)** |
| 거리의 평균 | 2.25 | 1.08 | **겹침 (구분 불가)** |

**정지 상태의 MAD가 이동보다 오히려 크다.** 채널 전환의 10dB 점프가 걷기로 인한 완만한
변화보다 순간 변동이 크기 때문이다. "MAD가 작으면 정지"라는 규칙이 성립하지 않는다.

(창을 5.6초로 늘리면 갈리는 것처럼 보였지만 3초 창에서는 뒤집혔다. 창 길이에 따라 결론이
바뀌는 불안정한 지표라 게이트로 쓰기 위험하다.)

## 4. 채택한 방식 — 구간 분할

### 기존 방식의 문제

```
40개 버퍼 중 [앞 4개 평균] 과 [뒤 4개 평균] 의 차이를 추세로 사용
```

- **40개 중 8개만 쓰고 32개를 버린다**
- 창이 **개수 기준**이라 수신 속도에 따라 실제 시간 폭이 달라진다
  (초당 10개면 4초, 초당 1개면 40초)
- 양끝 4개(0.4초)만 보므로 채널 전환 순간에 취약하다

### 구간 분할 방식

```
2.5초 창 (초당 10개면 약 25개)
  → 5개 구간으로 나눠 각 구간 평균 (구간당 약 5개)
  → 그 5개 평균점에 직선을 맞춰 기울기를 구함
  → 창 전체 변화량(dB)으로 환산 → 추세
```

구간 평균이 **1차 평활** 역할을 해서 채널 점프의 영향이 줄고, 그다음 기울기를 구하면
시간 순서 정보까지 반영된다. 단순 앞뒤 절반 비교는 결국 점 2개라 자르는 위치에 민감한데,
5구간은 5개 점으로 기울기를 재므로 한쪽 끝의 이상값에 덜 흔들린다.

**반환값을 기울기 자체가 아니라 "창 전체 변화량(dB)"으로 환산**하기 때문에, 기존 임계값(dB)을
그대로 쓸 수 있다.

## 5-A. 파라미터 최적화 (데이터셋 4개 전수 비교)

측정 파일이 4개(정지 2 · 이동 2) 모이자 파라미터를 눈대중이 아니라 **전수 비교로** 정할 수 있게 됐다.
데이터셋과 평가 스크립트를 저장소에 넣어 언제든 재현 가능하게 했다.

```
tests/measurements/            # CSV 4개 + manifest.json (232KB)
tests/eval_tracker.py          # python tests/eval_tracker.py --sweep-full
```

채점 항목은 네 가지다.

| 항목 | 의미 |
|---|---|
| 정지 오탐 | 서 있는데 안내가 나간 횟수. **0이 절대 조건** |
| 매칭 / 누락 / 초과 | 이동 전환을 제대로 잡았는지 (정답은 1초 구간별 최강 비콘 변화로 산출) |
| 평균 · 최대 지연 | 실제 전환 대비 안내가 얼마나 늦었는지 |
| 최소 통과 시간 | 합성 보행으로 "얼마나 빨리 지나가도 따라오는지" |

마지막 항목이 중요하다. 실측 데이터는 걷는 속도가 한 가지뿐이라 "빨리 지나가면 놓치는" 문제를
잴 수 없다. 창을 짧게 잡으면 정지 오탐은 줄지만 이 값이 나빠지는 트레이드오프가 있다.

### 창·구간별 "정지 오탐 0"이 되는 임계값 범위

마진이 넓다는 것은 다른 환경에서도 잘 버틴다는 뜻이다.

| 창 | 구간 | 안전 임계 범위 | 최대 지연 | 최소 통과 |
|---|---|---|---|---|
| 1.5초 | 5 | 2.0~2.5 (2개) | +1.14초 | 5초 |
| **2.0초** | **5** | **2.0~3.5 (4개)** | **+1.28초** | **6초** |
| 2.0초 | 4 | 2.0~3.0 (3개) | +1.28초 | 6초 |
| 2.5초 | 5 | 2.5~4.0 (4개) | +1.72초 | 7초 |
| 3.0초 | 5 | 3.0~4.0 (3개) | +1.86초 | 7초 |

**선정: 창 2.0초 / 5구간 / 임계 2.5dB**

- 안전 임계 범위가 2.0~3.5로 가장 넓다 → 2.5는 위아래로 여유가 있는 위치
- 창을 1.5초로 더 줄이면 수치는 조금 낫지만 안전 범위가 2개로 좁고, **관측된 채널 체류 시간
  (약 1.8초)보다 짧아** 다른 기기에서 깨질 위험이 있다
- 창 2.5초 이상은 지연이 커지고 최소 통과 시간도 나빠진다

### 기본값 변경 전후

| | trend (기존 방식) | segment 이전 기본 | **segment 새 기본** |
|---|---|---|---|
| 설정 | 40개 창 / 3.0dB | 2.5초 / 5구간 / 3.0dB | **2.0초 / 5구간 / 2.5dB** |
| 정지 오탐 | **6회** | 0 | **0** |
| 전환 검출 | 10/10 | 10/10 | 10/10 |
| 평균 지연 | +0.53초 | +0.36초 | **+0.24초** |
| 최대 지연 | +1.56초 | +1.72초 | **+1.28초** |
| 최소 통과 | 8초 | 6초 | **6초** |

## 5-B. 초기 실측 비교 결과

정지 2파일 + 이동 1파일로 전수 비교했다.

| 방식 | 정지A 오탐 | 정지B 오탐 | 이동 판정 | 안내 시점 | 최소 통과 시간 |
|---|---|---|---|---|---|
| 기존 (40개 중 양끝 4개) | **6회** | 0 | 정확 | 3.8초 전 | 8초 |
| 3초창 앞뒤 절반 (평균) | 0 | 0 | 정확 | 2.1초 전 | 8초 |
| 3초창 앞뒤 절반 (중앙값) | 0 | 0 | 정확 | 2.3초 전 | 8초 |
| **2.5초 / 5구간 / 임계 3dB** | **0** | **0** | **정확** | **2.8초 전** | **6초** |
| 2.5초 / 10구간 | 1 | 0 | 정확 | — | — |
| 3초창 전체 샘플 회귀 | 1 | 0 | 정확 | — | — |

**구간을 너무 잘게 쪼개면 역효과**다. 10구간이나 전체 샘플 회귀로 가면 구간당 샘플이 2~3개로
줄어 각 점이 다시 노이즈가 되고 오탐이 되살아난다. **4~6구간이 최적**이다.

### 최소 통과 시간

비콘 3개를 6m 간격으로 두고 통과 시간을 바꿔가며 시뮬레이션한 결과(3번에 도달해야 정상):

| 방식 | 4초 | 5초 | 6초 | 8초 | 12초 |
|---|---|---|---|---|---|
| 기존 | 1번 | 2번 | 2번 | 3번 | 3번 |
| **2.5초 / 5구간** | 2번 | 2번 | **3번** | 3번 | 3번 |

**8초 → 6초로 개선**됐다. 4초 통과는 창 2.5초로는 원리적으로 불가능하다
(구간당 2초면 추세를 낼 시간이 창보다 짧다).

## 6. 구현

기존 로직은 그대로 두고 **모드로 전환**한다. 판정 규칙(연속 2회·3회, 절대값 비교,
최소 감지 신호)은 양쪽 동일하고, **추세를 구하는 함수만 갈아끼운다.**

```python
MODE_TREND = "trend"       # 기존: 최근 40개 중 양끝 4개씩
MODE_SEGMENT = "segment"   # 신규: 시간 창을 N구간으로 쪼개 구간 평균의 기울기

DEFAULT_WINDOW_MS = 2500
DEFAULT_SEGMENTS = 5

def _trend(self, key):
    if self.mode == MODE_SEGMENT:
        return self._trend_segment(key)
    return self._trend_ends(key)
```

`history`를 값만 담던 것에서 `(수신시각, 값)` 튜플로 바꿨다. 시간 창을 쓰려면 시각이 필요하다.
버퍼는 개수(300)와 나이(15초) 둘 다로 정리하되, `trend` 모드는 여전히 최근 40개만 보므로
**기존 동작이 바뀌지 않는다.**

`/monitor`에서 판정 방식·창 길이·구간 수를 고를 수 있고, 기존 방식을 고르면 창·구간 입력칸이
비활성화된다. 서버는 `pathSet` 응답에 실제 적용된 설정을 실어 보내 화면에 표시한다.

## 8. 한계

- **4초 통과는 여전히 불가능하다.** 창이 2.5초라 그보다 빠른 이동은 원리적으로 못 따라간다.
  시각장애인 보행 속도(초당 0.5~1m)로 6m 간격이면 6~12초가 걸리므로 실사용에는 문제없을
  것으로 보이지만, 비콘 간격이 좁으면 재검토가 필요하다.
- **채널 체류 시간은 기기마다 다를 수 있다.** 여기서 관측한 5.6초는 특정 폰 기준이다.
  다른 기기에서는 주기가 달라지고, 그러면 최적 창 크기도 달라진다.
- **실측 표본이 3개 파일(정지 2, 이동 1)뿐이다.** 정지A와 정지B가 서로 다른 결과를 보인 것처럼
  (기존 방식에서 6회 대 0회) 조건에 따라 편차가 크다. 데이터가 쌓이면 파라미터를 다시 맞춰야 한다.
- 이동 파일이 1개뿐이라 **이동 중 오탐(있어야 할 곳에서 엉뚱한 번호를 부르는 경우)** 은
  충분히 검증하지 못했다.
