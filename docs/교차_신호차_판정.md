# 교차 신호차 판정 — 추세와 절대 RSSI 차이를 둘 다 요구한다

두 비콘이 교차한 뒤 **절대 RSSI 차이가 일정 이상 벌어졌을 때만** 전환을 확정한다.
기존 추세 조건은 그대로 두고 **AND로 함께** 건다.

| | |
|---|---|
| 구현 | `app/ws/path_tracker.py` — `_gap_value()`, `evaluate()` |
| 신호차 | `min_gap = 4.0 dB`, `gap_window_ms = 300` |
| 추세 | `require_trend = True` (함께 요구), `threshold = 2.5 dB` |
| 유지 시간 | `min_hold_ms = 0` (추세 창이 이미 시간 필터라 끔) |
| 절대 세기 하한 | `min_next = -85 dBm` **(이전과 동일)** |
| 재현 | `python tests/eval_tracker.py --sweep-gap` |
| 데이터 | `tests/measurements/` 13개 (정지 2, 이동 11) · 전환 31건 |

## 0. 판정식

```python
# 추세 — 지금 가까워지는 중인가 (방향)
trend_next > +2.5      and  trend_cur < -2.5

# 절대 세기 하한 — 너무 멀지 않은가 (이전과 동일)
next_latest > -85.0            # dBm

# 절대 RSSI 차이 — 실제로 얼마나 벌어졌는가 (크기)   ← 이번에 추가
next_mean - cur_mean >= 4.0    # dB, 최근 300ms 평균끼리 비교

# 위 셋을 모두 만족한 상태로 2회 연속 → 전진 확정
```

> `dBm` 은 절대 세기, `dB` 는 두 세기의 차이다.
> `min_next` 만 dBm 이고 `min_gap` 은 dB 다.

## 0-1. 왜 둘 다 필요한가 — 어느 한쪽만으로는 부족하다

| 구조 | 정지 오탐 | 검출 | 평균 지연 |
|---|---|---|---|
| 추세만 (차이 0dB) | **6** | 27/31 | +0.96초 |
| 차이만 3dB (추세 끔) | **1** | 31/31 | +0.70초 |
| **추세 AND 차이 4dB** | **0** | 27/31 | +1.29초 |

- **추세만 쓰면** 정지 상태에서 6건이 오탐으로 나간다.
- **차이만 쓰면** 검출은 좋지만 역시 오탐이 1건 난다.
- **둘 다 걸면 오탐 0.** 서로 다른 것을 보기 때문에 한쪽의 빈틈을 다른 쪽이 막는다.

```
추세      : 지금 가까워지는 중인가   → 방향
절대 차이 : 실제로 얼마나 벌어졌나   → 크기
```

## 0-2. 4.0dB 를 고른 근거

추세와 AND로 묶은 상태에서 차이값만 훑은 결과다.

```
   차이 │ 정지오탐   검출    평균지연   최소통과
 ───────┼──────────────────────────────────────
  0.0dB │    6     27/31    +0.96초     8초
  2.0dB │    4     27/31    +1.06초     8초
  3.0dB │    0     27/31    +1.12초     8초   ← 하한
  4.0dB │    0     27/31    +1.29초    10초   ← 채택
  5.0dB │    0     24/31    +1.51초    10초   ← 검출 하락 시작
  6.0dB │    0     23/31    +1.64초    12초
```

| | 값 | 근거 |
|---|---|---|
| 하한 | 3.0dB | 2.0dB 에서 정지 오탐 4건 |
| 상한 | 5.0dB | 여기서부터 실제 전환을 놓친다 (27 → 24건) |
| **채택** | **4.0dB** | 하한·상한의 **정확히 가운데**. 양쪽으로 1.0dB씩 여유 |

실제 전환의 **최소 분리폭은 9.0dB** 이므로 4.0dB 는 그 45% 수준이다.
(한때 3.8dB 로 보이던 전환 2건은 녹화가 끊긴 것이지 진짜로 좁은 게 아니었다.
 교차 후 0.6초 만에 파일이 끝났고 그 순간까지 계속 벌어지는 중이었다.)

## 0-3. 함께 고친 것 — 수신이 희박한 비콘

구간 추세는 창 안에 `구간수 × 2 = 10`개가 있어야 값을 낸다.
`walk_b12365` 는 1번 비콘이 3.1개/초뿐이라 추세가 아예 계산되지 않았고,
추세를 AND로 요구하니 그 비콘으로의 전환이 통째로 막혔다(4건 중 1건만 검출).

그래서 구간 추세를 못 낼 때는 **개수 기준(양끝 평균) 방식으로 대체**하도록 했다.

```python
if self.mode == MODE_SEGMENT:
    value = self._trend_segment(key)
    if value is not None:
        return value
    # 구간 방식은 창 안에 (구간수 × 2)개가 있어야 값을 낸다. 수신이 희박한
    # 비콘은 그 조건을 못 채워서 추세가 아예 None이 되고, 추세를 AND로
    # 요구하면 그 비콘으로의 전환이 통째로 막힌다.
    return self._trend_ends(key)
```

## 1. 왜 필요한가

기존 조건은 이랬다.

```python
and next_latest > cur_latest        # 다음 비콘이 더 세기만 하면 됨
```

문제는 **교차하는 순간에는 두 비콘의 세기가 거의 같다**는 것이다. 그 지점에서는
잡음만으로도 앞뒤가 쉽게 뒤바뀐다. 그래서 "더 세다"가 아니라 "이만큼 더 세다"를 요구한다.

```python
and next_mean - cur_mean >= self.min_gap
```

## 4. 하한 — 얼마나 작으면 잡음에 속나

### 4-1. 헛교차 (잠깐 앞질렀다 되돌아간 경우)

이동 데이터에서 "다음 비콘이 잠깐 앞섰다가 8초 안에 되돌아간" 구간의 봉우리를 모았다.

```
2초창 평균  :  5건  중앙값 0.7dB  90%값 6.3dB  최대 8.3dB
```

**대부분의 헛교차는 1dB 남짓**이다. 2dB면 83%가 걸러진다.

### 4-2. 정지 상태의 신호차 흔들림

움직이지 않았으니 여기서 나오는 차이는 전부 잡음이다.

|---|---|---|

| 300ms | 6.5dB | 3.9dB |
| 1000ms | 6.1dB | 3.9dB |
| 2000ms | 5.2dB | 3.7dB |

### 4-3. 여기서 나온 중요한 사실

**정지 상태의 잡음(6.5dB)이 상한(4.5dB)보다 크다.** 즉 이 조건만으로는

> 정지 오탐은 이미 추세 조건이 막고 있다.
> 이 신호차 조건이 맡는 것은 **교차 지점에서의 순간적인 뒤바뀜**이지
> 정지 상태 방어가 아니다. 이걸 혼동하면 값을 쓸데없이 크게 잡게 된다.

## 5. 측정 창을 따로 둔 이유

처음에는 추세 창(2초)을 그대로 썼다가 **빠른 걸음에서 전환을 무더기로 놓쳤다.**

임계 4dB 고정, 창만 바꿔가며 잰 매칭 수:

| 신호차 측정 창 | 매칭 |
|---|---|
| 최신값 | 26/31 |
| **300ms** | **26/31** |
| 500ms | 25/31 |
| 1000ms | 23/31 |
| 2000ms (추세 창과 동일) | **19/31** |

추세는 "기울기"라 길게 봐야 안정적이지만, 신호차는 "지금 얼마나 벌어졌나"라
**길게 보면 교차 지점을 걸쳐 평균내면서 차이가 작아진다.** 성격이 반대다.

최신값 하나만 보면 잡음을 그대로 맞으므로, 살짝만 평활하는 **300ms**로 정했다.

```python
def _gap_value(self, key):
    """신호차 비교에 쓸 대표값 — 최근 gap_window_ms 구간의 평균."""
    buf = self.history.get(key) if key else None
    if not buf:
        return None
    if self.gap_window_ms <= 0:
        return buf[-1][1]
    now = buf[-1][0]
    vals = [v for t, v in buf if now - t <= self.gap_window_ms]
    return sum(vals) / len(vals) if vals else buf[-1][1]
```

## 6. 최종 스윕 — 절대 차이만으로 판정

추세를 배제하고 차이 × 유지 시간을 훑었다. 표기는 `정지오탐 / 이동검출`.

```
   차이 │    0ms  100ms  200ms  300ms  500ms
 ───────┼───────────────────────────────────
  3.0dB │   1/31   1/31   1/29   0/29   0/29   ← 오탐 발생
  3.5dB │   0/31   0/31   0/29   0/29   0/29
  4.0dB │   0/29   0/29   0/29   0/29   0/29
  5.0dB │   0/29   0/29   0/29   0/29   0/29   ← 채택
  6.0dB │   0/29   0/29   0/29   0/29   0/29
```

### 하한 — 3.5dB

3.0dB 에서 정지 데이터에 오탐이 1건 난다. **여기가 잡음 바닥이다.**

### 상한 — 실제 분리폭이 정한다

한때 3.8dB 로 보이던 전환 2건이 상한을 압박하는 것처럼 보였지만, 확인해보니
**녹화가 끊긴 것**이었다.

```
walk_b123_a   2→3 교차 7.8초, 파일 끝 8.4초 → 교차 후 0.6초뿐
              마지막 1초에 -2.6dB → +5.1dB 로 계속 벌어지는 중
```

충분히 긴 파일의 같은 2→3 구간은 **9.0 / 13.0 / 15.2 / 21.2dB** 다.
**실제 최소 분리폭은 9.0dB.**

### 그래서 5.0dB

| | 값 | 근거 |
|---|---|---|
| 하한 | 3.5dB | 3.0dB에서 정지 오탐 1건 |
| 상한 | 9.0dB 아래 | 실제 최소 분리폭 |
| **채택** | **5.0dB** | 잡음 바닥에서 **2.0dB 위**, 최소 분리폭의 **55%** |

4.0dB 도 오탐 0에 검출이 같고 지연이 0.17초 짧지만, 잡음 바닥에서 1.0dB밖에
안 떨어져 있다. 정지 자료가 2건뿐이라 그 정도 여유로는 불안해서 5.0dB로 잡았다.

### 유지 시간 100ms 를 함께 켠 이유

`FORWARD_STREAK`(2회 연속)은 시간 필터가 되지 못한다. `evaluate()` 는 패킷마다
불리는데 실측 수신 속도로는 이렇다.

| 데이터 | 판정 빈도 | "2회 연속"의 실제 길이 |
|---|---|---|
| `walk_b1235_b` | 117.7회/초 | **17ms** |
| `walk_b123_a` | 32.0회/초 | 62ms |

17ms면 같은 잡음 봉우리 안이다. 절대 차이를 주 기준으로 삼으면 시간 필터가
반드시 필요해서 100ms 를 켰다. **검출을 전혀 깎지 않는다**(31/31 유지).

## 7-2. 자주 나오는 질문 세 가지

### Q1. 그래서 몇 dB 차이가 나야 하나

**3.0dB.** 안전 구간은 2.0~4.5dB.

> 단위는 dBm이 아니라 dB다. -67dBm과 -70dBm의 **차이**는 3dB다.
> dBm은 절대 세기, dB는 두 세기의 비율이다.

### Q2. 그러면 실제로 지나온 것보다 늦게 잡히는 것 아닌가

**맞다.** 다만 얼마나 늦는지 재보면 생각보다 작다.

| | 실제 신호 교차 대비 |
|---|---|
| 신호차 조건 없음 (0dB) | 중앙값 +0.56초 |
| **신호차 3dB** | **중앙값 +0.73초** |
| 신호차 조건이 더하는 몫 | **+0.23초** (보행 1.2m/s 기준 약 0.3m) |

**여기서 중요한 것**: "교차 지점"은 비콘 위가 아니라 **두 비콘의 딱 중간**이다.
RSSI가 같아지는 곳이 중간이기 때문이다.

```
   비콘A ●━━━━━━━━━━━━━━━━━━━━━━━━━━━━● 비콘B
                      ↑             ↑
                   교차 지점      3dB 지점
                   (중간)      (중간에서 0.5~1.2m)
```

그래서 "교차에서 바로 안내"해도 이미 중간까지 온 상태이고,
3dB를 기다리는 것은 거기서 **0.5~1.2m 더 간 지점**일 뿐이다.
오히려 중간에서 걸치는 동안 앞뒤가 뒤바뀌는 것을 막아준다.

중간보다 **앞서** 안내하려면 신호차로는 불가능하고 추세를 외삽해야 하는데,
그건 잘못 짚었을 때 되돌릴 수 없어서 택하지 않았다.

### Q3. 비콘 위를 정확히 걷지 않으면 신호차 폭이 줄어드는데 ★

**이것이 임계값을 크게 잡으면 안 되는 가장 큰 이유다.**

경로가 비콘에서 옆으로 h만큼 비켜 있으면, 같은 dB에 도달하는 지점이 훨씬 뒤로 밀린다.
아래는 중간 지점에서 **몇 m 더 가야** 그 신호차가 나오는지다.

**비콘 간격 6m**

| 옆으로 비킨 거리 | 2dB | 3dB | 4dB | 5dB | 6dB |
|---|---|---|---|---|---|
| 0m (비콘 바로 위) | 0.34m | **0.51m** | 0.68m | 0.84m | 1.00m |
| 1m | 0.38m | **0.57m** | 0.76m | 0.94m | 1.12m |
| 2m | 0.50m | **0.75m** | 1.01m | 1.26m | 1.53m |
| 3m | 0.70m | **1.06m** | 1.44m | 1.86m | 2.34m |
| 4m | 0.98m | **1.51m** | 2.11m | 2.89m | **도달 불가** |

**비켜 지나가는 정도가 클수록 큰 임계값은 급격히 나빠진다.**
간격 6m 통로를 4m 비켜 지나가면 **6dB는 아예 나오지 않는다** — 안내가 통째로 없다.
같은 조건에서 3dB는 1.51m만 더 가면 된다.

실측에서도 같은 경향이 확인된다. 전환 22건을 분리폭이 좁은 순으로 늘어놓으면:

```
 8.9dB  walk_roundtrip      2→3     ← 가장 좁음
 9.0dB  walk_b123_b         2→3
 9.2dB  walk_b5321_fast     2→1
10.2dB  walk_b32            3→2
11.8dB  walk_b12365         2→3
  …
34.2dB  walk_b1235_a        1→2     ← 가장 넓음
```

- 중앙값 15.9dB, 하위 25% 12.7dB, **최악 8.9dB**

| 임계값 | 최악 구간(8.9dB) 대비 여유 |
|---|---|
| **3dB** | **3.0배** |
| 5dB | 1.8배 |
| 6dB | 1.5배 |

**3dB가 실패하려면 그 지점의 분리폭이 3dB 미만이어야 한다.**
그 정도면 두 비콘이 거기서 사실상 구분되지 않는다는 뜻이라,
임계값 문제가 아니라 **비콘 배치 문제**다.

> 아직 확인 못 한 것: 이번 자료에 진짜 코너(꺾이는 구간) 통과가 없다.
> 코너에서 분리폭이 9dB보다 훨씬 좁게 나오면 3dB도 여유가 줄어든다.
> 코너 구간을 한 번 재서 이 표에 넣어보길 권한다.
> 분리폭이 6dB 아래로 나오면 **2dB로 낮추는 것**을 검토해야 한다
> (2dB도 정지 오탐 0, 매칭 26/31 로 3dB와 같고 최소 통과가 6초로 더 낫다).

## 7-3. "3dB는 잡음에 먹히지 않나" — 검증과 정정

타당한 의심이라 직접 재봤다. **처음 잰 방식이 틀렸다는 것부터 정정한다.**

### 잘못 쟀던 것

정지 상태에서 `|신호차| ≥ 3dB` 인 시간이 36~37%나 돼서 "게이트가 샌다"고 봤다.
하지만 **실제 조건은 방향이 있다.**

```python
next_mean - cur_mean >= self.min_gap      # 절대값이 아니다
```

정지 상태에서는 다음 비콘이 계속 약한 쪽이라 그 방향으로는 거의 넘지 않는다.

| | \|차이\| 기준 (잘못) | next − cur 기준 (실제) |
|---|---|---|
| `still_a` | 36% | **0.0%** |
| `still_b` | 37% | **0.8%** |

### 여유가 얼마나 있나

정지 데이터로 추적기를 돌려 **판정 직전까지 간 횟수**를 셌다.
전진은 2회 연속이면 발동하므로, streak가 1까지 올라간 적이 잦으면 위태롭다는 뜻이다.

```
신호차 0dB / 2dB / 3dB / 5dB / 8dB  — 전부 동일
   streak ≥ 1 도달 :     0 회
   전체 판정       : 1,065 회
   오탐            :     0 회
```

**한 번도 1에 도달하지 않았다.** 오탐 0이 아슬아슬한 0이 아니라 여유가 크게 남은 0이다.
조건별로 나눠 보면 실제 문지기가 누구인지도 분명하다.

```
still_b 기준
   신호차 3dB 통과   0.8%
   추세 조건 통과    0.0%   ← 여기서 이미 막힌다
   둘 다 통과        0.0%
```

신호차는 보조 조건이고, 잡음을 막는 것은 추세 조건이다.
그래서 신호차를 6dB로 올려도 **막을 것이 더 없고**, 코너·비켜걷기에서 손해만 커진다.

### 그래도 유효한 지적 — "2회 연속"에는 시간 개념이 없다

`evaluate()` 는 패킷이 올 때마다 불린다. 실측 수신 속도로 환산하면:

| 데이터 | 판정 빈도 | "2회 연속"의 실제 길이 |
|---|---|---|
| `walk_b1235_b` | 117.7회/초 | **17ms** |
| `walk_b12365` | 41.7회/초 | 48ms |
| `walk_b123_a` | 32.0회/초 | 62ms |

**17ms면 같은 잡음 봉우리 안이다.** 시간 필터라고 부를 수 없다.
지금 데이터에서는 추세 조건이 워낙 세서 드러나지 않았을 뿐,
수신이 느려지거나 비콘이 촘촘해지면 여기가 먼저 무너진다.

### 그래서 `min_hold_ms` 를 만들되 끄고 둔다

"조건이 T밀리초 계속 유지돼야 확정"을 넣고 값을 훑어봤다.

| 유지 시간 | 정지 오탐 | 매칭 | 평균 지연 | 최소 통과 |
|---|---|---|---|---|
| **0ms (기본)** | 0 | **26/31** | +1.13초 | 7초 |
| 100ms | 0 | 25/31 | +1.24초 | 7초 |
| 200ms | 0 | 24/31 | +1.37초 | 8초 |
| 500ms | 0 | 20/31 | +1.83초 | 10초 |

**공짜가 아니다.** 100ms만 요구해도 실제 전환 1건을 잃는다.
막을 오탐이 이미 없는데 검출만 깎이므로 **기본값은 0(끔)** 으로 두고,
현장에서 오탐이 실제로 보이면 그때 200~300ms로 켜는 레버로 남겼다.

```json
{ "type":"guide", "event":"setPath", "path":[…],
  "minGap": 3.0, "gapWindowMs": 300, "minHoldMs": 0 }
```

### 정리

| 의심 | 결과 |
|---|---|
| 3dB가 잡음에 먹히나 | **아니다.** 방향까지 보면 정지 통과율 0.0~0.8%, streak 도달 0회 |
| 값을 올려야 하나 | **아니다.** 막을 것이 없고 코너에서 손해만 커진다 |
| "2회 연속"이 약한가 | **맞다.** 17~62ms에 불과하다. `min_hold_ms` 로 대비책만 마련해뒀다 |

> 남는 한계: 정지 자료가 2건(20·30초, 비콘 2개)뿐이다.
> 더 시끄러운 환경에서 정지 측정을 몇 건 더 모으면 이 결론이 바뀔 수 있다.
> 그때는 `min_gap` 을 올리기 전에 `min_hold_ms` 를 먼저 켜보는 편이 낫다 —
> 코너 대응을 깎지 않기 때문이다.

## 8. 같이 발견한 별개 문제 (아직 안 고침)

이번 데이터로 돌려보니 **신호차와 무관하게** 놓치는 전환이 5건 있다.

**`walk_b12365` 는 4건 중 1건만 잡는다.** 원인은 수신 속도 불균형이다.

```
ESP32-Beacon1-tx    87개   3.1/초  (2초창 ≈  6.3개)  ← 구간 추세에 10개 필요
ESP32-Beacon2-tx   251개   9.0/초
ESP32-Beacon3-tx   295개  10.6/초
ESP32-Beacon5      259개   9.3/초
ESP32-Beacon6      269개   9.7/초
```

`_trend_segment()` 는 창 안에 `구간수 × 2 = 10`개가 있어야 값을 낸다.
1번 비콘은 그 절반뿐이라 추세가 아예 계산되지 않는다.

같은 경로를 나중에 다시 잰 `walk_b1235_a/b` 는 모든 비콘이 29/초로 균일하고
**3/3 을 다 잡는다.** 즉 이 파일 특유의 수신 문제이지 알고리즘 결함은 아니다.

> 다만 현장에서 수신이 나빠지면 같은 일이 생길 수 있으므로,
> 샘플이 모자랄 때 구간 수를 자동으로 줄이는 대비책은 따로 검토할 만하다.
> 이번 신호차 결정과는 별개 문제라 여기서는 손대지 않았다.

## 9. 바뀐 코드

`app/ws/path_tracker.py`

```python
DEFAULT_MIN_GAP = 3.0          # 교차 후 요구하는 신호차(dB)
DEFAULT_GAP_WINDOW_MS = 300    # 신호차 측정 창 (추세 창과 별개)
```

전진 조건에서 절대값 비교를 신호차 조건으로 바꿨다.

```python
# 이전
and next_latest > cur_latest

# 지금
and cur_mean is not None
and next_mean is not None
# 교차 후 신호차 조건 — 단순히 "더 세다"가 아니라 "이만큼 더 세다"를 요구한다.
# 교차 순간에는 둘이 거의 같아서 잡음만으로 앞뒤가 뒤바뀌기 때문이다.
and next_mean - cur_mean >= self.min_gap
```

후퇴 조건도 같은 방식으로 바꿨다.

```python
and prev_mean - cur_mean >= self.min_gap
```

두 값 모두 `setPath` 메시지로 바꿀 수 있다(`minGap`, `gapWindowMs`).
서버를 재시작하지 않고 현장에서 조정할 수 있다.
