# 2단계 확인 판정 (`confirm` 모드)

**② 구간 분할 위에 확인 단계를 얹은 방식.** ②를 대체하는 것이 아니라 뒤에 한 단계를 더 붙인다.

| | |
|---|---|
| 구현 | `app/ws/path_tracker.py` — `_confirm_stage()` |
| 기본값 | `mode="confirm"`, `confirm_delay_ms=500`, `confirm_gap=5.0`, `confirm_trend=0` |
| ② 파라미터 | `threshold=2.5`, `window_ms=2000`, `segments=5` (그대로 씀) |
| 재현 | `python tests/eval_tracker.py` |
| 데이터 | `tests/measurements/` 13개 · 전환 31건 |

```
②   추세 조건 성립 + 2회 연속  →  즉시 확정
③   추세 조건 성립 + 2회 연속  →  대기 0.5초  →  신호차 5dB 확인  →  확정
                                              └ 못 미치면 계속 지켜봄
                                              └ 도로 역전되면 취소
```

---

## 1. 왜 필요한가 — 측정으로 드러난 것

②가 **판정을 내리는 바로 그 순간**, 두 비콘의 절대 RSSI 차이를 26건 전부 재봤다.

```
   최소 -2.6dB   하위10% -1.1dB   중앙값 +0.6dB   최대 +19.0dB
```

**중앙값이 0.6dB다.** ②는 두 비콘이 거의 같은 순간에 결론을 낸다.
심지어 최소값은 음수 — 다음 비콘이 아직 더 약한데도 추세만 보고 판정한 경우다.

```
   RSSI
     │  현재 ╲
     │        ╲
     │         ╳ ← ②는 여기서 확정. 두 신호가 겹치는 가장 불안정한 지점
     │        ╱
     │  다음 ╱
     └──────────────→ 시간
```

그 순간이 하필 잡음이면 그대로 오판이 된다. 확인 단계는 이 지점을 메운다.

## 2. 판정 후 신호차가 벌어지는 속도

②가 판정한 시점부터 시간이 지나면 차이가 얼마나 벌어지는지.

| 대기 | 건수 | 최소 | 하위10% | 중앙값 | 최대 |
|---|---|---|---|---|---|
| 0ms | 26 | -2.6 | -1.1 | 0.6 | 19.0 |
| 300ms | 26 | 0.4 | 1.2 | 2.8 | 21.0 |
| **500ms** | 26 | -2.3 | 1.4 | **4.3** | 22.3 |
| 1000ms | 25 | -0.2 | 4.5 | 6.7 | 23.2 |
| 1500ms | 24 | 3.2 | 5.2 | 8.9 | 22.6 |
| 2000ms | 23 | 3.8 | 7.0 | 11.7 | 25.5 |

건수가 줄어드는 것에 주의 — 대기를 늘리면 그 사이 파일이 끝나거나 다음 전환이
시작돼서 확인 자체를 못 하는 경우가 생긴다.

## 3. 최적값 — 대기 × 확인 신호차 전수

`정지오탐 / 검출`. **② 원본은 0 / 26.**

```
     대기 │   2dB    3dB    4dB    5dB    6dB    8dB
   ───────┼──────────────────────────────────────────
    300ms │  0/26   0/26   0/26   0/26   0/25   0/20
    500ms │  0/26   0/26   0/26   0/26   0/25   0/20   ← 채택
    800ms │  0/25   0/25   0/25   0/25   0/25   0/20
   1000ms │  0/25   0/25   0/25   0/25   0/25   0/19
   1500ms │  0/24   0/24   0/24   0/24   0/24   0/19
   2000ms │  0/23   0/23   0/23   0/23   0/23   0/17
```

| | 값 | 근거 |
|---|---|---|
| 확인 신호차 상한 | 6dB | 여기서부터 검출이 준다 (26 → 25). 8dB면 6건을 놓친다 |
| 대기 상한 | 800ms | 여기서부터 검출이 준다 (26 → 25) |
| **채택** | **대기 500ms · 확인 5.0dB** | ②와 **똑같은 검출(26/31)** 을 유지하면서 요구할 수 있는 **가장 큰 신호차** |

**왜 5dB가 최적인가**: 확인 단계는 "5dB 될 때까지 기다린다"에 가깝다.
못 미쳐도 취소가 아니라 계속 지켜보므로, 값을 올리면 **검출보다 지연이 먼저 늘어난다.**
6dB부터는 지연으로 흡수되지 못하고 실제 손실이 시작된다. 그 바로 아래가 5dB다.

## 4. 세 방식 비교

| 방식 | 정지오탐 | 검출 | 평균 지연 | 최대 지연 | 최소 통과 |
|---|---|---|---|---|---|
| ① trend | 6 | 27/31 | +0.76초 | +5.78초 | 8초 |
| ② segment | 0 | 26/31 | **+0.59초** | **+3.06초** | **6초** |
| **③ ② + 확인 0.5초/5dB** | 0 | 26/31 | +1.51초 | +4.67초 | 10초 |

**③은 ②와 검출이 같다.** 대신 판정 시점에 신호차 5dB를 실제로 확인하고 넘어가므로
잡음에 강하고, 그 대가로 안내가 평균 0.9초 늦는다.

②가 더 빠르므로 **빠른 걸음을 우선하면 ②, 오판을 줄이려면 ③** 이다.
현재 기본은 ③.

## 5. 취소 동작

기다리는 동안 **교차가 되돌아가면 즉시 취소**한다. 잡음이었다는 뜻이다.

```python
if other_g <= cur_g:
    self._disarm("교차가 되돌아감 — 취소")
```

반대로 신호차가 아직 5dB에 못 미치는 것만으로는 취소하지 않는다.
대기 시간은 "이때부터 보기 시작한다"는 뜻이지 마감 시한이 아니다.
(처음엔 대기 후 한 번만 확인하고 취소하게 만들었다가, 조금만 더 기다리면 될 상황에서
매번 처음부터 다시 기다리느라 검출이 줄었다.)

## 6. 선택적 조건 — 확인 시점의 추세

`confirm_trend` 를 0보다 크게 두면 확인 시점에 다음 비콘의 추세도 함께 본다.
실측에서는 켜도 얻는 게 없고 검출만 줄어서 기본은 끔(0)이다.

## 7. 설정

```json
{ "type":"guide", "event":"setPath", "path":["…"],
  "mode": "confirm",
  "threshold": 2.5, "windowMs": 2000, "segments": 5,   // ② 부분 (그대로)
  "confirmDelayMs": 500,    // 판정 후 최소 대기
  "confirmGap": 5.0,        // 확인 시 요구하는 절대 신호차(dB)
  "confirmTrend": 0.0,      // 확인 시 추세도 볼지 (0 = 안 봄)
  "gapWindowMs": 300,       // 신호차를 잴 때 쓰는 평균 창
  "minNext": -85.0 }        // 절대 세기 하한(dBm)
```

`"mode": "segment"` 로 바꾸면 확인 단계 없이 ② 그대로 돌아간다.

## 8. 화면 표시

```

확인 중 3.1/5.0dB
확인 완료 (5.4dB) → 다음 노드로
교차가 되돌아감 — 취소
```

## 9. 아직 확인 못 한 것

- 정지 자료가 2건뿐이라 ②의 정지 오탐이 이미 0이다. 그래서 **확인 단계가 실제로
  막아낸 오판을 이 데이터로는 셀 수 없다.** 값의 근거는 "판정 순간의 신호차가
  중앙값 0.6dB"라는 관측이지, 오탐 감소 실적이 아니다.
- 더 시끄러운 환경에서 ②가 오탐을 내는 자료가 모이면 그때 확인값을 다시 정할 수 있다.
- 코너 통과 자료가 없다. 코너에서 분리폭이 5dB에 못 미치면 확인이 계속 지연된다.
