# 목적지 매칭 테스트하기 — 세 단계

Ollama에서 답이 나오는 것까지 됐다면, 남은 건 세 가지다.

```
①  매칭     내 JSON의 랜드마크 이름과 이어지는가      ← 서버·폰 없이
②  서버     WebSocket 왕복이 되는가                 ← 폰 없이
③  STT      마이크로 받아적는가                     ← 기기 필요
```

아래로 갈수록 필요한 게 늘어난다. **①부터 순서대로** 하면 문제가 생겨도
어디서 났는지 바로 안다.

---

## ① 매칭 — 내 프로젝트 파일로 직접 쳐보기

서버도 폰도 필요 없다. 매칭 부분만 떼어서 바로 시험한다.

```bash
python tests/try_destination.py --list          # 등록된 랜드마크 먼저 확인
python tests/try_destination.py                 # 대화형 — 직접 입력
python tests/try_destination.py "용변 보러"       # 한 문장만
python tests/try_destination.py --file 내목록.txt  # 내가 적은 문장들 한 번에
```

`--list` 는 **LLM에게 실제로 보여주는 목록**을 그대로 출력한다.

```
     L01  계단1          → 종류 '계단' + 1번
     L11  407          → 방 번호
     L12  화1           → 종류 '화' + 1번
```

### 시험 문장을 코드에 넣어두지 않는다

예전에는 `BATCH`·`GENERALIZE` 라는 목록에 시험 문장과 기대 답을 미리 적어뒀다.
**그 목록 자체가 문제였다.**

- 목록에 있는 표현만 계속 확인하게 되어, 사람들이 실제로 어떻게 말하는지는 알 수 없다
- 더 나쁘게는, 그 표현이 프롬프트에도 들어가 있으면 "되네" 하고 확인한 것이
  모델의 이해가 아니라 **프롬프트를 베낀 것**이 된다 (실제로 그랬다)

그래서 목록을 없앴다. 시험할 문장은 그때그때 직접 입력하거나, 자기가 적은 파일을
`--file` 로 넘긴다. **무엇을 시험할지는 코드가 아니라 사람이 정한다.**

```bash
# 내목록.txt — 아무거나 적으면 된다
용변 보러
손 씻는 데
위층 가는 곳
407호 좀 찾아주실래요
영화관
```

### 결과에서 **엔진**을 꼭 보라

```
  입력   '용변 보러'
  결과   ambiguous  →  ['화1', '화2']
  안내   "화 1번, 화 2번 중에서 말씀해 주세요."
  엔진   llm   (0.52초)          ← 이게 핵심
```

| 표시 | 뜻 |
|---|---|
| `llm` | LLM이 판단했다 |
| `rule` | LLM을 아예 안 썼다 (`LLM_PROVIDER=off`) |
| `llm→rule(호출 실패)` | LLM을 부르려다 실패해서 규칙 엔진으로 넘어갔다 |
| `llm→rule(번호 불일치)` | LLM이 엉뚱한 방을 골라서 버렸다 |

### 프롬프트에 무엇이 들어있는지 직접 본다

```bash
python tests/try_destination.py --prompt
```

**시험하려는 표현이 거기 이미 있으면 그 확인은 의미가 없다.**
지금은 few-shot을 실제 건물에 없는 가상 이름(`201호`, `도서관`, `수영장`)으로만
채워서 동의어를 하나도 가르치지 않는다. 그래서 동의어가 맞으면 모델이 원래 아는 것이다.

### 규칙 엔진은 어디까지 하나

```bash
python tests/try_destination.py --file 내목록.txt --rule
```

```
'407호 좀 찾아주실래요' → resolved   407              [rule]   ← 말투가 붙어도 잡는다
'화장실 어디 있나요'     → notFound   []                [rule]   ← 이름이 '화1'이라 못 잡음
'용변 보러'            → notFound   []                [rule]   ← 돌려 말하면 못 잡음
```

규칙 엔진에는 **동의어 표도, 어미 목록도 없다.** 숫자 정확 일치와 부분 유사도뿐이다.
말투가 붙어도 이름만 찾아내지만(`407호 좀 찾아주실래요` → 407),
뜻으로 돌려 말한 것은 못 잡는다. 그건 LLM의 몫이다.

> 지금 프로젝트 파일의 이름이 `화1`, `엘베1` 같은 줄임말이라 규칙 엔진이 더 불리하다.
> `화장실 1`, `엘리베이터 1` 로 풀어 쓰면 LLM이 죽었을 때의 폴백 품질이 올라간다.

## ①-2 LLM이 진짜 도는지 눈으로 확인하기

"정상 동작하는 것 같은데 정말 모델이 답한 건가?" 를 확인하는 방법이 네 가지 있다.

### 방법 1. `--trace` — 오간 값 전부 출력

```bash
python tests/try_destination.py --trace "용변 보러"
```

```
[REQUEST]
  provider      ollama
  model         exaone3.5:7.8b
  endpoint      http://localhost:11434/api/chat
  timeout       6 s
  landmarks     24
  input         '용변 보러'

[PROMPT] 마지막 메시지
  장소 목록:
  - L11: 407
  - L12: 화1
  - L13: 화2
    …
  사용자: "용변 보러"

[RESPONSE]
  raw           {"ids": ["L12", "L13"], "why": "볼일 보는 곳"}
  model         exaone3.5:7.8b
  elapsed       1.84 s
  prompt_tokens 312
  eval_tokens   34
  tokens/s      21.5
  load          0.04 s

[PARSE]
  ids           ['L12', 'L13']
  names         ['화1', '화2']
  status        ambiguous
  source        llm

[OUTPUT]
  landmark      ['화1', '화2']
  speech        화 1번, 화 2번 중에서 말씀해 주세요.
  total         1.85 s
```

| 지표 | 의미 |
|---|---|
| `raw` | 모델이 돌려준 문자열 그대로 |
| `prompt_tokens` / `eval_tokens` | Ollama가 센 입력·생성 토큰 수 |
| `tokens/s` | 생성 속도 (`eval_count / eval_duration`) |
| `load` | 모델 적재 시간. 첫 호출이 아니면 0에 가깝다 |
| `ids` → `names` | 응답 id 중 목록에 있는 것만 남긴 결과 |
| `source` | `llm` / `rule` / `llm→rule(사유)` |

`prompt_tokens`·`eval_tokens`·`tokens/s` 는 Ollama가 생성 과정에서 집계한 값이라,
규칙 엔진이 처리한 경우에는 존재하지 않는다.

모델 호출이 없었으면 `[RESPONSE]` 가 이렇게 나온다.

```
[RESPONSE]
  raw           -
  note          모델 호출 없음
[PARSE]
  ids           -
  status        notFound
  source        llm→rule(호출 실패)
```

### 방법 2. `LLM_DEBUG=1` — 부를 때마다 세 줄씩 로그

```bash
LLM_DEBUG=1 python tests/try_destination.py "손 씻는 데"
```

```
[LLM] 질문 '손 씻는 데'
[LLM] 모델 exaone3.5:7.8b · 1.62초 · 입력 312토큰 · 생성 34토큰 · 21.5토큰/초
[LLM] 원문 응답: '{"ids": ["L12", "L13"], "why": "볼일 보는 곳"}'
```

**서버에도 그대로 적용된다.** 데모 중에 폰으로 말하면서 서버 콘솔을 보면
호출이 실시간으로 찍힌다.

```bash
LLM_DEBUG=1 uvicorn app.main:app --host 0.0.0.0 --port 8000
```

### 방법 3. Ollama 쪽에서 확인

```bash
ollama ps
```

```
NAME              ID              SIZE      PROCESSOR    UNTIL
exaone3.5:7.8b    abc123def456    6.2 GB    100% CPU     29 minutes from now
```

모델이 **메모리에 올라와 있으면** 우리 서버가 실제로 불렀다는 뜻이다
(`keep_alive=30m` 으로 붙잡아 두기 때문). 아무도 안 불렀으면 목록이 비어 있다.

Ollama 서버 로그도 볼 수 있다.

```bash
# Linux (서비스로 설치한 경우)
sudo journalctl -u ollama -f

# 직접 띄운 경우 — 그 터미널에 그대로 찍힌다
ollama serve
```

요청이 들어올 때마다 `POST /api/chat` 이 찍힌다.

### 방법 4. 켜고 끄고 대조 (가장 직관적)

같은 문장을 두 번, 한 번은 LLM을 꺼서 돌린다.

```bash
python tests/try_destination.py "용변 보러"            # LLM 켬
python tests/try_destination.py "용변 보러" --rule      # LLM 끔
```

```
LLM 켬 : ambiguous  ['화1','화2']   [llm]
LLM 끔 : notFound   []              [rule]
```

**결과가 갈리면 LLM이 일하고 있는 것이다.** 규칙 엔진에는 동의어 지식이 아예
없으므로 돌려 말한 표현은 반드시 `notFound` 가 나온다.

### 정리 — 무엇을 보면 되나

| 보고 싶은 것 | 방법 |
|---|---|
| 모델이 뭐라고 답했는지 원문 | `--trace` ②번 칸 |
| 정말 생성했는지 (증거) | `--trace` 의 토큰 수·토큰/초 |
| 실시간으로 흐르는지 | `LLM_DEBUG=1` |
| 모델이 메모리에 있는지 | `ollama ps` |
| 요청이 도달했는지 | `journalctl -u ollama -f` |
| LLM 없을 때와 뭐가 다른지 | `--rule` 로 대조 |

## ② 서버 — 폰인 척하고 WebSocket 왕복

앱을 빌드하지 않고 **마이크를 뺀 전부**를 확인한다.
앱이 실제로 보내는 것과 똑같은 JSON을 보낸다(`BleScanner.sendDestination` 참고).

```bash
# 서버를 먼저 띄운다
uvicorn app.main:app --host 0.0.0.0 --port 8000

# 다른 터미널에서
python tests/ws_phone.py --scenario          # 정해둔 대화 자동 실행
python tests/ws_phone.py                     # 대화형
python tests/ws_phone.py --url wss://hanium.mcsmtp.org/ws
```

```
  📱 resolve  "407호로 가줘"      ← 방 번호 — 한 번에 확정되어야 함
  🖥  확정   407  (id=L11, x=888.0, y=1450.0)
  🔊 "407호로 안내합니다."   (0.08초)

  📱 resolve  "409"             ← 같은 번호 2곳 → 되묻기
  🖥  되묻기 ['409(1)', '409(2)']
  🔊 "409호 1번, 409호 2번 중에서 말씀해 주세요."

  📱 choose   "첫번째"           ← 되묻기 답변
  🖥  확정   409(1)  (id=L06, x=188.0, y=1456.0)
  🔊 "409호로 안내합니다."
```

대화형에서는 **되물으면 다음 입력이 자동으로 선택(`choose`)으로** 나간다.
앱의 동작과 같다.

여기까지 되면 서버 쪽은 끝이다. 앱에서 안 되면 앱 문제다.

> `x`, `y` 좌표가 같이 온다. 나중에 경로 계산을 붙일 때 쓸 값이다.

## ②-2 전 구간 점검 — 어디서 막혔는지 한 번에

`ws_phone.py` 는 대화를 흉내내는 도구고, 이건 **구간별로 살아 있는지**를 본다.
앱이 안 될 때 원인이 폰인지 서버인지 모델인지부터 갈라야 한다.

```bash
python tests/check_pipeline.py                       # 전 구간
python tests/check_pipeline.py --url ws://192.168.0.10:8000/ws
python tests/check_pipeline.py --say "화장실"          # 한마디만
python tests/check_pipeline.py --load                # RSSI 흘리면서
```

```
점검 대상: ws://127.0.0.1:8000/ws

── 연결 ──
  ✓ WebSocket 연결                       8 ms

── 랜드마크 ──
  ✓ 서버가 들고 있는 랜드마크                24개
     계단1, 엘베1, 엘베2, 계단2, 410, 409(1), 409(2), 411, 408, 412 …

── 왕복 ──
  ✓ "계단1"                              확정 계단1  (1.00초)
  ✓ 판단 주체                              llm
  ✓ Ollama                             모델이 판단했다
```

시험 문장을 코드에 안 적었다. **서버가 실제로 들고 있는 이름 중 하나**를
골라서 왕복시킨다. 프로젝트 파일을 바꿔도 그대로 쓸 수 있고, 시험 문장이
프롬프트에 들어가 있어서 생기는 착시도 없다.

### `--load` 가 중요한 이유

조용한 상태로 시험하면 안 보이는 문제가 있다. 실제로는 **걸어가면서**
말하므로 RSSI 가 계속 흐른다. 그 상태에서 목적지를 물었을 때 중계가 끊기면
위치 판정이 같이 무너진다.

폰 역할과 모니터 역할로 각각 붙어서, 해석하는 동안 중계가 멈추는지 잰다.

```
── RSSI 를 흘리면서 목적지 해석 ──
  ✓ 목적지 응답              확정 엘베1  (1.01초)
  ✓ 그동안 보낸 RSSI          30개
  ✓ 모니터가 받은 중계         30개 (요청 시점 이후 20개)
  ✓ 중계가 끊긴 최대 구간       0.10초

  ✓ 해석에 1.0초가 걸렸는데도 중계는 최대 0.10초만 비었다.
```

`0.10초` 는 RSSI 를 보내는 간격 그 자체다. 즉 한 박자도 안 빠졌다.
막혔다면 이렇게 나온다.

```
  ✗ 중계가 끊긴 최대 구간       2.60초
  ✗ 목적지를 해석하는 동안 중계가 2.6초 멈췄다.
     이벤트 루프가 막혔다는 뜻이다 — handler.websocket_endpoint 의
     asyncio.to_thread 분기가 동작하는지 확인할 것.
```

같은 말을 두 번 물으면 서버가 캐시해둬서 모델을 안 부른다. 그러면 느린
경로를 안 타므로 측정이 무의미해진다. 응답이 0.3초 안에 오면 **측정 무효**로
표시한다.

### 읽는 법

| 표시 | 뜻 | 다음에 볼 곳 |
|---|---|---|
| 연결 ✗ | 서버가 안 떴거나 주소가 틀림 | `uvicorn app.main:app --host 0.0.0.0` |
| 랜드마크 0개 | 지도 프로젝트 파일을 못 찾음 | `MAP_TOOL_DIR` 환경변수 |
| 판단 주체 `llm` | 모델이 판단했다 | 정상 |
| 판단 주체 `llm→rule(…)` | 모델을 못 불러 규칙 엔진이 받았다 | `ollama ps`, `ollama list` |
| 판단 주체 `rule` | `LLM_PROVIDER=off` 로 꺼둔 상태 | 환경변수 확인 |
| 중계 끊김 ✗ | 해석이 이벤트 루프를 막고 있다 | `handler.py` 의 `_handle_destination` |

## ③ STT — 여기서부터는 기기가 필요하다

음성 인식은 **에뮬레이터로는 제대로 안 된다.** 실제 안드로이드 기기에서 해야 한다.

### 준비

1. Android Studio에서 `server/bleapp` 열고 빌드
2. USB로 기기 연결 후 실행
3. 앱을 처음 켜면 권한을 묻는다 — **마이크 허용**
4. 서버 주소를 입력하고 `연결`

### 확인 순서

```
1. 🎤 목적지 말하기  버튼이 눌리는가
      · 비활성이면 → "이 기기에서 음성 인식을 쓸 수 없습니다"
        Android 11+ 의 <queries> 선언 문제일 가능성이 크다 (매니페스트 확인)

2. 버튼을 누르면 "듣는 중…" 으로 바뀌는가
      · 안 바뀌면 마이크 권한 문제

3. "407호"라고 말하면 화면에 들은 말이 뜨는가
      · "들은 말: 407호" 가 뜨면 STT는 성공이다

4. 잠시 뒤 음성으로 "407호로 안내합니다" 가 나오는가
      · 여기까지 오면 전체가 연결된 것이다

5. "변소" 라고 말해본다
      · 되묻기 음성이 끝난 뒤 마이크가 자동으로 켜진다
      · "두 번째" 라고 답하면 확정
```

### Logcat 으로 보기

```bash
adb logcat -s VoiceInput:D SpeechGuide:D BleScanner:D WebSocketManager:D
```

| 태그 | 볼 것 |
|---|---|
| `VoiceInput` | `받아적음: 407호 (후보 3개)` — STT 결과 |
| `WebSocketManager` | `제어 메시지 전송: {"type":"destination"...}` — 서버로 나갔는지 |
| `WebSocketManager` | `서버 메시지 :` — 응답이 왔는지 |
| `SpeechGuide` | `안내 음성: 407호로 안내합니다.` — TTS가 읽었는지 |

이 네 줄이 순서대로 찍히면 전체 경로가 정상이다.
**어느 줄에서 끊기는지가 곧 문제 위치다.**

### 자주 나오는 문제

| 증상 | 원인 |
|---|---|
| 버튼이 회색 | `<queries>` 선언 누락 (Android 11+). `AndroidManifest.xml` 확인 |
| "마이크 권한이 필요합니다" | 설정 → 앱 → 권한에서 마이크 허용 |
| "네트워크에 연결되지 않아…" | 구글 음성 인식은 기본적으로 인터넷이 필요하다 |
| 받아적기는 되는데 응답이 없음 | 서버 연결 문제. ②로 돌아가서 확인 |
| 응답은 오는데 소리가 안 남 | `비콘 전환 음성 안내` 체크박스가 꺼져 있는지 확인 |
| 되묻기 뒤 마이크가 안 켜짐 | TTS `onDone` 콜백 문제. Logcat 의 `SpeechGuide` 확인 |
