# 위치 판정 로직 — 파일 위치와 전체 코드 해설

HTML(`app/ws/monitor.html`, `map-tool/map_inspection.html`)은 화면 표시용이라 제외했다.
**판정에 실제로 관여하는 파이썬 코드 전부**를 한 줄씩 설명한다.

## 2. 데이터가 흐르는 순서

```
 [안드로이드 폰]
      │  WebSocket 으로 JSON 전송
      │  { "MAC|ESP32-Beacon1-tx": -67, "timestamp": 1234567890 }
      ▼
 handler.websocket_endpoint()        ← /ws 로 들어온다
      │
      ▼
 handler._process_message()          ← 메시지 종류를 나눈다
      │
      ├─ type=="measure" ──► _process_control()  측정 시작/종료 → 안내 켜기/끄기
      ├─ type=="guide"   ──► _process_guide()    경로 등록/중지
      └─ 그 외 (= RSSI)  ──┐
                           ▼
                  RssiFilterPipeline.filter()     중앙값 → 칼만 → 히스테리시스
                           │  정제된 값
                           ▼
                  PathTracker.feed()              (시각, 값) 버퍼에 쌓는다
                           ▼
                  PathTracker.evaluate()          ★ 여기서 전진/후퇴를 판정
                           │
              ┌────────────┴────────────┐
              │                         │
        전환이 있으면              항상 (표시용)
        guide 메시지 생성          snapshot() 을 payload 에 첨부
              │                         │
              ▼                         ▼
      _broadcast(전체)          _broadcast(보낸 쪽 제외)
              │                         │
              ▼                         ▼
       [폰이 TTS 로 읽음]         [/monitor 가 화면에 표시]
```

**두 브로드캐스트의 대상이 다른 게 핵심이다.**
RSSI 중계는 보낸 쪽(폰)을 뺀다 — 자기가 보낸 걸 되돌려받을 필요가 없으니까.
안내는 보낸 쪽을 포함한다 — 안내를 들어야 할 대상이 바로 그 폰이니까.

## 4. `app/ws/handler.py` — WebSocket 입구

### 4-1. 전역 상태 (11~22행)

```python
router = APIRouter()

_connections: set[WebSocket] = set()
_filters: dict[str, RssiFilterPipeline] = {}
_tracker = PathTracker()
```

세 개 다 **모듈 전역**이다. 의미를 알아두는 게 중요하다.

| 변수 | 내용 | 한계 |
|---|---|---|
| `_connections` | 지금 붙어 있는 모든 WebSocket | — |
| `_filters` | 비콘 키별 필터 상태 | **모든 접속자가 공유.** 두 사람이 동시에 붙으면 같은 비콘의 칼만 상태가 섞인다 |
| `_tracker` | 경로 추적기 | **전역 하나.** 동시에 두 명을 안내할 수 없다 |

이 한계는 Java 원본에서 그대로 넘어온 것이고, 실측 도구 수준에서는 문제가 없어서 두었다.

> **여기서 나온 적 있는 함정**: `_tracker` 가 전역이라 **브라우저를 새로고침해도 살아있다.**
> 그래서 예전에 화면은 "경로 등록 필요"라고 떠 있는데 음성 안내는 정상 작동하는 일이 있었다.
> 지금은 `snapshot()` 의 `enabled` 값을 화면이 받아서 동기화한다.

### 4-2. 경로 탐색 (25~64행)

```python
_APP_DIR = Path(__file__).resolve().parent          # backend-python/app/ws
_PROJECT_DIR = _APP_DIR.parents[1]                  # backend-python
_MONITOR_HTML_PATH = _APP_DIR / "monitor.html"

    _APP_DIR / "map-tool",

    if env:
        return Path(env).expanduser().resolve()
    for cand in _MAP_TOOL_CANDIDATES:

```

`backend-python` 과 `map-tool` 이 **다른 git 저장소**라서, 어떻게 clone 했느냐에 따라
상대 위치가 달라진다. 그래서 한 경로에 고정하지 않고 후보를 순서대로 뒤진다.
못 찾으면 첫 후보를 돌려주는데, 이건 실패를 숨기지 않고 **오류 메시지에 경로가 찍히게**
하려는 것이다.

`_map_tool_dir()` 은 캐시하지 않고 매번 다시 찾는다. 서버를 켠 뒤에 파일을 갖다 놔도
재시작 없이 잡히도록.

### 4-4. WebSocket 엔드포인트 (160~192행)

```python
@router.websocket("/ws")
async def websocket_endpoint(websocket: WebSocket):
    await websocket.accept()
    _connections.add(websocket)

    try:
        while True:
            raw = await websocket.receive_text()
            payload, guides = _process_message(raw)

            # RSSI/측정 메시지는 "보낸 쪽 제외" 브로드캐스트
            await _broadcast(payload, exclude=websocket)

            # 안내 메시지는 "보낸 쪽 포함" 전체
            for guide in guides:
                await _broadcast(json.dumps(guide, ensure_ascii=False))
    except WebSocketDisconnect:
        pass
    finally:
        _connections.discard(websocket)
```

**`_process_message()` 가 왜 두 개를 돌려주는지**가 여기서 드러난다.
브로드캐스트 대상이 다르기 때문에 한 덩어리로 합칠 수가 없다.

- `payload` (중계용) → `exclude=websocket`. 폰이 보낸 RSSI를 폰에 되돌려줄 필요가 없다
- `guides` (안내용) → 제외 없음. **안내를 들어야 할 대상이 그 폰이다**

`finally` 에서 반드시 `discard` 한다. 안 하면 끊긴 소켓이 `_connections` 에 남아
브로드캐스트마다 예외가 난다.

```python
async def _broadcast(payload: str, exclude=None) -> None:
    for conn in list(_connections):        # list() 로 복사 — 순회 중 변경 대비
        if exclude is not None and conn is exclude:
            continue
        try:
            await conn.send_text(payload)
        except Exception:
            pass   # 끊긴 연결은 무시하고 계속
```

`list(_connections)` 로 복사하는 이유: 전송 중에 다른 코루틴이 집합을 건드리면
"순회 중 크기 변경" 오류가 난다.

### 4-5. 메시지 분류 (297~314행)

```python
def _process_message(raw: str) -> tuple[str, list[dict]]:
    try:
        data: dict = json.loads(raw)
    except json.JSONDecodeError as e:
        return raw, []                      # 파싱 실패 → 원본 그대로 중계

    if isinstance(data, dict) and data.get("type") == _MEASURE_TYPE:   # "measure"
        return _process_control(data)

    if isinstance(data, dict) and data.get("type") == _GUIDE_TYPE:     # "guide"
        return _process_guide(data), []

    # 그 외는 전부 RSSI 데이터로 본다
```

**`type` 필드가 없으면 RSSI로 간주한다.** 안드로이드가 보내는 RSSI 메시지는
`{"MAC|이름": -67, "timestamp": ...}` 형태라 `type` 이 없기 때문이다.

파싱에 실패해도 예외로 끊지 않고 원본을 그대로 중계한다. 중계 자체는 살려두는 쪽이
현장에서 디버깅하기 낫다.

### 4-6. RSSI 처리 (316~357행) — 필터와 판정이 만나는 곳

```python
    try:
        filtered: dict = {"timestamp": data.get("timestamp", int(time.time() * 1000))}
        got_rssi = False

        for key, value in data.items():
            if key == "timestamp":
                continue
            if not isinstance(value, (int, float)) or isinstance(value, bool):
                continue

            rssi = float(value)
            if rssi >= 0 or rssi == 127:      # 0 이상이거나 127이면 무효값
                continue

            pipeline = _filters.setdefault(key, RssiFilterPipeline())
            filtered_rssi = pipeline.filter(rssi)
            rounded = round(filtered_rssi, 1)

            filtered[key] = rssi                  # 원본값
            filtered[f"{key}__f"] = rounded       # 필터값

            _tracker.feed(key, filtered_rssi)     # ★ 추적기에 먹인다
            got_rssi = True
```

한 줄씩 짚으면:

- `isinstance(value, bool)` 체크가 따로 있는 이유 — 파이썬에서 `bool` 은 `int` 의
  하위 타입이라 `isinstance(True, int)` 가 참이다. 빼주지 않으면 `True` 가 RSSI 1로
  들어간다
- `rssi >= 0 or rssi == 127` — RSSI는 음수여야 한다. **127은 안드로이드가 "값 없음"을
  나타낼 때 쓰는 값**이라 명시적으로 버린다
- `_filters.setdefault(key, RssiFilterPipeline())` — 비콘 키마다 **독립적인 필터
  인스턴스**를 만든다. 칼만 필터는 내부 상태를 갖기 때문에 절대 공유하면 안 된다
- **`_tracker.feed()` 에 넘기는 건 필터를 거친 값**(`filtered_rssi`)이지 원본이 아니다.
  판정은 항상 정제된 값 위에서 한다
- 화면에는 원본과 필터값을 **둘 다** 보낸다. 필터가 과하게 뭉개는지 눈으로 볼 수 있어야 하니까

```python
        guides: list[dict] = []
        if got_rssi:
            transition = _tracker.evaluate()      # ★ 판정
            if transition:
                guides.append(transition)

            snapshot = _tracker.snapshot()        # 표시용 상태
            if snapshot:
                filtered["_track"] = snapshot

        return json.dumps(filtered, ensure_ascii=False), guides
```

`evaluate()` 는 **RSSI가 하나라도 들어온 경우에만** 부른다(`got_rssi`).
빈 메시지나 잡음만 온 경우에 판정을 돌리면 스트릭 카운터가 헛돈다.

`snapshot()` 을 **별도 메시지로 안 보내고 RSSI payload 에 얹는** 이유가 두 가지 있다.

1. 메시지 수를 늘리지 않는다
2. 화면에 보이는 추세 값이 **항상 그 RSSI와 같은 시점**의 것이 된다

### 4-7. 측정 제어 (203~252행) — 안내를 켜고 끄는 곳

```python
_MEASURE_EVENTS = ("start", "mark", "end")

def _process_control(data: dict) -> tuple[str, list[dict]]:
    event = data.get("event")
    if event not in _MEASURE_EVENTS:
        return json.dumps({"type": "measure", "event": "error", ...}), []
```

**모르는 이벤트를 그냥 통과시키지 않고 `error` 로 바꿔서 보낸다.**
그대로 흘려보내면 화면이 낯선 이벤트를 측정 시작/종료로 착각할 수 있다.

```python
    guides: list[dict] = []
    if event == "start":
        started = _tracker.start_session()
        if started:
            guides.append(started)
    elif event == "end":
        ended = _tracker.end_session()
        if ended:
            guides.append(ended)
```

**여기가 "측정 시작" 버튼과 음성 안내를 잇는 유일한 지점이다.**
`mark` 는 아무것도 하지 않고 중계만 된다.

### 4-8. 경로 등록 (267~294행)

```python
def _process_guide(data: dict) -> str:
    event = data.get("event")

    if event == "setPath":
        path = data.get("path")
        if not isinstance(path, list):
            path = []
        result = _tracker.set_path(
            [str(p) for p in path],
            threshold=data.get("threshold"),
            min_next=data.get("minNext"),
            mode=data.get("mode"),
            window_ms=data.get("windowMs"),
            segments=data.get("segments"),
        )
        return json.dumps(result, ensure_ascii=False)

    if event == "stop":
        return json.dumps(_tracker.stop(), ensure_ascii=False)
```

파라미터(임계값·모드·창·구간)를 **전부 메시지로 받는다.** 그래서 서버를 재시작하지 않고
화면에서 값을 바꿔 실험할 수 있다. `None` 을 넘기면 `set_path()` 가 기존 값을 유지한다.

> **자주 헷갈리는 부분**: 파란 버튼(경로 등록 = `setPath`)과 초록 버튼(측정 시작 = `measure/start`)은
> **다른 메시지다.** 경로 등록만 하면 `enabled=True, active=False` 라 판정이 돌지 않는다.
> 측정을 시작해야 `active=True` 가 되면서 안내가 나간다.

## 5. `app/ws/rssi_filter.py` — 신호 정제 (73행 전문)

Java `RssiFilterPipeline` 을 그대로 옮긴 것. **중앙값 → 칼만 → 히스테리시스** 3단이다.

### 5-1. 상태값

```python
class BeaconState(str, Enum):
    ARRIVED = "ARRIVED"
    DEPARTED = "DEPARTED"
    STABLE = "STABLE"  # Java 원본에도 정의만 있고 실제로 안 쓰이는 값. 그대로 포팅.
```

`STABLE` 은 어디서도 대입되지 않는다. 원본과 대조하기 쉽도록 남겨뒀다.

### 5-2. 생성자

```python
class RssiFilterPipeline:
    MEDIAN_WINDOW = 3

    def __init__(self, q=0.008, r=4.0, entry_threshold=-65.0, exit_threshold=-75.0):
        self.q = q          # 프로세스 잡음 — 값이 클수록 필터가 빠르게 따라감
        self.r = r          # 측정 잡음   — 값이 클수록 새 측정값을 덜 믿음
        self.entry_threshold = entry_threshold   # 이보다 세면 "도착"
        self.exit_threshold = exit_threshold     # 이보다 약하면 "이탈"

        self.x = 0.0            # 추정값
        self.p = 1.0            # 추정 오차 공분산
        self.initialized = False
        self.state = BeaconState.DEPARTED
        self._median_buffer: deque[float] = deque()
```

`q = 0.008`, `r = 4.0` 이면 **비율이 1:500** 이라 상당히 무겁게 평활된다.
급변에 느리게 반응하는 대신 튀는 값에 강하다.

### 5-3. 파이프라인

```python
    def filter(self, measurement: float) -> float:
        median_filtered = self._apply_median_filter(measurement)
        kalman_filtered = self._apply_kalman_filter(median_filtered)
        self._apply_hysteresis(kalman_filtered)
        return kalman_filtered
```

**반환값은 칼만 결과다.** 히스테리시스는 `self.state` 만 바꾸고 반환값에 영향을 주지 않는다.
즉 판정에 쓰이는 값은 칼만 출력이고, `ARRIVED`/`DEPARTED` 는 표시용이다.

### 5-4. 중앙값 필터 — 순간적으로 튀는 값 제거

```python
    def _apply_median_filter(self, measurement: float) -> float:
        self._median_buffer.append(measurement)
        if len(self._median_buffer) > self.MEDIAN_WINDOW:
            self._median_buffer.popleft()
        if len(self._median_buffer) < 3:
            return measurement          # 아직 3개가 안 모이면 그대로 통과
        sorted_values = sorted(self._median_buffer)
        return sorted_values[len(sorted_values) // 2]
```

창이 3이라 **최근 3개 중 가운데 값**을 고른다. 평균이 아니라 중앙값인 이유는,
평균은 튄 값 하나에 통째로 끌려가지만 중앙값은 아예 무시하기 때문이다.

```
값: -67, -95, -68      평균 = -76.7 (튄 값에 오염)
                       중앙값 = -68  (튄 값 무시)  ← 이쪽을 쓴다
```

다만 3개 중 **2개가 같이 튀면 중앙값도 같이 튄다.** 창이 3이라 방어할 수 있는 건
"고립된 이상치 1개"까지다.

### 5-5. 칼만 필터 — 부드럽게 다듬기

```python
    def _apply_kalman_filter(self, measurement: float) -> float:
        if not self.initialized:
            self.x = measurement            # 첫 값을 그대로 초기 추정으로
            self.initialized = True
            return self.x
        self.p += self.q                    # 예측: 불확실성이 조금 커진다
        k = self.p / (self.p + self.r)      # 칼만 이득
        self.x = self.x + k * (measurement - self.x)   # 보정
        self.p = (1 - k) * self.p                      # 불확실성 감소
        return self.x
```

핵심은 `k` 다. **새 측정값을 얼마나 믿을지의 비율**이고 0~1 사이다.

```
k 가 크면  →  새 값을 많이 반영 → 빠르지만 흔들림
k 가 작으면 →  기존 추정 유지    → 안정적이지만 느림
```

`q=0.008, r=4.0` 이면 `p` 가 수렴한 뒤 `k` 는 대략 0.04 근처가 된다.
**새 측정값을 4%만 반영한다**는 뜻이라 꽤 둔하다.

> 이 둔함이 예전에 문제를 키운 적이 있다. 안드로이드가 누적된 `bleRssiMap` 전체를
> 매 스캔마다 보내던 버그가 있었는데, 같은 값이 반복 입력되니 칼만이 그 값에
> 완전히 수렴해버려서 정지 상태인데도 추세가 -4.68dB 로 나왔다.
> **필터가 무거우면 입력이 잘못됐을 때 그 오류에도 강하게 수렴한다.**

### 5-6. 히스테리시스 — 경계에서 깜빡이지 않게

```python
    def _apply_hysteresis(self, filtered_rssi: float) -> None:
        if self.state == BeaconState.ARRIVED:
            if filtered_rssi <= self.exit_threshold:      # -75
                self.state = BeaconState.DEPARTED
        else:
            self.state = (ARRIVED if filtered_rssi >= self.entry_threshold   # -65
                          else DEPARTED)
```

**들어가는 문턱(-65)과 나오는 문턱(-75)이 다르다.** 이 10dB 간격이 핵심이다.

```
        -65 ─────────────── 진입 문턱
             ↑         │
             │  10dB   │  이 구간에서는 상태가 안 바뀐다
             │         ↓
        -75 ─────────────── 이탈 문턱
```

문턱이 하나면 -65 근처에서 값이 미세하게 흔들릴 때마다 도착/이탈이 반복된다.
두 개로 벌려두면 한 번 도착한 뒤에는 -75까지 떨어져야 이탈로 바뀐다.

### 6-1. 상수 (19~59행)

```python

HISTORY_MAX = 40        # trend 모드가 보는 최근 샘플 수
FORWARD_STREAK = 2      # 전진은 2회 연속이어야 확정

DEFAULT_MIN_NEXT = -85.0    # 다음 비콘이 이보다 약하면 전진으로 안 침
```

**전진 2회, 후퇴 3회로 다르게 둔 이유**: 전진은 정상적인 진행이라 빠르게 반응해야 하고,
후퇴는 대개 신호 흔들림이지 실제로 되돌아간 게 아니라서 더 신중해야 한다.

```python

MODE_SEGMENT = "segment"

DEFAULT_WINDOW_MS = 2000
DEFAULT_SEGMENTS = 5
DEFAULT_SEGMENT_THRESHOLD = 2.5

BUFFER_MAX = 300
BUFFER_MAX_AGE_MS = 15000
```

**두 가지 판정 모드가 있다.**

| | `trend` (기존) | `segment` (구간 분할) |
|---|---|---|
| 창 기준 | **개수** (최근 40개) | **시간** (최근 2.0초) |
| 쓰는 샘플 | 40개 중 양끝 4+4 = 8개만 | 창 안의 **전부** |
| 계산 | 뒤 4개 평균 − 앞 4개 평균 | 5구간 평균 → 최소제곱 기울기 |

`trend` 의 약점 두 가지:

1. **32개를 버린다.** 40개 중 8개만 쓴다
2. **창이 개수 기준이라 실제 시간 폭이 들쭉날쭉하다.** 초당 10개가 들어오면 4초,
   초당 1개면 40초가 된다. 수신 속도가 변하면 판정 성격이 통째로 바뀐다

`segment` 는 창 안 모든 샘플을 쓰고, 구간 평균이 1차 평활 역할을 해서
BLE 광고 채널 전환으로 생기는 계단식 점프에 덜 흔들린다.

실측 4개 파일(정지 2, 이동 2)로 전수 비교한 결과:

```
trend    정지 오탐 1회,  최소 통과 시간 8초
segment  정지 오탐 0회,  최소 통과 시간 6초   (2.0초 / 5구간 / 임계 2.5dB)
```

`BUFFER_MAX = 300`, `BUFFER_MAX_AGE_MS = 15000` 은 시간 창을 쓰려면 개수 기준 40개로는
모자랄 수 있어서 넉넉히 잡은 것이다. `trend` 모드는 여전히 최근 40개만 보므로
동작이 바뀌지 않는다.

### 6-2. 헬퍼

```python
def short_name(key: str) -> str:
    """비콘 키는 "MAC|이름" 형태 — 안내 음성에는 이름만 쓴다."""
    if not key:
        return ""
    head, sep, tail = key.partition("|")
    return tail if sep else head
```

`partition` 은 `split` 과 달리 **구분자가 없어도 예외 없이 3개를 돌려준다.**
`sep` 이 빈 문자열이면 `|` 가 없었다는 뜻이라 `head`(=원본 전체)를 그대로 쓴다.

### 6-7. `feed()` — 데이터 수집 (209~215행)

```python
    def feed(self, key: str, filtered_rssi: float, now_ms: int | None = None) -> None:
        now = _now_ms() if now_ms is None else int(now_ms)
        buf = self.history.setdefault(key, [])
        buf.append((now, filtered_rssi))
        while buf and (len(buf) > BUFFER_MAX or now - buf[0][0] > BUFFER_MAX_AGE_MS):

```

**개수와 나이 둘 다로 정리한다.** 개수만 보면 데이터가 뜸하게 들어올 때 15초도 더 된
값이 남고, 나이만 보면 빠르게 들어올 때 메모리가 커진다.

`now_ms` 인자가 있는 이유: **평가 하네스가 CSV의 기록 시각을 그대로 넣어서 재생**할 수
있게 하기 위해서다. 실서비스에서는 `None` 이라 현재 시각을 쓴다.

### 6-8. `_trend_ends()` — 기존 추세 (224~234행)

```python
    def _trend_ends(self, key: str):
        buf = self.history.get(key)
        if not buf:
            return None
        vals = [v for _, v in buf][-HISTORY_MAX:]     # 최근 40개
        if len(vals) < TREND_WINDOW * 2:              # 8개 미만이면 판단 불가
            return None
        recent = sum(vals[-TREND_WINDOW:]) / TREND_WINDOW   # 뒤 4개 평균
        old = sum(vals[:TREND_WINDOW]) / TREND_WINDOW       # 앞 4개 평균
        return recent - old
```

**반환값은 dB 차이**다. 양수면 가까워지는 중, 음수면 멀어지는 중.

`len(vals) < TREND_WINDOW * 2` 체크가 없으면 앞 4개와 뒤 4개가 겹쳐서
추세가 항상 0에 가깝게 나온다.

### 6-9. `_trend_segment()` — 구간 분할 추세 (236~276행) ★

```python
    def _trend_segment(self, key: str):
        buf = self.history.get(key)
        if not buf:
            return None

        now = buf[-1][0]
        pts = [(t, v) for t, v in buf if now - t <= self.window_ms]
        if len(pts) < self.segments * 2:      # 구간당 최소 2개
            return None
```

**시간 창으로 자른다.** `now` 는 현재 시각이 아니라 **마지막 수신 시각**이다.
데이터가 끊겼을 때 창이 통째로 비는 것을 막는다.

```python
        t0, t1 = pts[0][0], pts[-1][0]
        if t1 == t0:
            return None

        buckets: list[list[float]] = [[] for _ in range(self.segments)]
        for t, v in pts:
            idx = int((t - t0) / (t1 - t0 + 1) * self.segments)
            buckets[min(self.segments - 1, idx)].append(v)
```

시간 비율로 구간을 나눈다. `+1` 은 **0으로 나누기 방지**이고,
`min(self.segments - 1, idx)` 는 마지막 점(비율 1.0)이 범위를 벗어나는 것을 막는다.

**개수가 아니라 시간으로 나누는 게 중요하다.** 개수로 나누면 수신이 뜸했던 구간과
촘촘했던 구간이 같은 비중을 갖게 된다.

```python
        means = [(i, sum(b) / len(b)) for i, b in enumerate(buckets) if b]
        if len(means) < 2:
            return None
```

빈 구간은 버린다(`if b`). 그래서 `means` 의 인덱스가 0,1,2,3,4 가 아닐 수 있다 —
예를 들어 2번 구간에 데이터가 없으면 `[(0,..), (1,..), (3,..), (4,..)]` 가 된다.
**그래서 기울기를 구할 때 인덱스를 그대로 x값으로 쓴다.**

```python
        n = len(means)
        mean_i = sum(i for i, _ in means) / n
        mean_v = sum(v for _, v in means) / n
        den = sum((i - mean_i) ** 2 for i, _ in means)
        if den == 0:
            return None
        slope = sum((i - mean_i) * (v - mean_v) for i, v in means) / den

        return slope * (means[-1][0] - means[0][0])
```

표준 최소제곱 직선 맞춤이다.

```
slope = Σ(xᵢ - x̄)(yᵢ - ȳ) / Σ(xᵢ - x̄)²
```

`den == 0` 은 구간이 하나뿐일 때인데, 위에서 이미 걸렀으니 방어 코드다.

**마지막 줄이 핵심이다.** 기울기는 "구간 하나당 dB 변화"인데, 이걸 그대로 쓰면
구간 수를 바꿀 때마다 임계값도 바꿔야 한다. 그래서 **창 전체에 걸친 변화량(dB)으로
환산**한다. 덕분에 `trend` 모드와 같은 임계값 단위(dB)를 쓸 수 있다.

#### 숫자로 따라가보기

창 2.0초, 5구간, 초당 10개 수신이라면:

```
20개 샘플 → 5구간 → 구간당 4개
구간 평균: [-77.2, -75.8, -74.1, -72.5, -70.9]

x̄ = 2,  ȳ = -74.1
slope = ((0-2)(-3.1) + (1-2)(-1.7) + 0 + (3-2)(1.6) + (4-2)(3.2)) / (4+1+0+1+4)
      = (6.2 + 1.7 + 0 + 1.6 + 6.4) / 10 = 1.59  (구간당 dB)

반환값 = 1.59 × (4 - 0) = 6.36 dB   ← 창 2초 동안 6.36dB 가까워졌다
```

임계 2.5dB를 넘으므로 "가까워지는 중"으로 판정된다.

#### 전진 조건 (307~327행)


네 조건을 **모두** 만족해야 한다. 각각이 막아주는 상황이 다르다.

| 조건 | 막아주는 것 |
|---|---|
| ① 다음이 가까워짐 | 그냥 현재에서 멀어지기만 하는 경우(옆길로 샘) |
| ② 현재가 멀어짐 | 제자리에서 신호만 좋아진 경우 |
| ③ 절대값 하한(-85) | 아주 멀리 있는 비콘이 조금 세진 것으로 전진 판정되는 것 |
| ④ 다음 > 현재 | **추세만 보고 판정하는 것.** 직관적으로 더 가까운 비콘이 따로 있는데도 추세만으로 넘어가는 문제를 막는다 |

> 엉뚱한 데로 넘어가는" 문제가 실제로 관측돼서 넣었다.

**스트릭이 조건을 만족 못 하면 초기화되지 않는다는 점**에 주의. 이 블록은
조건을 만족했을 때만 `forward_streak += 1` 하고, 만족하지 못하면 아래로 흘러가
후퇴 조건을 검사한 뒤 마지막에 둘 다 0이 된다.

### 7-2. 정답 만들기

```python
def ground_truth(by: dict, path: list[str]) -> list[tuple[float, int]]:
    """1초 구간마다 가장 센 비콘을 구하고, 그게 바뀌는 순간을 전환으로 본다."""
    end = max(v[-1][0] for v in by.values())
    switches, prev = [], None
    for t0 in range(0, end + GROUND_TRUTH_BIN_MS, GROUND_TRUTH_BIN_MS):
        means = {}
        for i, k in enumerate(path):
            win = [v for t, v in by[k] if t0 <= t < t0 + GROUND_TRUTH_BIN_MS]
            if win:
                means[i + 1] = sum(win) / len(win)
        if not means:
            continue
        best = max(means, key=means.get)
        if prev is not None and best != prev:
            switches.append((t0 / 1000, best))
        prev = best
    return switches
```

정답 라벨이 따로 없으니 **"1초 단위로 가장 센 비콘이 바뀌는 지점"** 을 정답으로 삼는다.
완벽한 기준은 아니지만, 판정 알고리즘과 독립적이라 비교 기준으로는 쓸 만하다.

### 7-3. 채점

```python
def score_moving(events, truth):
    """실제 전환마다 같은 번호의 판정을 하나씩 짝지어 지연을 잰다."""
    used, lags = set(), []
    for t_true, num in truth:
        cand = [(i, e) for i, e in enumerate(events)
                if i not in used and e[1] == num and e[0] >= t_true - MATCH_TOLERANCE_S]
        if cand:
            used.add(cand[0][0])
            lags.append(cand[0][1][0] - t_true)
    return len(used), len(events) - len(used), lags
```

`used` 로 **한 번 짝지은 이벤트를 재사용하지 않는다.** 이게 없으면 같은 판정 하나가
여러 정답에 중복으로 매칭돼서 점수가 부풀려진다.

`MATCH_TOLERANCE_S = 2.0` — 정답보다 최대 2초 **앞선** 판정까지는 같은 전환으로 인정한다.
1초 구간 기준이라 정답 자체에 오차가 있기 때문이다.

반환값은 `(매칭, 초과, 지연목록)`. **초과(extra)는 정답에 없는데 나온 판정** = 오탐이다.

경로 등록만 하면 히스토리는 쌓이지만 `evaluate()` 가 첫 줄에서 바로 돌아간다.

**Q. 왜 파란 버튼을 안 눌렀는데 안내가 나오지?**

`_tracker` 가 **모듈 전역**이라 브라우저를 새로고침해도 서버 쪽 경로가 살아있기 때문이다.
이전에 등록한 경로가 그대로 남아 있는 것이다.

**Q. 판정은 어디서 하나? 화면도 하나?**

**서버에서만 한다.** `/monitor` 는 `snapshot()` 이 실어 보낸 값을 표시만 한다.
예전에는 JS에도 같은 로직이 있었는데, 서버와 결과가 어긋날 수 있어서 서버로 일원화했다.

**Q. 비콘과 비콘 사이에 멈춰 서면?**

창 길이만큼(2.0초) 지난 뒤에 판정된다. 추세가 임계값을 못 넘으면 "유지" 상태로 남는다.

**Q. `trend` 와 `segment` 중 지금 뭐가 기본인가?**

코드상 `DEFAULT_MODE = MODE_TREND` 지만, 화면에서 모드를 골라 `setPath` 로 보내면
그 값이 적용된다. 실측 비교에서는 `segment` 가 더 좋았다.

**Q. 필터값과 원본값 중 판정에 쓰이는 건?**

**필터값**(`RssiFilterPipeline.filter()` 의 반환값 = 칼만 출력)이다.
화면에는 둘 다 보내지만 `_tracker.feed()` 에 들어가는 건 필터값 하나다.
