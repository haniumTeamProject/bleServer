## 1. 출발 문구 — 벽을 짚으라는 말이 안 맞는 자리

### 1.1 첫 안내가 횡단이면 벽 짚기를 뺀다

`"손이 닿는 벽을 짚고 걸어주세요."` 바로 뒤에 `"벽이 끊깁니다. 손을 떼고 직진하세요."`
가 이어지면 **두 지시가 맞부딪힌다.** 화면을 볼 수 없는 사용자는 되물을 수도 없어서
어느 쪽을 따라야 하는지 그 자리에서 판단해야 한다.

```python
_NO_WALL_START = ("crossEnter", "crossExit", "cross", "connectorExit")
```

출발 칸의 **첫** 안내가 이 종류면 첫 구간이라도 벽 짚기를 뺀다. `cross` 는
`merge_crossing` 이 진입·도달을 한 문장으로 합쳤을 때의 종류다. 회전·직진은 벽을 짚은
채로 하는 일이라 그대로 둔다.

### 1.2 출발 문구가 네 갈래가 됐다

위에서부터 먼저 걸리는 것을 쓴다.

```
연결자에서 출발   407로 계속 안내합니다. 엘리베이터에서 나와 왼쪽 벽을 짚고 직진하세요.
두 번째 구간      407로 계속 안내합니다.
첫 안내가 횡단    407로 안내합니다.
평소             407로 안내합니다. 손이 닿는 벽을 짚고 걸어주세요.
```

**연결자를 맨 위에 둔 이유** — 엘리베이터에서 내려 시작하는 것은 대개 두 번째 구간이라,
`first_leg` 를 먼저 보면 `"계속 안내합니다"` 만 나가고 정작 지금 막 내린 사람에게 어느
벽을 짚어야 하는지는 아무도 안 알려준다. 앞머리(`안내합니다` / `계속 안내합니다`)는
구간 번호가 그대로 정한다.

### 1.3 왜 그 문장을 골랐는지 로그에 남긴다

문구가 빠지면 "왜 안 나오지"를 로그 없이는 알 수 없고, **빠지는 게 맞는데 틀린 줄 알고
고치면 더 나빠진다.** 실제로 이 로그가 없어서 한 번 헛짚었다.

```
[nav s-xxxx] 출발 문구 — 연결자 (1번칸 ['turn'])
[nav s-xxxx] 출발 문구 — 평소 (1번칸 안내 없음)
```

## 2. 수직연결자 출발 안내

### 2.1 좌우를 무엇으로 정하나 — `side_from_connector()`

"왼쪽 벽을 짚으세요"의 왼쪽은 **사용자가 지금 향한 쪽** 기준이다. 막 내린 사람이 향한
쪽은 문에서 복도로 나오는 방향이다.

```
f = 첫 경로노드 - 연결자       엘리베이터에서 나오면서 향하는 방향
v = 다음 노드 - 첫 경로노드     이제 가야 하는 방향
```

`f` 를 기준으로 `v` 가 어느 쪽으로 벌어지는지가 답이다. 화면 좌표라 y 가 아래로
증가하므로 `cross > 0` 이 오른쪽이다(`turn_at` 과 같은 규칙).

**한때 첫 회전 방향을 썼는데 근거가 약해서 버렸다.** 30m 앞의 코너가 왼쪽이라고 해서
지금 짚을 벽이 왼쪽이라는 보장이 없다. 이쪽은 지금 서 있는 자리의 기하다.

벌어진 각이 30도 미만(곧장 앞)이거나 연결자 좌표가 첫 노드 위에 찍혀 있으면 **방향을
빼고** `"벽을 짚고 직진하세요"` 만 말한다. 모르는 쪽을 찍으면 반대편 벽으로 걸어간다.

### 2.2 문구를 진입·도달로 나눴다

```
평소     벽이 끊깁니다. 손을 떼고 직진하세요.              (6)
        벽이 끊깁니다. 벽에 도달하면 오른쪽으로 꺾으세요.    (7)

연결자   엘리베이터를 등지고 곧장 걸어가세요.               (8)
        벽이 나오면 오른쪽으로 꺾으세요.                   (7)
```

처음에는 한 문장으로 합쳐 뒀는데 **시점이 다르다.** "등지고 걸어가세요"는 지금 할 일이고
"벽이 나오면 꺾으세요"는 건너편에 닿아서 할 일이라, 붙여 말하면 20m 앞의 회전을 지금
하라는 말로 들린다.

도달은 `crossExit` 를 그대로 쓴다 — 배정·여유(`LEAD_CROSS_M`)가 평소 횡단과 같고, 앞이
`crossEnter` 가 아니라 `merge_crossing` 이 이 짝은 안 건드린다.

조사는 받침으로 가린다(`_eul_reul`) — 엘리베이터**를** / 계단**을**.

### 2.3 대치 조건 — `i == 0` 으로 되돌렸다

첫 실측에서 로그에는 `엘리베이터 2호기에서 출발` 이 찍히는데 말은 `벽이 끊깁니다` 가
나갔다. 조건이 `i == 0`(첫 경로노드) 이라 횡단이 두어 노드 뒤에서 시작하면 안 걸렸다.

**그래서 `not cues`(앞에 다른 사건이 없으면)로 넓혔다가 다시 되돌렸다.** 사건이 없어도
노드를 몇 개 지났으면 그동안 벽을 따라 걸은 것이고, 그 사람에게 "엘리베이터를 등지고"는
이미 지나간 기준점이다 — 등질 엘리베이터가 등 뒤에 없다.

첫 노드에서 바로 건너는 경우에만 사용자가 아직 문 앞에 서 있다. 노드를 지나고 나서
만나는 횡단은 평소 문구가 맞고, 벽을 짚기 시작하라는 안내는 **출발 문장**이 따로 한다.

두 갈래가 갈라지지 않게 `_connector_opening()` 은 조건을 다시 적지 않고
**`connectorExit` 가 실제로 만들어졌는지**를 본다.

## 3. 직진 안내

### 3.1 겹치면 물러난다 — `shift_straight()`

```
조금 뒤 벽을 따라 오른쪽으로 꺾으세요. 계속 직진하세요.
```

꺾으라는 건지 직진하라는 건지 부딪힌다. 직진 안내는 셋 중 **가장 덜 급하다** — 회전·횡단은
놓치면 길을 잃지만 직진은 놓쳐도 하던 대로 걸으면 된다. 그래서 이쪽이 물러난다.

| 다음 칸 | 처리 |
| --- | --- |
| 비어 있다 | 거기로 옮긴다 |
| 안내가 있다(직진이든 아니든) | 버린다 |
| 없다(마지막 칸) | 버린다 |

**한 칸만 본다.** 계속 밀면 원래 알리려던 구간을 다 지나고 나서 나온다 — 그럴 바에는
안 하는 것이 낫다. 마지막 칸은 도착 안내가 있어 자연히 버려진다.

버린 개수는 로그에 `겹친 직진 N개 버림` 으로 남는다.

### 3.2 통째로 끄는 스위치

`EMIT_STRAIGHT = False` 로 두면 직진 안내가 아예 안 나간다. **꺼도 `runs` 는 그대로
계산해서** 다른 안내 위치가 안 흔들린다 — 껐다 켜도 비교가 되어야 하기 때문이다.

## 4. 경로 만들기 — 물리적으로 불가능한 길이 나오던 것

### 4.1 벽을 뚫는 건너기 — `_segment_walkable()`

실측 4층 B1→402 경로가 **계단실을 가로질러** 그려졌다. 축도 맞고 길이도 12m 안이라
기존 검사를 전부 통과했다.

맞은편 지점은 `_cast_to_wall` 로 찾으므로 **찾는 순간에는** 벽을 안 뚫는다. 문제는 그
뒤에 점이 두 번 움직인다는 것이다.

```
1. _snap_facing_to_wall   단순화된 벽선 위로 당김
2. find_or_insert         MERGE_RADIUS_PX 안의 기존 노드에 흡수
```

옮겨진 끝점끼리 이으면 처음 쐈던 선이 아니다. 그래서 간선을 만들기 직전에 실제로
걸어본다. 양 끝은 벽선 위로 당겨져 있어 그 픽셀 자체가 통행영역 밖으로 찍히는 것이
정상이므로 **사이만** 본다.

### 4.2 남의 목적지 앞을 지름길로 가로지르던 것 — `cross_edge_usable()`

관리자웹 `pathfind.ts` 의 `isCrossEdgeUsable` 이 **서버에만 빠져 있었다.**

```python
def cross_edge_usable(node_type, node_id, start_id) -> bool:
    return node_type not in ("landmark", "connector") or node_id == start_id
```

건너기 안내는 "**여기서 출발해** 반대편으로 건너세요"라는 말이다. 그 시작점이 남의
목적지나 연결자 앞이면, 거기 있지도 않은 사람에게 그 문 앞에서 건너라고 말하는 셈이다.
코너는 실제 출입구가 아니라 벽 모양이 만든 점이라 제약이 없다.

`find_node_path`(실제 안내)와 `find_shortest_path`(TS 대조용) **둘 다**에 넣었고,
후자는 아직 양방향이던 것도 `if not directed` 로 맞췄다.

> **테스트가 못 잡은 이유** — 픽스처 생성기가 노드의 `type` 과 엣지의 `directed` 를
> **빼고** 저장해서 두 규칙이 모두 무력화된 채 통과했다. 지금은 필드가 없으면 원본 TS
> 와 똑같이 통과시킨다(`undefined !== 'landmark'`). 픽스처 생성기를 고쳐야 앞으로 이
> 종류가 잡힌다 — **WEB-FE 쪽이라 아직 안 했다.**

## 5. 경로에 어느 비콘을 세우나

### 5.1 1등만 고르던 것 — `_seq_approach()`

넓은 홀에서 **가운데 비콘 넷이 통째로 빠졌다.** 반경을 12m 로 키워도 그대로였다.

옛 방식은 표본마다 **반경 안 1등 하나**를 고르고 직전과 같으면 접었다. 그러면 어느
표본에서도 1등을 못 하는 비콘은 영원히 안 들어온다. 경로는 벽을 따라 도는데 비콘이 홀
한가운데 있으면 구조적으로 그렇게 된다.

```
표본 위치   가장 가까운 셋
x=  0px    B1:1.0m   B2:10.0m   T1:11.7m
x=200px    B2:1.0m   T1: 6.0m   B1:10.0m      ← T1 이 2등, 한 번도 1등이 아니다

[옛 방식]   3m → B1 B2 B3 B4    8m → B1 B2 B3 B4        ← 키워도 그대로
[지금]      3m → B1 B2 B3 B4    8m → B1 B2 T1 B3 T2 B4
```

지금은 비콘마다 **반경 안에 들어와 있던 구간**을 끊어서, 그 구간의 최근접 표본을 그
칸으로 삼고 지나는 순서대로 늘어놓는다.

**왕복은 그대로 두 번 센다.** 처음에 전체 최소 하나만 잡았다가 기존 테스트
(`왕복에서 연속이 아닌 재방문은 남긴다`)가 깨져서 구간 단위로 다시 짰다.

되돌리려면 `BEACON_PICK=nearest`.

### 5.2 반경을 층마다 다르게

좁은 복도(4층 실측 3.0m)와 넓은 홀은 **정반대 문제**라 한 값으로 둘 다 맞출 수 없다.
복도에서 키우면 옆 복도 비콘이 딸려 들어오고, 홀에서 줄이면 가운데가 사라진다.

```
BEACON_MATCH_RADIUS_M=3.0                              전역 기본
BEACON_MATCH_RADIUS_BY_FLOOR="<층id>=8.0,<층id2>=2.5"    층별
```

안 적은 층은 예전 그대로 3.0m 다. **값을 안 쓰면 아무것도 안 달라진다.** 적용된 값은
경로 로그에 `반경 8.0m` 로 남는다. 오타가 있으면 그 항목만 무시하고 로그를 남긴다 —
오타 하나로 안내 전체가 죽으면 안 된다.

> **§5.1 과 §5.2 는 같이 써야 한다.** 규칙만 바꾸고 반경이 3m 면 홀 가운데는 여전히
> 안 들어온다.

## 6. 그 밖에 고친 것

### 6.1 연결자 목적지가 `/monitor` 에서 언제나 실패하던 것

```
목적지를 DB 에서 찾을 수 없습니다: c611f077-...
```

`handler._attach_route` 가 `plan_route` 에 **`floor_id` 를 안 넘기고 있었다.** 그러면
`landmarks` 테이블에서 층을 읽는데 **연결자는 그 테이블에 없다** — `connectors` 라는
다른 표에 있고 `DbMapSource.landmarks()` 가 조회할 때만 합쳐서 내보낸다.

방 번호는 landmarks 에 있어서 멀쩡히 됐고 연결자만 100% 죽어서, 목적지 해석이 잘못된
것처럼 보였다. `floor_id=_current_floor_id()` 한 줄.

> **폰 쪽 갈래는 아직이다.** `_plan_legs` 가 `session.floor_id is None` 일 때
> `Leg(floor_id="")` 를 만들고 그것이 `or None` 으로 떨어져 같은 에러가 난다. 층 확정
> 전에 연결자를 고르면 폰에서도 재현된다. **§8 참고.**

### 6.2 재연결 시 같은 문장이 세 번 나가던 것

실측 로그에서 한 소켓이 1초 안에 세 번 말했다 — 셋이 서로 다른 경로라 서로가 뭘
말했는지 모른다.

```
→ ready   말="목적지를 말씀해 주세요." 마이크엶      navigation_endpoint
→ resume  말="목적지를 말씀해 주세요." 마이크엶      on_resume     ← 뺐다
→ list    말="목적지를 말씀해 주세요." 마이크엶      on_beacons
```

`on_resume` 은 **소켓이 열린 뒤에만** 불리고, 그 소켓은 열리는 순간 이미 같은 문장을
보냈다. 즉 이 문장은 언제나 중복이고 단독으로 나가는 경우가 없다. `listenAfter` 는
그대로 뒀다 — 말은 안 해도 마이크는 열려 있어야 한다.

> `ready` 와 `list` 의 중복은 **아직 남아 있다.** 둘 중 하나를 지우려면 "hello 가 실제로
> 들리는가"를 알아야 하는데, 코드 주석은 *"화면이 아직 안 붙어 있어 허공으로 날아간다"*
> 고 하고 실제 증상은 *들린다* 라 어긋난다. 확인 없이 지우면 무음이 될 수 있다.

### 6.4 두 번 두드리면 지금 칸의 안내를 읽는다 (APP-FE)

`NavigationFragment` 에 `lastGuidance` 를 두고 **idle 이 아닌 메시지마다 덮어쓴다.
`utterance` 가 null 이면 지운다** — 그게 핵심이다. 안내가 없는 칸은 서버가 무음으로
내려보내는데, 그때 앞 값을 두면 두드렸을 때 **이미 지나온 칸의 지시**가 나온다.

`speech.replayLast()` 를 안 쓴다. 그쪽은 "마지막으로 **말한** 문장"이라 이 칸과 무관한
것이 나온다. 할 말이 없으면 진동만 하고 만다.

화면 문장과 상자 색도 같이 되돌린다 — 소리만 되돌리면 "안내를 계속할까요?"가 화면에
남아 말과 화면이 서로 다른 것을 가리킨다. 진행 점·단계는 idle 메시지의 `screen` 이
null 이라 원래 안 바뀐다.

## 8. 아직 안 한 것

### 8.1 손이 필요한 것 (승인 대기)

| 무엇 | 어디 | 왜 아직 |
| --- | --- | --- |
| 벽 뚫는 건너기 막기 | `WEB-FE/pathNodes.ts:738` | WEB-FE 수정이라 승인 필요. **안 하면 재생성할 때 같은 간선이 또 들어간다** |
| 픽스처에 `type`·`directed` 담기 | WEB-FE 하네스 | 이게 없으면 §4.2 종류를 테스트가 영영 못 잡는다 |
| TTS 를 `USAGE_MEDIA` 로 | `APP-FE/SpeechOutput.kt` | 화면 녹화에 TTS 가 안 담김. 안드로이드가 `USAGE_ASSISTANCE_ACCESSIBILITY` 를 재생 캡처에서 제외하기 때문. 운영은 `ACCESSIBILITY` 가 맞아서 `BuildConfig.DEBUG` 로 갈라야 함 |
| 저장된 경로노드 지우기 | DB `floor_path_nodes` | 저장된 층은 §4.1 이 안 걸린다 |

### 8.2 원인을 아직 못 좁힌 것

- **TTS 가 문장 도중 끊기고 처음부터 다시 읽힌다.** 서버는 `start` 를 한 번만 보냈고 앱
  코드에서 같은 문장을 두 번 부르는 곳은 없다. TalkBack 을 끄고도 재현되므로 남은 후보는
  **흔들기 오검출**(`SHAKE_THRESHOLD_G = 2.4f`, `MIN_INTERVAL_MS = 1500`)이다. `replay()`
  가 `QUEUE_FLUSH` 로 말해서 증상이 정확히 "끊기고 처음부터"다. 폰을 책상에 놓고 재현
  되는지 보면 갈린다. 완화는 임계값을 3.0 으로 올리는 한 줄.
- **B3 이후 판정이 안 된다**던 건은 CSV 재생으로는 재현이 안 됐다. 어떤 설정·어떤 경로
  모양으로 돌려도 1→2→3→4→5→6→7 로 넘어간다. 실제 경로·판정설정이 든 **JSON 사이드카**가
  있어야 좁힐 수 있다.

### 8.3 알고 두는 것

- `ready` 와 `list` 의 중복 발화 (§6.2)
- 폰에서 층 확정 전 연결자 목적지 (§6.1)
- 세션이 겹칠 때(폰이 이전 소켓을 닫기 전에 새로 붙음) 같은 말이 두 갈래로 나감 —
  서버가 기기별로 세션을 묶어야 하는 일이라 작은 수정이 아니다
- `nav_recorder` 가 발화 시점·배정 설정을 기록 안 함 — 녹화로 안내 타이밍을 재현 못 함
- `setTuning` 이 `_TUNING_FIELDS` 15개 중 7개만 받음
- DB 비콘 이름이 들쭉날쭉 (minor 3·4 는 이름 없음, 8~11 은 `B8` 이 아니라 `8`)
