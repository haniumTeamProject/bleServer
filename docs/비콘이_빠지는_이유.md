# 경로에 비콘이 몇 개만 잡히는 이유

관리자웹 지도에서 경로를 그렸는데 비콘이 B1~B4 넷만 서는 일이 있었다.
경로 노드는 촘촘한데 왜 그러는지 찾은 기록이다.

정리 시점: 2026-08-31

---

## 0. 결론부터

**반경이다.** `BEACON_MATCH_RADIUS_M = 3.0` (미터).

경로에서 3m 넘게 떨어진 비콘은 **하나도 안 들어온다.** 좁은 복도에서는 맞는
값이지만 넓은 홀에서는 경로가 벽을 따라 도는 사이 가운데 비콘이 통째로 빠진다.

실측 4층 한 경로에서 **29개가 이 이유로 빠지고 있었다.**

```
[경로] 반경(3.0m) 밖이라 뺀 비콘 29개 — B31 4.0m, B6 8.1m, B4 9.6m, B18 12.5m …
```

`B31` 은 4.0m 다. **1m 차이로 빠졌다.**

---

## 1. 어떻게 고르나

`route_engine._seq_approach`.

```
경로를 1m 간격으로 훑는다
비콘마다 그 표본들과의 거리를 잰다
가장 가까워진 거리가 반경 안이면 경로에 세운다
```

노드 사이는 표본으로 메우므로 **긴 복도에서 비콘이 빠지는 문제는 없다.**
빠지는 이유는 오직 하나, 옆으로 멀어서다.

경로 노드를 아무리 촘촘히 찍어도 안 달라진다. 노드는 경로의 **모양**을 정할
뿐이고, 비콘은 그 모양에서 옆으로 얼마나 떨어졌는지로 걸러진다.

---

## 2. 층마다 다른 값을 줄 수 있다

`.env` 에 적는다. **안 적은 층은 3.0m 그대로**라 안전하다.

```
BEACON_MATCH_RADIUS_M=3.0
BEACON_MATCH_RADIUS_BY_FLOOR=<층id>=8.0,<다른층id>=2.5
```

층 id 는 관리자웹 주소나 `/map-db` 응답에서 볼 수 있다.

### 넓히면 잃는 것

**경로에 세운다고 폰이 그 비콘을 가장 세게 잡는다는 보장은 없다.**
걷는 내내 한 번도 1등을 못 하는 비콘이 경로에 끼면 **추적기가 그 칸에서 멈춘다.**
실측 4층 B7 이 그랬다.

그래서 무작정 키우면 안 되고, 넓힌 층은 `/monitor` 로 그 칸을 실제로 넘어가는지
봐야 한다.

## 3. 같은 비콘이 연속으로 나오던 것 (수정함)

반경 언저리를 스치는 비콘은 한 번 지나가는데도 통과 구간이 둘로 쪼개진다 —
들어왔다, 잠깐 나갔다, 다시 들어옴. 그러면 경로에 이런 것이 생겼다.

```
… → B11 → B12 → B12 → B25 → …
```

보기 나쁜 정도가 아니다. **안내가 그 칸에서 영원히 멈춘다.** 추적기는 "다음 칸
비콘이 지금 것보다 세졌나"로 넘어가는데, 둘이 같은 비콘이면 성립할 수가 없다.

바로 옆에 같은 비콘이 오면 접는다. 사이에 다른 비콘이 낀 재방문
(`B17 → B15 → B17`)은 그대로 둔다 — 그건 실제로 두 번 지나가는 것이고,
접으면 왕복 경로의 뒷부분이 통째로 사라진다.

`tests/test_route_from_db.py` 의 "같은 비콘이 연속으로 나오지 않는다"가
이걸 잡는다.

## 4. 왜 빠졌는지 이제 로그에 찍힌다

경로를 만들 때마다 한 줄 나온다.

```
[경로] 반경(3.0m) 밖이라 뺀 비콘 29개 — B31 4.0m, B6 8.1m, B4 9.6m …
```

가까운 순으로 여섯 개까지. 이걸 보면 두 가지가 바로 갈린다.

```
4~6m 짜리가 여럿    반경 문제다. 그 층만 넓히면 된다
20m 넘는 것이 섞임  좌표가 이상하다. 관리자웹에서 그 비콘 위치를 확인
```

## 5. 그 밖에 의심할 것

### minor 중복

같은 층에 `minor` 가 겹치면 추적 키(`major-minor`)가 같아져서 **두 비콘이 한
칸으로 합쳐진다.** 경로가 짧아 보이는 원인이 될 수 있다.

```sql
SELECT floor_id, major, minor, count(*), array_agg(name)
FROM beacons GROUP BY floor_id, major, minor HAVING count(*) > 1;
```

### major 가 층과 안 맞음

```sql
SELECT b.name, b.major AS 비콘, f.major AS 층, f.floor
FROM beacons b JOIN floors f ON f.id = b.floor_id
WHERE b.major IS DISTINCT FROM f.major;
```

### 좌표가 비었거나 0

```sql
SELECT id, name, x, y FROM beacons
WHERE x IS NULL OR y IS NULL OR (x = 0 AND y = 0);
```

### 층에 비콘이 몇 개인가

```sql
SELECT f.floor, count(b.id) AS 비콘, count(*) FILTER (WHERE b.type = 'semantic') AS 의미,
       count(*) FILTER (WHERE b.type = 'reinforcement') AS 보강
FROM floors f LEFT JOIN beacons b ON b.floor_id = f.id
GROUP BY f.id, f.floor ORDER BY f.floor;
```

## 6. 아직 안 고친 것

`tests/test_path_nodes.py` 의 **"연결 수" 149 / 151** 이 실패한다.

`path_nodes._segment_walkable()` 이 벽을 뚫는 건너기 두 개를 막으면서 생긴
차이다. 막는 것 자체는 맞는데, **관리자웹은 아직 그 두 엣지를 그린다.**
화면에 보이는 경로와 안내에 쓰는 경로가 그만큼 갈라져 있다.

둘 중 하나를 해야 한다.

```
WEB-FE 에도 같은 검사를 넣는다          맞추는 쪽
픽스처를 149 로 갱신하고 차이를 적는다   서버가 옳다고 인정하는 쪽
```
