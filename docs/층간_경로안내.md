# 층을 넘는 경로 안내

목적지가 다른 층일 때 무슨 일이 일어나는지 전부 적는다.

한 줄로 줄이면 이렇다.

    한 층짜리 안내를 두 번 돌린다. 사용자에게는 한 번으로 보인다.

---

## 1. 왜 이렇게 하나

### 1.1 층 그래프를 합치지 않는 이유

층마다 경로 그래프가 따로 있다. 이걸 하나로 이어붙이고 계단을 엣지 하나로 두면
다익스트라 한 번으로 끝난다. 그렇게 하지 않았다.

**거리가 뜻을 잃는다.** 안내 문구가 "지금 할 일"과 "조금 뒤에 할 일"을 가르는
기준(`cues.lead_phrase`)은 바닥을 걷는 거리다. 그 안에 계단이 섞이면 몇 걸음이면
되는 것을 "조금 뒤"라 하고 그 반대도 된다 — 수식이 통째로 거짓말이 된다.

**신호가 실제로 끊긴다.** 층을 옮기는 동안 출발 층 비콘은 죽고 도착 층 비콘은
아직 안 잡힌다. 한 경로로 이어두면 그 구간에서 `PathTracker` 가 후퇴를 잡아
"경로를 벗어났습니다"를 내보낸다. 실제로 이탈한 것이 아닌데 그렇게 읽힌다.

### 1.2 그래서 나눈다

```
1층에서 407호(4층)로

  ①  지금 비콘 → 계단1        1층 안내. 계단1을 목적지처럼 다룬다
  ②  (신호 끊김)              층 이동 중. 판정을 멈추고 기다린다
  ③  4층 비콘 잡힘            major 가 바뀌는 것으로 안다
  ④  그 비콘 → 407호          4층 안내. ①과 같은 코드
```

①과 ④는 **완전히 같은 일**이다. `plan_route` 도 `PathTracker` 도 `cues` 도
"한 층 + 출발 비콘 + 목적지" 하나만 알면 되게 되어 있어서, 위에 구간 목록 하나만
얹으면 아래는 손대지 않아도 된다.

## 2. 사용자에게는 한 번이다

**`arrived` 는 최종 목적지에서 딱 한 번 나간다.** 계단1에 닿은 것은 서버 내부의
일이다. 거기서 도착을 알리면 사용자는 다 왔다고 생각하고 멈춘다.

```
서버 안    legs = [계단1, 407호],  leg_index 0 → 1
앱한테     state="navigating" 이 처음부터 끝까지,  arrived 는 마지막에 한 번
```

앱은 이 파일의 존재를 모른다. **APP-FE 는 한 줄도 안 고쳤다.**

### 여기가 갈리는 지점

`PathTracker` 는 경유지에 닿아도 최종 목적지에 닿은 것과 **똑같이 `isLast` 를
올린다.** 경로 마지막 칸이라는 사실만 알지 그 경로가 왜 거기서 끝나는지는 모른다.

```python
# navigation_ws._transition_message
if is_last:
    leg = session.leg
    if leg is not None and not leg.is_final:
        return _handoff(session, leg)      # arrived 를 안 만든다
    ...
    return [out("arrive", "arrived", ...)]
```

세션이 들고 있는 구간 목록만이 둘을 가릴 수 있다. **그 상태를 두는 목적이
`arrived` 를 내보내기 위해서가 아니라 내보내지 않기 위해서다.**

---

## 3. 상태

`NavSession` 에 넷을 뒀다. 전부 서버 안에만 있다.

| 이름 | 뜻 |
| --- | --- |
| `legs` | 구간 목록. 같은 층이면 1개, 다른 층이면 2개 |
| `leg_index` | 지금 몇 번째 구간 |
| `awaiting_floor` | 층 이동이 끝나기를 기다리는 층 id. 아니면 None |
| `floor_since` | 지금 층으로 바뀐 시각 |

`destination` 은 예전 그대로 **사용자가 말한 최종 목적지**다. 구간이 바뀌어도
안 바뀐다 — 화면에 띄우는 이름이 이 값이라, 경유지 이름으로 덮으면 사용자가
목적지가 바뀐 줄 안다.

## 4. 구간 쪼개기 — `app/nav/legs.py`

```python
plan_legs(db, from_floor_id, dest_id, dest_name, origin_x, origin_y) -> list[Leg]
```

### 4.1 같은 층이면 하나

```python
if dest_floor_id is None or dest_floor_id == from_floor_id:
    return [Leg(..., is_final=True)]
```

`dest_floor_id is None` 은 **목적지가 연결자일 때**다. 연결자는 여러 층에 걸쳐
있어서 자기 층을 하나로 말할 수 없다. "계단1로 가줘"는 지금 층의 계단1을 뜻하는
것으로 본다.

### 4.2 연결자 고르기

두 조건을 **둘 다** 만족해야 후보다.

```
운행층      connectors.floors 에 출발 층과 도착 층이 다 들어 있다
좌표        두 층 도면에 모두 위치가 찍혀 있다
```

운행층만 보면 안 된다. 운행은 하는데 그 층 도면에 위치를 안 찍은 연결자가 실제로
있다 — 층 상태 `connector_missing` 이 그 경우다. 그걸 고르면 경로 노드를 찾을 수
없어 안내가 그 자리에서 끊긴다.

후보가 여럿이면 **지금 서 있는 자리에서 가장 가까운 것**을 고른다.

```python
pairs.sort(key=lambda cp: math.hypot(cp[1].x - origin_x, cp[1].y - origin_y))
```

좌표를 못 구하면 첫 번째를 고른다. 층 이동은 되고 멀리 도는 것뿐이라, 여기서
막지 않는다.

### 4.3 갈 수 있는 연결자가 없으면

```
4층으로 갈 수 있는 계단이나 엘리베이터가 없습니다.
관리자웹에서 두 층을 모두 운행하는 연결자에 위치를 찍어주세요.
```

1층→4층인데 그 계단이 3층까지만 간다면 갈아타야 한다. **지금은 안 한다.**
`legs` 는 N개를 담을 수 있게 해뒀지만 만드는 것은 최대 2개다.

## 5. 층 이동 판정

### 5.1 언제 "끊겼다"고 보나

**①구간의 도착 판정이 난 뒤에만** 층 이동으로 해석한다.

도착 전에 신호가 끊기는 것은 층 이동이 아니라 신호 골짜기다. 그건 지금까지 하던
대로 기다린다(§2부 `next_rising` 참고). 둘을 구분하지 않으면 코너를 돌 때마다
층이 바뀐 줄 알게 된다.

### 5.2 판정을 멈춘다 — `_handoff()`

```python
session.tracker.end_session()      # active=False. 경로는 남긴다
session.stop_recording("층 이동")
session.awaiting_floor = leg.next_floor_id
```

`end_session()` 은 측정만 끄고 경로는 그대로 둔다. `/monitor` 가 1층 경로를 계속
그릴 수 있어야 층 이동 직전 상태를 볼 수 있다.

말은 이렇게 나간다.

```
계단1입니다. 계단을 이용해 4층으로 이동해 주세요.
```

엘리베이터면 "엘리베이터를 타고". `event` 는 `advance`, `state` 는 `navigating`
이다 — 앱은 안내 화면에 머문다.

### 5.3 언제 "도착했다"고 보나

**새 층의 비콘이 잡힌 것** 하나만 본다. 시간을 재지 않는다 — 계단을 오르는 속도는
사람마다 다르고, 엘리베이터는 몇 층을 더 돌기도 한다. 목표 층 신호가 들어온 것보다
확실한 증거는 없다.

펌웨어에 `major = 100 + 층` 이 새겨져 있어서 `_locate()` 가 이미 층을 따라간다.
`_maybe_resume()` 은 그 결과가 기다리던 층인지만 확인한다.

### 5.4 지나가는 층

계단통을 오르는 동안 2층·3층 비콘이 잠깐씩 잡힌다. 그걸 곧바로 "내렸다"로 읽으면
층마다 안내를 새로 만들며 계속 말한다.

```python
WRONG_FLOOR_DWELL_MS = 5_000
```

기다리던 층이 **아닌** 곳에서는 5초를 머물러야 인정한다. 목표 층은 이 대기가
없다 — 거기서 멈출 것이 확실하므로 기다릴 이유가 없다.

### 5.5 엉뚱한 층에 내렸으면

엘리베이터에서 층을 잘못 눌렀을 수 있다. 그때는 **다시 쪼갠다.**

```python
return _start_route(session, dest)   # 최종 목적지는 그대로
```

3층에 내렸으면 3층에서 4층으로 가는 안내가 새로 나온다. 같은 함수를 다시 부르는
것뿐이라 특별한 처리가 없다.

### 5.6 층을 정하는 길은 하나다

`_locate()` 는 **층이 실제로 바뀌었을 때만** True 를 돌려준다.

```
건물   MAC 으로 한 번만
층     그 건물 안에서 major 로 — 첫 층도 포함해서 언제나
```

예전에는 **첫 층만 MAC 으로** 정하고 그 뒤로만 major 로 따라갔다. 길이 둘이어서
`session.major` 가 첫 분기에서 안 채워졌고, 두 번째 분기는 층이 같으면 저장 전에
빠져나가서 **출발 층에 있는 내내 None 이었다.**

```
첫 비콘 뒤 :  floor_id = f-1   major = None
같은 층 계속:  floor_id = f-1   major = None
```

§6 의 필터가 이 값을 쓰므로, None 이면 아무것도 안 걸러진다. 계단 근처에서 위층
신호가 새어 들어오면 그것이 출발 비콘으로 뽑힌다. **§6 은 §5.6 없이는 반쪽이다.**

```python
session.major = major          # 층이 그대로여도 저장한다
if floor_id == session.floor_id:
    return False               # 저장한 뒤에 빠져나간다
```

`building_from_mac()` 도 층을 안 돌려주게 바꿨다. 안 쓰는 값을 돌려주면 "여기서도
층을 정할 수 있다"는 오해가 남는다.

MAC 과 major 는 **같은 메시지에 함께 온다.** `NavClient.sendBeacon` 에서
major/minor 는 필수이고 mac 만 nullable 이다 — major 는 iBeacon 광고 바이트
`[18..19]` 에서 뽑는 값이라 없을 수가 없다. 그래서 한 번에 둘 다 정해진다.

## 6. 떠나온 층의 필터 — 조용한 함정

**칼만 필터는 신호가 끊겨도 값을 잃지 않는다.** 마지막 추정값을 그대로 들고 있다.
한 층에서만 쓸 때는 그게 오히려 안정적인데, 층을 옮기고 나면 문제가 된다.

```
4층에 막 도착한 순간의 filters

  101-26   -45.0   ← 1층. 20초 전 값인데 아직 제일 세다
  104-26   -72.0   ← 4층. 방금 잡혀서 아직 약하다
```

출발점을 "가장 센 비콘"으로 고르므로 1층 비콘이 뽑힌다. 그러면 4층 설치 목록에서
못 찾아 이렇게 끊긴다.

```
지금 잡히는 비콘이 이 층에 등록되어 있지 않습니다 — 101-26
```

minor 로 거를 수도 없다. minor 는 층 안에서만 유일해서 1층 26번과 4층 26번이
**둘 다 `minor=26`** 이다. major 가 층을 담는 유일한 값이다.

```python
strongest_beacon_key(filters, major)      # major 가 맞는 것만 본다
```

`resolve_origin` · `origin_point` · `plan_route` 가 전부 `major` 를 받아 넘긴다.

**아무것도 지우지 않는다.** 옛 값은 `filters` 에 그대로 남고, 출발점을 고를 때만
건너뛴다. 지우는 방법도 있었지만 층 판정이 한 번 흔들렸다 돌아오면 날아간 이력을
다시 만들 수 없다. 거르는 것은 되돌릴 수 있고 지우는 것은 못 되돌린다.

"마지막 갱신 시각이 오래된 것을 빼는" 방법도 있다. 몇 초를 오래됐다고 볼지가 또
실측이 필요한 값이라 미뤘다. major 는 정할 것이 없다 — 4층 경로를 세울 때 4층
비콘만 보는 것은 기준이 아니라 정의다.

## 7. 다른 층 목적지를 어떻게 말하나

1층에서 "407호"라고 말해야 하는데, 목적지 목록은 **지금 층 것만** 내려간다.

### 순서를 둔다

```
① 지금 층에서 찾는다
② 못 찾으면 다른 층에서 찾는다
```

처음부터 건물 전체를 후보로 두지 않는 이유는 **화장실** 때문이다. 층마다 있으니
건물 전체를 보면 "화장실"이라고 말할 때마다 다섯 개가 나와서 "몇 층 화장실이요?"를
되묻게 된다. 사용자가 원한 것은 거의 언제나 지금 층의 화장실이다.

이 순서면 "407호"는 이 층에 없으니 자연히 다른 층에서 찾히고, "화장실"은 이 층에서
끝나서 다른 층 것이 끼어들지 않는다.

### 다른 층의 연결자는 후보에서 뺀다

계단·엘리베이터는 층마다 같은 이름으로 있다. 다른 층 것까지 넣으면 "계단1"이 여러
개가 되는데, 다른 층 계단을 목적지로 삼는 것은 뜻이 없다 — 거기 가려면 어차피 이
층 계단을 타야 한다.

## 8. 흐르는 순서

```
on_destination
  └ _start_route(최종 목적지)
      ├ _plan_legs()              legs.plan_legs
      └ _start_leg()              ← 구간 하나. 층을 넘는 것을 모른다
          ├ plan_route(floor_id=leg.floor_id, major=session.major)
          ├ _build_cues()
          ├ tracker.set_path() / start_session()
          └ "407로 안내합니다. 손이 닿는 벽을 짚고…"

on_beacons (매 스캔)
  ├ _locate()                     major 로 층을 따라간다
  ├ _maybe_resume()               awaiting_floor 면 여기서 다음 구간
  └ tracker.evaluate()
      └ _transition_message()
          └ isLast + not is_final → _handoff()
```

두 번째 구간의 출발 안내만 문구가 다르다.

```
첫 구간    407로 안내합니다. 손이 닿는 벽을 짚고 걸어주세요.
두 번째    407로 계속 안내합니다.
```

"손이 닿는 벽을 짚고"를 다시 말하지 않는다. 이미 그러고 있는 사람에게 반복하면
새 지시로 들린다. 대신 최종 목적지를 다시 짚어준다 — 층을 옮기는 동안 어디로 가는
중이었는지 잊기 쉽다.

## 9. 기록

구간마다 CSV·JSON 한 쌍이 따로 남는다. 한 안내에 파일이 두 쌍 생긴다.

```
B26_계단1_20260822-100633.csv/json     구간 1 — 끝난이유 "층 이동"
B03_407_20260822-100712.csv/json      구간 2 — 끝난이유 "도착"
```

JSON 에 구간 정보가 들어간다.

```json
{ "목적지": "계단1", "최종목적지": "407", "구간": "1/2" }
```

나누는 편이 낫다고 본 이유는, 층마다 신호 환경이 달라서 한 파일에 섞으면
`eval_tracker.py` 로 다시 돌릴 때 어느 층 문제인지 안 갈리기 때문이다.

| 지나가는 층에서는 구간이 안 넘어간다 | ✓ |
| 목표 층에서 다음 구간이 시작되고 경로가 그 층 비콘으로만 찬다 | ✓ |
| 화면에는 경유지가 아니라 최종 목적지가 뜬다 | ✓ |
| 떠나온 층 필터가 출발점을 가로채지 않는다 | ✓ |
| 출발 층에서도 `session.major` 가 채워진다 | ✓ |

기존 스위트도 전부 그대로 통과한다(합계 282개).

## 11. 아직 없는 것

| | |

| 세 구간 이상 | 갈아타야 하는 층 조합. 지금은 "갈 수 있는 연결자가 없습니다" |

| 연결자 선택에 사용자 사정 반영 | 계단을 못 쓰는 사람에게 엘리베이터 우선 |

`WRONG_FLOOR_DWELL_MS = 5000` 은 **실측으로 정한 값이 아니다.** 계단통에서 지나가는
층 비콘이 실제로 몇 초 잡히는지 재본 적이 없다. 짧으면 지나가는 층에서 안내가
새로 나오고, 길면 정말 잘못 내렸을 때 알려주는 게 늦는다. 첫 실측에서 봐야 한다.
